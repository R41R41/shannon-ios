# Haiku model and cache contract

Status: implementation authority for the Haiku migration candidate. Production activation and Apple delivery require their own verified gates and owner approval; this contract does not assert that the candidate is deployed. Own-time shared-key activation requires a separate verified environment receipt.

This contract owns the current small-model provider, credentials, cache and cost boundary. [architecture.md](architecture.md) owns response/worker boundaries, [skill-and-routing-contract.md](skill-and-routing-contract.md) owns logical tier selection, and [self-improvement-runbook.md](self-improvement-runbook.md) owns delivery. [model-mode-contract.md](model-mode-contract.md) owns the owner-selected primary model policy and its separate readiness gates.

## Selection and compatibility

`DEFAULT_HAIKU_MODEL` in `infra/models/anthropic/haikuConfig.ts` is `claude-haiku-5-5`. Normal factories resolve an absent setting or the replaced `gpt-5.6-luna` family, including dated suffixes, to Haiku. Other deliberately configured model IDs remain unchanged. Existing own-time preferences retain their stored model ID, reason and timestamp: the registry resolves an old Luna preference to equivalent Haiku research/reading or planning at use time, without rewriting the preference. Gemini prose/critique and GPT Terra/Sol registry entries retain their behavior.

Text, voice reply, Jev's lightweight fallback and the migrated small-model background paths use the official `@anthropic-ai/sdk` native Messages API when they resolve to Haiku. Explicit non-Haiku models use their existing provider path; OpenAI transcription, embeddings, explicit Terra/Sol and Gemini synthesis/vision remain separate capabilities. The pattern-wiki maintainer retains its explicit Terra default.

`luna`, `luna_plus`, `luna_weak` and `judgedBy: luna` are durable logical symbols in existing policies and ledgers. Preserve them and historical rows; actual model fields identify the model that was asked. Haiku and Sonnet both use provider `mode: anthropic`, so `servedTier` independently identifies which logical tier answered. `SHANNON_SONNET_ROUTING=off` blocks the Sonnet conversation tier and leaves the Haiku base model available. The separately gated sleep proposer keeps its existing Sonnet rule.

## Credentials and native transport

| Path | Credential | Boundary |
| --- | --- | --- |
| Regular Haiku | `SHANNON_HAIKU_API_KEY`, else `SHANNON_ANTHROPIC_API_KEY`, else `ANTHROPIC_API_KEY` | The first setting is Haiku-only; the existing shared-key fallback remains for compatibility. Server only; no key is returned to a client or prompt. |
| Existing Sonnet hooks | `SHANNON_ANTHROPIC_API_KEY`, else `ANTHROPIC_API_KEY` | Haiku-only key addition does not activate Sonnet routing or the sleep proposer; their existing gates and Terra fallback remain. |
| Own-time Haiku | `SHANNON_AUTONOMY_ANTHROPIC_API_KEY` only | The setting is always required explicitly. Equality with any of the three regular Haiku/Anthropic values is unavailable by default; only owner-authorized `SHANNON_AUTONOMY_ANTHROPIC_SHARED_KEY=on` permits equality. There is no regular-key fallback. |
| Own-time Gemini/GPT | Their existing `SHANNON_AUTONOMY_GEMINI_API_KEY` / `SHANNON_AUTONOMY_OPENAI_API_KEY` | Existing dedicated-key, distinct-value and registry boundaries remain; the Anthropic opt-in does not apply to Google/OpenAI. |

The owner's current instruction may authorize the Anthropic same-value opt-in above; it does not authorize regular-key fallback or a different provider's sharing. The shared key's provider cap is not a separate own-time-only spending limit. Existing application daily/session budgets, reservations, caller stop checks, unknown outcomes and mandatory cache requirements still apply.

Native clients explicitly select the official API origin, `authToken: null`, `webhookKey: null`, `logLevel: off` and `maxRetries: 0` (`claudeClient` in `infra/models/claude/claudeClient.ts`). The Sonnet skill proposer is the one exception kept as it was: no SDK retries and its own deadline, but not pinned (`ambientClaudeClient`), until a stage that may change requests pins it. The only retry is the conversation chat model's one bounded Haiku retry (`infra/models/claude/claudeTransport.ts`, Haiku only; Sonnet never retries): a 429/529/5xx refusal, or an overloaded/api error event before `message_start`, of a turn's first request that returned no usage and handed out no word is retried once after the provider's `retry-after` (default 1 s, at most 3 s); no tool has run then. A stream that failed after `message_start`, a connection failure or an abort is never retried. Ambient SDK bearer-token/base-URL/log settings must not change the credential or transport boundary. Model failures expose closed codes, never SDK error text containing request material or a credential.

The own-time adapter combines request, current-action and timeout cancellation signals and rechecks the live action permit immediately before its only request. It uses adaptive thinking at low effort while retaining the existing maximum output-token ceiling; thinking consumes that same output budget. No request is resent automatically after an uncertain outside result. Existing stop, scope, audience, approval and permission gates remain authoritative.

### Lazy tool menus and signed history

For exactly `claude-haiku-5-5` and `claude-sonnet-5-5`, foreground text and voice function-tool rounds use `inline-tools-2026-09-15`. Their top-level tools are the fixed, non-deferred strict `tool_open` and `tool_call`. The opener's `name` is a required string without a changing catalog enum; the bridge requires `name` and `argumentsJson`. The current offered names/descriptions, tool-specific and audience instructions, and admitted selected/always-loaded strict schemas follow the current user turn and context in a mid-conversation system section. Schemas use the SDK's `tool_addition` / `tool_definition` shape and are usable in the first decision. Jev still selects the menu. Changing his selection or the offered catalog does not change this tool prefix or insert a menu into the top-level system. Introducing the fixed bridge changes the prefix once; later menus share that same two-tool prefix.

Before either text or voice instructions are built, a native 5.5 session without a menu is normalized to the same lazy protocol. An oversized direct/chosen menu starts with its offered always-loaded controls, while all original tools remain discoverable. Initial and subsequent native-schema admission is then evaluated against the actual complete provider request by `anthropicToolCapacity.ts`, including both fixed tools, inline additions and the text output schema. Always-loaded controls have admission priority. Selected definitions that do not fit are supplied as quoted input-schema data and remain callable through `tool_call`; no selection grants new authority. This covers Jev timing out, failing, being disabled or absent. The original session retains its deadline, audience, call count, execution gate, cancellation, per-call identity and result recording. The opener cannot open an unoffered tool. The bridge accepts only originally offered, already opened tools, bounds the JSON string to 512,000 characters, validates its object shape and delegates to the original session's input validation and execution gate. It cannot invoke the meta-tools recursively.

After `tool_open` succeeds, its result supplies the original input schema as data. If the definition fits, a system `tool_addition` carries the full strict definition by value and its normal name remains usable. Otherwise the opened tool remains executable through the bridge. Reopening or calling an already selected tool adds no duplicate definition. Top-level tools/system and accepted earlier messages, including signed thinking and tool results, remain unchanged throughout the turn. Foreground stored conversation turns remain their existing public text history; no signed provider history is rewritten to obtain a hit. Deliberately configured Haiku 4.5 and older Sonnet overrides retain their previous menu transport. No-tool replies and native server web search retain their separate request shapes, including signed pause continuations and search evidence checks.

The provider permits at most 20 strict tools, 24 optional parameters and 16 union parameters across the complete request's strict schemas and JSON output schema, including inline definitions. The full-registry fallback's initial request is verified offline as 6 strict tools, 11 optional parameters and 9 union parameters. Admission stays within those explicit limits, but the provider also has an internal compiled-grammar complexity limit: on 2026-10-13 a voice turn with 10 strict tools, 19 optional and 10 union parameters was refused. A definition is therefore strict only within `ANTHROPIC_GRAMMAR_BUDGET` (8 strict tools, 12 optional, 12 union parameters, controls and the owner's voice lookups first); every other selected or opened definition is added as a native non-strict tool, callable by its own name, and the original executor validates its input. An explicit HTTP 400 saying that the compiled grammar is too large still permits one bounded transition: definitions in the unaccepted request tail lose strict decoding (they stay native tools), accepted messages remain byte-identical, and the turn continues with `tool_choice: auto`. No prior tool is executed again, and no unknown network/paid/write outcome is retried. Later tools are added non-strict that turn. When the provider still refuses and the turn answers without tools, she is told so (`TOOLS_FAILED_NOTE`) and does not invent a reason. Diagnostics expose numeric status, a closed category and structural schema counts, never provider text or request material. Since ADR-0009 stage 1 (`anthropicRejection.ts`) every 4xx is counted by `status:class` (`GET /v1/ops`, `server.execution.modelRequestRejections`) and logged as `anthropic_request_rejected` with its status, the provider's error type, a closed message class (`strict_grammar_capacity`, `strict_tool_capacity`, `tool_schema_invalid`, `inline_tools_unsupported`, or `unclassified`) and whether the request offered tools or schemas. During the canary any 4xx except 401/403/408/409/429 still earns the one tool-less answer; `SHANNON_ANTHROPIC_STRICT_REJECTIONS=on` limits it to a 400 that names the offered tools or schemas, the rest being handled like any other error. [Structured-output limits](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), [inline tool definitions](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages#define-tools-in-a-message-beta).

Strict decoding is off for conversation tools by default (2026-10-13, `strictConversationTools` in `anthropicToolCapacity.ts`): the fixed pair, the selected definitions and every opened definition are sent as native non-strict tools, and the strict admission above applies only with `SHANNON_STRICT_CONVERSATION_TOOLS=on`. Reason, measured on the VM against `claude-haiku-5-5` with the production request shapes: the provider compiles one grammar per request tool set (with the text output schema), caches it, and a tool set it has not compiled before (the turn's selection varies) delays the first event by 5.5–7.6 s (voice, strict pair + two inline definitions: 6.9–8.2 s first event against 1.4–1.6 s for the same set repeated; with no strict tool at all: 0.7 s, fresh or repeated; text with its strict output schema: 5.5 s fresh with non-strict tools against 8.8 s with strict ones, 1.3–1.8 s repeated). A description change does not recompile; a new property or tool name does. Eight strict inline definitions were refused as a too large grammar. Executors validate every input, so strictness only saved a retry of a malformed call. The text output schema stays strict.

Haiku's voice turn does not think before it speaks (`thinking: disabled`) unless `SHANNON_HAIKU_VOICE_THINKING=on` (owner-approved 2026-10-13; `haikuVoiceThinking` in `anthropicConfig.ts`): at effort `low`, adaptive thinking still spent 450–650 hidden tokens and 2–3 s before the first word of a one- or two-sentence spoken reply (the same probe). Haiku rejects `between_tools`, the Sonnet tier's voice setting. Text keeps adaptive thinking, except a light or read-aloud text turn that is neither hard nor research, which answers with `disabled` too (owner decision 2026-10-14, `SHANNON_TEXT_LIGHT_NO_THINKING`; the rule is in [skill-and-routing-contract.md](skill-and-routing-contract.md#thinking-of-a-text-turn-owner-decision-2026-10-14-shannon_text_light_no_thinking)). Prompt-cache reads did not change the time to the first event measurably at 21–25k input tokens (cost only).

性能上の制約：公開されている個数上限内でも内部の文法サイズで拒否される組合せは、次の会話でも最初に通常の定義を送り、明示的な400を受けてから橋の呼び出しへ移るため、通信が1回増える。既存の能力、入力検証、実行権限、受理済み履歴とキャッシュの固定部分を保つことを今回の修正では優先する。拒否された組合せを次の会話で先に避ける学習や永続的な能力フィードバックは実装していない。実測の待ち時間やキャッシュ利用率は、固定部分の一致やオフライン試験から推測せず、提供側の実際の受領結果で確認する。

### One transport (ADR-0009 stage 1, M3)

Every Claude request leaves through `infra/models/claude/`: `claudeClient.ts` builds the SDK client of each credential lane, `claudeTransport.ts` sends a conversation request (text, voice, native web search: created or streamed, with the action permit, round deadline and abort signals, the voice stream bounds, first-token timing, usage capture and booking, the cache receipt, the cache-evidence check, the observer span and the transient retry), `claudeOnce.ts` sends a one-shot request (FCA, the skill proposer, the background route) inside its observer span with its cache receipt, and `claudeUsage.ts` holds the prices, the counts and the booking of a usage row. Request builders, the tool loop and each caller's reading of the answer stay with the callers. Her own time's adapter uses only the pinned client and the usage counts: it has no span and no receipt, and its process loads nothing of the conversation's transport (`autonomyLoopPrivacy.test.ts`). The request goldens (`services/api/tests/claudeRequestGoldens.test.ts`, `tests/fixtures/claude-requests/`) record, for synthetic scenarios, every request byte, booked usage row, cache receipt and result; the extraction changed none of them.

### One tool loop and the background route (ADR-0009 stage 1, M7–M8)

- **One tool loop** (`claude/claudeToolLoop.ts`, `claudeToolLoop`): every Claude request that may take more than one round goes through it: text and voice turns of Haiku and Sonnet (rounds against the turn deadline, the session as the executor, inline `tool_addition`s, the acknowledged grammar bridge, the deadline notes, the read recovery, refusals, the cache plan's decline and fallback), the native web search and page read (their `pause_turn` continuations, at most three; a refusal is read by the caller, `refusal: 'final'`), and the FCA step (`maxRounds: 1`: one request, its runner executes the calls and answers in the next decision). The duplicated pause loops are gone. Every request golden was unchanged by this.
- **The background route** (`claude/claudeStructured.ts`, `completeStructured<T>(route, system, input, schema, options)`): the 17 background callers (18 call sites: the turn checker, the spoken report, organize, the replay summary and its template, person facts, impressions, the platform summary, sleep, knowledge, the skill sleep, memory rewrite, rerank and sections, the daily mind, a touch, a room look, a voice photo, the voice router) build no OpenAI Responses body for a Claude model any more. The route builds the native request (protocol prefix, the caller's instructions, its input as text or native messages with image blocks, adaptive thinking at the caller's effort, its schema in the supported subset, an output ceiling of at least 1,024), sends it through `claudeOnce.ts` (span, `background` receipt), books one usage row in the route's lane (`BACKGROUND_ROUTES`: `chat`, `voice`, `memory`, `memory_background` or `sleep`, as each caller booked before) before anything is checked, and then throws the same closed codes as before (`HAIKU_CACHE_*`, `HAIKU_RESPONSE_USAGE_INVALID`, `_REFUSAL`, `_INCOMPLETE`, `_UNSUPPORTED_BLOCK`, `_EMPTY`; `BACKGROUND_MODEL_USAGE_UNKNOWN` first for an FCA-accounted call). A provider refusal returns `{ ok: false, status, body }` and books nothing, so each caller keeps its own error code. A model that is not Claude (`claudeBackground` returns null) keeps its OpenAI Responses request byte for byte (the Terra defaults of knowledge and the skill sleep, the historical OFF proofs). The fake fetch (`haikuResponses.ts`) is deleted. The 18 background goldens were re-recorded: the only change is the three `cacheCreationInputTokens*` fields the shim's Responses usage had spread into each usage row (the store never kept them); request bytes, costs, receipts and outcomes are the same.
- **No Responses IR on the Claude path**: the text and voice requests (and their cache-plan forms) are built from `chatTurnInstructions`, `chatTurnSchema` and `claudeTurnMessages` (history joined by role, a marker before a first turn of hers, her preceding words, the owner's words with an attachment's projection, the turn's context as one `system` message after them), never from `chatTurnRequestBody`, which stays the OpenAI adapter's body. Every request golden is byte-identical.
- What stays for M9: the `Tiered`/`PrimaryMode` wrappers and their `luna*` names, the OpenAI chat adapter (still the provider of an explicitly configured GPT `SHANNON_LLM_MODEL` and of the historical OFF proofs), the own-time adapter's own client use, and the Sonnet skill proposer's ambient client.

## Mandatory useful one-hour cache

Every Haiku Messages request and owner-selectable native Sonnet 5.5 conversation request passes through `cacheHaikuRequest` in `haikuCache.ts`, except foreground text turns under the cache plan (next section), which use `cachePlanRequest`, and the background route (`claudeStructured.ts`, below), which uses `cacheOneShotRequest`: the same protocol prefix with its 1h breakpoint, and no automatic marker on the unique task tail (ADR-0009 stage 1); the prefix alone is above the 512-token minimum, so each call still reports a cache write or read. That route passes the caller's effort through (`none`/`minimal` → `low`, `low`, `medium`, `high`). It adds a stable, useful transport protocol describing quoted reference material, task/schema fidelity, uncertainty and separation of thinking from the final result. It does not replace Shannon's canonical persona or grant a new ability. Task-specific instructions and variable input retain their existing authority and meaning.

The stable prefix must reach at least 512 tokens for the selected native 5.5 model, verified with the native token-count API rather than character count. Its explicit cache breakpoint and automatic conversation caching both use `ttl: 1h`. Existing breakpoints are checked for compatible TTL and the native breakpoint limit; repeated application does not duplicate the prefix. Tools/system precede changing conversation material so repeated requests can reuse the stable part.

Anthropic caches in tools → system → messages order. The fixed foreground opener and relocated menu remove the selected schema/catalog enum and menu text from the earlier prefix. They do not guarantee a provider cache hit: first use, expiry/eviction, model or workspace changes, a different no-tool/server-tool lane, upstream capability/persona/profile or output-schema changes, thinking/image settings, and changed or compacted conversation history can still reduce reuse. Existing surface capability lines are preserved and can change when the surface's available capabilities change. Text and voice have distinct instructions/output formats. The current turn's context and inline menu remain variable and require processing; a new schema combination may also require structured-output compilation. A long inline menu can exceed automatic caching's 20-content-block lookback to a matching history block; the explicit protocol/system breakpoints remain available, but full history reuse is not guaranteed. Provider cache-read/write counts, rather than local prefix equality or elapsed time, establish actual reuse. [Cache hierarchy and invalidation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

A cache-control block alone is not proof of caching. After a real response, require safe, nonnegative integer input, output, cache-creation and cache-read counts and positive creation or read usage. A response with known zero creation and zero read fails closed after recording its actual spent usage, except for Haiku in the conversation chat model (`AnthropicChatModel`), including its native web search (`searchWeb`): there the answer is valid and already paid, its complete usage is booked at the measured uncached price, and the anomaly is logged (`Shannon model cache unconfirmed`) instead of discarding the turn (stabilization 2026-10-12). Sonnet keeps failing closed (its turn falls back to Haiku before any word), as do the FCA and own-time models and any malformed or incomplete count. Missing/null/malformed required counts and stream receipts before finalMessage leave the final usage unknown; known lower-bound counts are retained with a conservative cost bound, and an own-time reservation is not settled as zero. Known refusal, truncation, empty output or a cache-contract failure retains known tokens and cost. Returned task text excludes internal thinking.

Requests use one-hour cache controls. Provider server tools can additionally produce five-minute cache writes; valid native five-minute/one-hour usage breakdowns are accepted and charged at their actual TTL. An absent breakdown uses the conservative one-hour write price for Haiku. This preserves existing web-search/tool behavior. See the [official prompt caching documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

For a streamed native web-search request, the SDK can retain the start TTL split while final cumulative creation grows and `message_delta` omits that split. Capture the initial counters and TTLs as immutable values, before the SDK mutates its snapshot. After `finalMessage`, a matched server search/result (including an original pending call across a bounded pause) permits only the additional creation to be classified as the provider's [automatic five-minute server-result cache](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching#server-tool-results-are-cached-automatically). Preserve the initial one-hour creation and all signed content. This is a derived TTL breakdown, not an explicit final provider split. Explicit final TTL data remains authoritative; a legal null keeps conservative one-hour pricing, and a malformed object still fails after recording spend. Ordinary/nonstreamed requests and incomplete usage are not repaired by this rule.

### Foreground cache plan (ADR-0009 stage 1, M4)

`SHANNON_CLAUDE_CACHE_PLAN` (off by default; `explicit_on`) makes every foreground text turn of `claude-haiku-5-5` and `claude-sonnet-5-5` repeat one prefix, so a follow-up turn reads what the previous turn wrote (`anthropicCachePlan.ts`, `cachePlanMarkers.ts`). Voice follows the same plan under its own switch (M6, below); the history is rendered once per epoch under replay epochs (M5, below).

- Tools: always the fixed pair `tool_open` / `tool_call` with `tool_choice: auto`, also in a turn that offers no tool. Such a turn says so in its own lines ("tool_open と tool_call は呼ばずに"); a call it makes anyway runs nothing, is answered once with a `not_offered` tool result, and the answer after it is asked for with `tool_choice: none`, so a second stray call cannot end the turn (`declineUnofferedCalls`).
- Output: the common schema, exactly the one an owner turn that offers only her feeling has without the plan (the base fields and `feeling`; 10 union parameters). A turn that does not offer her feeling sends it too, told that `feeling` is null. A turn that offers a rarer field (`places`, `roomLook`, `appLook`, `minecraftIntent`, the required web read's `webSearchNeedsInput`) is an exception: it sends the schema it has without the plan; tools, system and the breakpoints stay those of the plan (`exceptionTurn`, the body's mark `planSchemaOf`). The provider documents that a change of `output_config.format` "will invalidate any prompt cache for that conversation thread" and that the format adds a system prompt of its own; whether the static prefix (BP1) survives such a change is not stated, so an exception turn may also miss BP1, and the next common turn reads at most what was written before the exception. The probe's `plan-exception-looks` measures it. Why not one superset: on the VM probe (2026-10-12) a superset with every rarer field (first nullable, 15 unions; then non-nullable, 10 unions) was refused as `strict_grammar_capacity` with the always-loaded controls, while the plan-off owner schema with identical tool, optional and union counts passed: the refusal follows the schema's size, not its union count. A grammar refusal still never fails a turn: the bridge asks again in the plan's prefix with the definitions as quoted data, a second refusal answers without tools in the shape without the plan, and a turn without tools falls back as described below.
- System: her identity, the fixed instructions, what she knows of the owner, `CLAUDE_TEXT_LINES` and, in the app's own Talk, rich chat's lines (`RICH_TEXT_BLOCK_INSTRUCTIONS`, as without the plan; they depend on the surface, not the turn). Everything that depends on the turn moves into the turn's system message after the owner's words: the tool-dependent capability lines `withToolCapabilityLines` inserted (taken back out of the identity by `splitCapabilityLines`), the skill index (`splitSkillIndex`), the reply-feeling instructions, the tool or no-tool line, the web-answer line and the unused-fields line. The menu and its inline definitions follow as before.
- Effort and thinking: as configured (Haiku at medium), never changed by the turn.
- Breakpoints, placed by the transport on each request whose body the plan built (a symbol mark that object spreads keep and JSON never sends; `isPlannedBody`): BP1 (1h) on the last system block, after the protocol prefix, which has no marker of its own; BP2 (1h) on the last block of the turn's latest words; BP3 (5m) on the latest tool result after them, since the rounds of a turn follow within seconds and the usage check accepts a five-minute share of the creation. No top-level automatic marker. BP1 keeps the cache-evidence rule satisfied on every request.
- Refusals (review F1): when the first request of a plan turn without tools is refused with a 400 the rejection classifier names (`strict_grammar_capacity`, `strict_tool_capacity`, `tool_schema_invalid`, `inline_tools_unsupported`), the turn is asked once more with exactly the request the plan-off model sends (logged as `cache_plan_fallback`, counted); nothing ran and no word went out. A plan turn with tools keeps its existing recoveries, and its tool-less answer uses the plan-off body and schema. Any other refusal is handled as without the plan.

The goldens `plan-*` hold the shapes (`plan-text-rejected-fallback` and `plan-text-tools-rejected` the refusals); `plan-text-talk` is a Talk of three different turns (feeling, tools with a capability line and the skill index, a web search), and `adr9CachePlan.test.ts` asserts that each turn's request repeats the previous turn's prefix byte for byte up to that turn's BP2. With the switch off every earlier request golden is unchanged.

What actually hits is measured, not inferred. `GET /v1/ops` `server.modelCache.foregroundText` (`cacheWarmTurns.ts`; in this process only, empty again after a restart) shows per day and lane (`plan` for the common schema, `plan_exception`, `base`) the text turns that followed the previous turn of the same Talk and model within an hour (`warmTurns`), how many read anything and how many read the history: more than the static prefix, whose size is learned per prefix fingerprint from a first request without history that read the cache (`warmTurnsWithHistoryRead`, `historyReadRate`; until the size is known a warm turn counts in `warmTurnsPrefixUnknown`). Reading the static prefix alone is guaranteed by BP1, so only the history rate is the canary's measure. Beside them: `warmReadShare` (read / all input), the creation warm turns still paid, the first-token time of turns that read the history and turns that did not, the plan's events per surface (`text:fallback`, `text:plain_recovery`, `text:grammar_bridge`, `text:declined`, `text:schema_common` / `text:schema_exception` per plan turn, and `text:recovered` for a turn that answered after a refusal), and how often an offered feeling was answered per lane. A plan turn that fell back is counted in the `base` lane, the shape it was sent in. The daily log line carries `warmTextReads=plan=<history reads>/<warm>,base=…`. A Talk is kept there only as an 8-character hash.

`services/api/scripts/cache-plan-probe.ts` (never run by the tests) sends synthetic text-turn requests per model, prepared as the transport prepares them: the plan with no tool, with the always-loaded controls only (`minimal`, what every text turn with tools carries), with two selected definitions (`typical`), and an exception turn offering both looks after them (`plan-exception-looks`: its cache read shows whether BP1 survives the format change); `--compare` adds the same offers without the plan and a heavy offer. It prints only the strict-schema counts, the schema's length and whether a plan request's format equals the plan-off one, the status, stop reason, usage counts and an estimated cost (output ceiling 256 tokens; stop at an estimated $0.03 for Haiku, $0.05 for Sonnet).

### Replay epochs (ADR-0009 stage 1, M5)

`SHANNON_REPLAY_EPOCHS` (off by default; `explicit_on`; needs `SHANNON_CLAUDE_CACHE_PLAN`) makes the replayed history append-only (`conversationWindow.ts`, `epochReplayWindow`). Without it the window is recomputed every turn and a text message is clipped by its position (the newest 20 as stored, older ones to 1,500 characters), so a long message changes its bytes when it leaves the newest 20 and every later turn misses the history the previous turn wrote.

- An epoch is cut (a rebase) to the newest messages up to the fill, three quarters of the budget, with the rule's clipping at that moment: the newest `minimumMessages` as stored (voice: 600 characters), older ones clipped. From then on each new message is appended as stored and no replayed message changes a byte, so every turn of the epoch repeats the previous turn's request up to its words (BP2).
- The epoch is cut again when it passes the budget or the message limit (unless it holds only the newest `minimumMessages`, which a cut would keep anyway), when its first message or the message it replays as stored from is no longer replayed (forgotten, withheld, or out of the 400 read), or when the budget changed. The room between fill and budget, a quarter, is some ten text turns. The trace block of her tools follows the words and never moves the start.
- The text budget is 32,000 characters when `SHANNON_CONVERSATION_REPLAY_CHARACTERS` is unset (owner answer 4, 2026-10-12: widened only where the cache carries it; a set value still wins). With Haiku's system and tools that is about 45k-55k input tokens a turn, well under the 100k-token price threshold. Voice replays in epochs only with the voice plan on as well, and keeps `SHANNON_VOICE_REPLAY_CHARACTERS` (12,000 when unset).
- Kept in `conversation_replay_epochs` (one row per thread and channel: the epoch number, the first message's id, the id the epoch replays as stored from, the budget, the time; never a word), created additively with `CREATE TABLE IF NOT EXISTS` at store open, and only while the switch is on (off: no table, every table as it was), beside `conversation_replay_summaries`, outside the numbered migrations: an older binary never reads it. A missing or unwritable row only starts a new epoch.
- The replay summary covers, under epochs, everything older than the newest fill less that room (half the budget; `summaryCoverRule`), which a cut after the next turn can leave out. The background worker must see the same switch.
- `GET /v1/ops` counts `text:epoch_rebase` / `text:epoch_kept` (and `voice:…`) under `modelCache.foregroundText.events`.

`adr9ReplayEpochs.test.ts` plays 25 text turns (some replies longer than 1,500 characters) through the SQLite store, the replay and the plan's request: the first epoch begins with the first history, exactly one cut follows (turn 20), every other turn repeats the previous turn's request byte for byte up to its words, a long reply stays as stored while its epoch lasts, and the same Talk without epochs misses at the turn its long reply leaves the newest 20.

### Voice on the cache plan (ADR-0009 stage 1, M6)

`SHANNON_CLAUDE_CACHE_PLAN_VOICE` (off by default; `explicit_on`; apart from the text switch so voice can be canaried) gives voice turns of `claude-haiku-5-5` and `claude-sonnet-5-5` the text plan's prefix (`anthropicVoicePlan.ts`):

- Tools: the same fixed pair as text with `tool_choice: auto`; a turn without tools says so after the words; a stray call is declined once as for text.
- System: her identity without the turn's capability lines, then the voice instructions whole and in their order (`VOICE_REPLY_INSTRUCTIONS`, `VOICE_NATURAL_INSTRUCTIONS`, `CLAUDE_VOICE_LINES`). What she knows of the owner reaches a voice turn only when its skills ask for it, so it moves after the words with the capability lines, the skill index and the tool line. No output schema; thinking and effort as configured. Breakpoints as for text (BP1 1h, BP2 1h on the words, BP3 5m on a tool result).
- The owner's words are sent with whitespace runs as one space, as the next turn's history replays them, so the next request repeats this one up to them.
- A turn with a native web search keeps its request without the plan (its server tool is not in the pair; offering it always would let any turn search), counted `voice:web_exception`. A refused first request of a turn without tools is asked again in the shape without the plan (`voice:fallback`).
- Latency: the plan is local work (about 0.02 ms more per turn to build) and adds no request to an ordinary turn (`adr9VoicePlan.test.ts` compares the goldens' request counts with the plan-off ones); only a declined stray call or a refused request adds one, as for text. The voice watchdog, the waiting phrase and the output ceiling are unchanged.
- `GET /v1/ops` `modelCache.foregroundText` has the voice lanes `voice_plan` and `voice_base` (warm turns, history reads, first-token times), counted per Talk apart from text; the voice request carries the Talk only as the receipts' 8-character hash.

The goldens `plan-voice-*`, `plan-sonnet-voice` and `plan-text-rich-blocks` hold the shapes; `plan-voice-talk` is a Talk of three voice turns whose requests repeat each other's prefix up to BP2.

## Cost and budget accounting

The implementation's Haiku prices are USD per million tokens, selected by total input = uncached + cache creation + cache read:

| Total input | Uncached input | Output, including thinking | Five-minute write | One-hour write | Cache read |
| --- | --- | --- | --- | --- | --- |
| At most 100,000 | 0.10 | 0.50 | 0.125 | 0.20 | 0.01 |
| More than 100,000 | 0.50 | 2.50 | 0.625 | 1.00 | 0.05 |

`estimatedAnthropicCostUsd` applies the selected tier to actual uncached, write, read and output counts, plus the existing web-search charge. Valid TTL subtotals must sum to cache creation. The own-time `AutonomyModelUsage` carries those counts through errors as well as successful results; its existing spend table retains total token counts and the resulting cost without a new cache column.

Before an own-time paid action, `paidCall` includes the stable prefix in its conservative input estimate and reserves all estimated input at the one-hour write rate plus the maximum output/thinking cost. Configured own-time prices are treated as base input/output rates with the corresponding cache multipliers and long-context tier. Old Luna price settings resolve to Haiku; an explicit Haiku setting wins if both are supplied. Permission is refused before any RPC when that reservation exceeds the existing cap. A cache hit never waives the budget gate.

On a closed response, charge actual ordinary input, write/read and output. On an incomplete usage receipt or interrupted call, retain the original unknown-action/reservation handling; do not fabricate an acknowledged zero. Background/main usage likewise records known lower-bound spend and a conservative bound when complete native counts are unavailable (since ADR-0009 stage 1, M4 review: the input counts the provider already reported, every write at the one-hour price, plus the whole output ceiling and every allowed search; a full-context one-hour write only when no input count is known or the request carries a server tool, whose results add input later in the same request), so a malformed receipt cannot free budget. The conversation token bound includes the separately acknowledged web-search fee; taking the larger token estimate must not absorb that fee. Historical Luna cost examples in earlier architecture sections are historical estimates, not current Haiku prices.

## Search evidence and structured output

Text search uses the real `web.search` read tool, selected by Jev or discovered through `tool_open`. A separate native Haiku 5.5 operation searches without JSON output format; the pinned primary model receives its result and produces the usual structured answer. Explicit web and place searches retain their existing user intent. The existing native non-JSON voice search stays available.

The [native web tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) always uses citations, and may return a tool error inside HTTP 200. [Structured output compatibility](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) forbids combining citations with JSON output format. Do not infer search success from a provided tool, Jev selection, HTTP success or generated prose. Check native search counts, matching tool/result IDs, result status and actual source URLs; preserve empty, unavailable, not-searched and unknown outcomes.

The auxiliary search has a 30-second maximum within the caller's remaining deadline, at most three searches per request and the existing three pause continuations (at most four requests/twelve searches). The original cancellation remains authoritative. Pause appends the full signed assistant content without mutating system, tools or max_uses. One-hour cache evidence is required and absent search usage retains the maximum search fee. Deterministic search fixtures do not establish a real provider search or a warm-cache hit.

Deep research (2026-10-13, `webResearchTools.ts`, `anthropicWebRead.ts`, `webResearch.ts`). A text reply may call `web.search` up to three times and `web.read` up to two times; one step of a common research task (FCA) six and four (`acknowledgementOwner: 'fca'`). Each call is still one bounded auxiliary operation with its own slot, reserved before the await and left `unknown` if it never ends (an FCA step then holds its segment, never retries). `web.search` takes optional narrowing: up to eight plain `domains` (native `allowed_domains`) or `excludeDomains` (`blocked_domains`, ignored when domains are given), `locality` (`home`: approximate `user_location` from `SHANNON_OWNER_HOME_LOCATION` `lat,lon,label`, the label as city, or prefecture+city like `東京都西東京市`, else `SHANNON_OWNER_HOME_REGION` as region, country JP, the owner's time zone; `japan` while no home is set; `japan`: country only) and `recency` (a hint line after the query; the native tool has no date filter). Without narrowing the request is byte for byte the earlier one. `web.read` fetches one public http(s) URL with the native `web_fetch_20250910` tool (`max_uses` 2, `max_content_tokens` 12,000, citations on, `allowed_callers: ['direct']`), as a separate non-JSON Haiku request through the same transport (route `web_search`, booked usage; web fetch has no per-call fee, its page text is input tokens). Its receipt must agree: `web_fetch_requests`, the call IDs and the `web_fetch_tool_result` blocks; a provider fetch error is a known miss (`empty`), disagreement is `unknown`. Passages are only `cited_text` spans the provider attached to a returned search result URL or a fetched page, at most eight of 300 characters. The streamed server-result cache settlement accepts a request whose only tool is web search or web fetch. Version note: search uses `web_search_20260209` (already used with Haiku 5.5). Fetch uses `web_fetch_20250910`: a live probe on production Haiku 5.5 (2026-10-13) accepted both `web_fetch_20250910` and `web_fetch_20260209`, but 20260209 adds dynamic-filtering code execution blocks and used about 9.4k input tokens against about 2.4k; 20250910 returns `server_tool_use`, `web_fetch_tool_result` and text (thinking blocks may come first), which the receipt agreement accepts as is.

## OFF proofs and verification

Stage2/3 switches control those architecture features, independently of the intentional model/provider migration. Existing OFF byte goldens use an explicit historical GPT provider/model profile; Stage3's test-only pure registry/default/estimate/price policy is pinned to that historical profile while the real loop, gate, store and feature wiring run. Do not regenerate the old digests, alter expected receipts, add a production legacy mode or mock away a feature boundary to make the historical proof pass.

The foreground Observer inventories active top-level and inline tools through a closed name projection; it never includes schema text or signed blocks. For a completed streamed provider request, its `llm` output also contains `firstVisibleOutputAfterMs` when a nonempty decoded reply was accepted by the response callback, and `finalUsageAfterMs` when `finalMessage` supplied final usage. Both measure from that request's SDK stream start, independently for each tool round. JSON syntax, thinking, tool calls and application waiting phrases do not count as model reply text. A withheld web answer or a tool-only round has no first-visible measurement; nonstreamed responses omit both measurements. These are server handoff/final-receipt times, not device display or audio playback, and do not separate provider queue, prefill or thinking time. Existing complete/incomplete usage and no-retry rules remain unchanged.
