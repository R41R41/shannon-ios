互換性と運用リスク

通常会話の遅延

organize解析を既存/v1/chatのモデル出力へ常時追加すると、全会話のschemaとtokenを膨らませる。明示時だけ別model/workerを使う。

message IDの不一致

serverはmessage IDを保存するが、送信直後のSwiftモデルは新しいローカルUUIDを作る。provenanceとjumpの前にserver IDを返して保持する。

部分成功とcursor

cursorを早く進めると失敗itemが消え、遅く進めると再提案が重複する。失敗は元sessionから再送し、次回解析へ混ぜない規則が必要。

二重承認

reviewの「採用」と最終「反映」を混同しない。採用はsession内状態、外部writeは反映操作の一度だけ。

複数端末競合

iPhoneとMacが同じsessionを編集できるため、decisionにはexpectedSessionRevisionを要求し409で再読込する。

外部正本の変化

提案後に文書／タスクが変わる。expectedRevision競合では直接修復せず、再取得してユーザーへ再判断を返す。

秘密と過剰ログ

destination credential、会話全文、文書本文をattempt logへ残さない。provenanceはmessage IDと短い理由だけ。

既存UIとの衝突

Mac右inspectorは作業現在地に利用中。整理レビューを開いた時だけmodeを切替え、同時に2種類を重ねない。

契約案で確定前に直す点

  1. schemaにOrganizeSessionと確認カードがない。現JSONはdestination command/resultのみ。Shannon内部契約を別schemaとして定義する。
  2. Voyager createのthinkingが必須ではない。statusが省略できるため、schemaで必須化するかadapterが強制注入する。
  3. workSessionとOrganizeSessionの呼称が曖昧。ReferenceへorganizeSessionを足すか、両者を同一概念と明記する。
  4. Aether appendとupdate全文が非互換。更新adapterは新endpoint完成まで無効にする。
  5. 共通resultのpendingReviewはAether寄り。Voyagerの即時appliedとdestination別resultをどう表すかfixtureで確定する。
  6. 1MB本文と現在の64KB client request上限が不釣り合い。本文はserver内保持、client decisionはIDだけにするか、MVP上限を縮める。
  7. session全体のapply receiptが未定義。一件ごとのcommand resultとは別に、Shannon所有の件数／失敗／再試行状態が必要。

必要fixture

trigger / range

  • 単独「整理して」は起動
  • 「要点を整理して」は通常chat
  • 引用内の「整理して」は非起動
  • 初回は先頭、2回目はcursor以降
  • trigger message自身は抽出対象外

cards / review

  • single 2〜8、multi 2〜12
  • other自由入力
  • 編集後の再validation
  • reject理由は任意
  • deferは外部writeゼロ
  • once approvalのみ

delivery

  • 同key同bodyはduplicate
  • 同key別bodyは409
  • Aether revision conflict
  • Voyager whole-task atomicity
  • completed暗黙再開拒否
  • partial retryは失敗itemだけ

durability

  • API/worker再起動後に復元
  • background/foreground復帰
  • iPhone/Mac同時編集409
  • 古い解析結果のCAS拒否
  • session中のsource保持

navigation

  • 日本語・全半角・大小文字検索
  • title/section/summary順位
  • 未ロードmessageへjump
  • 削除／archive済みanchor
  • summary failureでもchat継続

privacy / bounds

  • 会話全文をdestination logへ出さない
  • 最大item/message/content件数
  • workspace owner分離
  • 未知field拒否
  • 秘密値をreceiptへ返さない

実装に進む場合の段階計画

  1. Decision gate：上の10項目と正常／競合／重複fixtureをユーザー確認。共通schemaを修正してfreeze。
  2. Identity foundation：server message IDのclient保持、anchor range API、加法DB migrationを実装。
  3. Shannon-only vertical slice：durable OrganizeSession、exact trigger、fake model、fake adapters、review UI。外部書込ゼロ。
  4. Model extraction：strict structured outputを明示時だけ実行。cost-bearing live evalは別承認・記録。
  5. Destination adapters：freeze済みfixtureに対してAether/Voyager接続。資格情報はserverだけ。
  6. End-to-end apply：partial success、retry、restart、複数端末競合を合成環境で検証。
  7. Thread navigation：section、rolling summary、jump、server searchの順に追加。
  8. 配布判断：API/iOS/Macの検証後、Azure/TestFlightは別の明示依頼で実施。

この順番で守る境界：destination endpointが未完成でもShannon UIをfake adapterで検証できる。逆に、共通契約が未確定のまま他repoへ先に型やendpointを作ると、3アプリ同時の作り直しになる。

今回の結論

次の作業は「契約確認用の視覚プロトタイプ＋fixture確定」が最小で価値の高い一歩。

方針の中心は採用してよい。Shannonは司令役、Aether/Voyagerは正本、ユーザーは最終判断者のままにする。一方、現在のschema案をそのまま実装せず、上記の7つの契約穴と10の未決事項を先に閉じる。合意後はShannon-only vertical sliceから始めれば、Mac M1/M2成果や現行会話を崩さず進められる。
