Shannon · quality programme · v24 · 2026-09-06

使いやすさを、
機能と同じ深さで仕上げる。

Shannonは「機能を増やす段階」から「毎日気持ちよく使える段階」へ移る。Build 30を基準に、画面の全状態をライト／ダークで撮影し、AetherとVoyagerから操作の良い部分だけを学びながら、1枚ずつ改善する。

Build 30 実機確認済み次: 音声SmokeUX監査を先行設計Live2D / Widget は後続
01 / decision

正本を固定してから、磨く

製品・配布の正本は shannon-ios。

work/shannon-v1 は旧来の研究用作業ツリーとして隔離する。そこから何かを採用する時は、対象を小さく読み取り、Shannonの現在の設計・権限・予算・テストに合わせて移植する。旧ツリーから直接ビルド、Azure反映、TestFlight配信はしない。

完了

Build 30の安定した出発点

新しいprimary AppIcon、会話・接続の維持、複数トーク、記憶、作業タスク、背景の関心と自発性、配信自動化まで実機で確認済み。

最優先

音声の実機完了判定

iOS 26の音声経路は録音tapと認識処理を分離済み。Build 30で「開始 → 話す → 確定 → 送信 → 返答・読み上げ → 停止」を確認して、過去のクラッシュ対応を閉じる。

02 / sequence

実装の順番

0. 正本の固定shannon-iosだけを製品変更・配布対象にする。完了。
→
1. 音声SmokeBuild 30で半二重会話の開始、確定、送信、読み上げ、停止を実機確認。
→
2. 撮影fixture個人会話を使わない固定データで、画面状態を安全に再現可能にする。
→
3. 画面監査ライト／ダーク・長文・空・失敗・キーボードなどを1枚ずつ評価。
→
4. 小さく改修発見した摩擦を優先順位順に直し、同じ画面を再撮影して差分確認。
このフェーズでは新しい大機能を混ぜない。 新しい情報源、Live2D、Widget、全二重音声は、基本操作の摩擦を消してから扱う。改善の原因と効果を見失わないための境界。
03 / screenshot matrix

画面を「状態」まで含めて撮る

最低48枚のコア画面を、同一の非個人fixtureと端末条件で撮影する。画像・会話・トークン・認証情報はサンプルに置き換え、共有しても安全な状態だけを残す。

画面必須状態表示条件見ること
トーク／スクロール通常、長文、送信中・失敗、キーボード表示ライト・ダーク × 4本文幅、情報密度、コピー、入力欄と最終返信の重なり
対話モード待機、考え中、短文、長文＋キーボードライト・ダーク × 4シャノンの存在感、吹き出し、視線、余白、対話への集中
トーク一覧空、複数、選択中、タイトル編集ライト・ダーク × 4新規作成、最終時刻、選択状態、編集と戻る導線
メモリーいま、知識、日記、空・更新失敗ライト・ダーク × 4「頭の中」として読めるか、根拠・編集・戻り道
作業タスクなし、進行中、許可待ち、完了・失敗ライト・ダーク × 4重要度、行動の分かりやすさ、通常会話を邪魔しないこと
設定通常、App Update、Voice Diagnostics、接続不調ライト・ダーク × 4情報の優先順位、異常の伝え方、戻りやすさ
追加アクセシビリティ撮影

大きな文字、Reduce Motion、VoiceOverの主要導線、横向き不要の崩れ確認。コア48枚と別に代表状態を撮る。

通信・データ保護の撮影

オフライン、遅い応答、再試行、復元中をfixtureで再現。実ユーザー会話や本番のタスク本文は使わない。

04 / review lens

1枚ごとの判定基準

① いま何ができるかが3秒で分かる
② 最も大切な内容に目が最初に行く
③ 操作できる要素が操作できる見た目をしている
④ 余白は静けさになり、情報不足にならない
⑤ ライト／ダーク双方で読みやすく、表情が沈まない
⑥ 直前の行動と次の行動が自然につながる
Aetherから学ぶ

文章と入力の居心地

透明感のある入力領域、情報を急かさない読み順、階層を増やしすぎないナビゲーションを参照する。ただしAetherの文書中心UIを会話にそのまま複製しない。

Voyagerから学ぶ

作業状態の明快さ

実行中・待機・完了・失敗の区別、次の行動を1つに絞る表現、長い作業を迷子にしない要約を参照する。ただしタスク管理画面の密度を通常会話に持ち込まない。

05 / delivery rhythm

監査から改善までの一巡

観察

スクリーンショットに注釈

各画面に「問題」「なぜ気になるか」「仮説」「優先度」を付ける。主観だけでなく、操作の失敗や視線移動も記録する。

選別

1ビルドは1つの体験単位

例: 入力体験、対話モード、メモリー階層。無関係な機能を同じ変更へ混ぜず、効果を実機で比較できるようにする。

検証

同じ状態を再撮影

変更前後を同条件で比較し、会話履歴・接続・記憶・タスク表示の回帰をチェックしてからTestFlightへ進む。

実際にあなたの操作・端末接続・TestFlight更新が必要になる時は、その都度「目的、具体的な手順、成功時の見え方、失敗時の復帰」を書いた専用HTMLガイドを先に作る。
