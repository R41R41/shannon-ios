# Minecraft 後半（ネザー奥〜エンドラ）の頭の入力と通しの自律（2026-11-02、S3）

- 決定: ライ氏 2026-11-02「11/10 の撮影までに、シャノンがエンドラを討伐できる状態に」。作戦書は Syzygy `notes/minebot-dragon-sprint-2026-11-02.md`。担当は頭（この文書）、体の S1（エンド）・S2（ネザー奥・パール・要塞探し）。
- 土台: 頭 `claude/dragon-head`（2bd7788 ＋ Codex の計画の target・現在の能力・目的別の進み・待ちの期限）。切り替えは**無い**（環境変数のスイッチを付けない）。
- 方針: 判断は LLM、入力は事実を分かりやすく。コードで強制しない（強制は、観測と食い違う「済み」を通さない検査と、立て直しの回数の上限だけ）。
- 「分かっている」は実装と単体テストで確かめたこと。実機・実走で確かめたことは**まだ無い**（下の「未確認」）。

## 1. 頭が体の frame から読む欄（契約の受け口）

欄が無い・形が違う時は黙って読み捨てる（その行を出さないだけ）。体の欄名・単位を変える時は、先に S3 と S0 に知らせる（頭の契約と produced の同期の順番を合わせるため）。

| 欄（`observation.state.world`） | 形 | 頭の使い方 |
|---|---|---|
| `dragon`（エンドだけ） | `{ id, health 0〜200, phase 0〜10 か名前, position, headPosition?, distance }` | live の「竜:」行。phase の番号は Mojang の順（0 周回 1 狙い 2 着陸接近 3 着陸中 4 離陸 5 止まり・息 6 止まり・見回し 7 止まり・攻撃 8 体当たり 9 死に際 10 ホバリング）。5〜7 を「頭が剣の届く高さ・矢は効かない」と言う。旧形式（`mapLandmarks` の `! エンダードラゴン … id N 体力 H/200`）も読む |
| `crystals` | `{ remaining, caged, list:[{ id, position, caged, distance }] }` | 「エンドクリスタル:」行（近い順 3 個）と、済む条件 `crystals<=n`。旧形式は「見えている n 個」とだけ言い、島全体の残りは言わない |
| `perch` | `{x,y,z}` | 「止まり木:」行（旧: `X 止まり木` の印） |
| `dragonBreath` | `[{ x, z, radius }]` | 「竜の息の雲:」行（近い順 3 か所） |
| `lastDeath`・`deaths` | 体が今出している行と記録 | 「最後の死:」行。死んだ次元が今と違えば「行くにはポータルを通る」と足す |
| `rememberedPlaces` | 体の記憶の 1 種 1 行 | 「控え（体の記憶、今いる次元）:」行（ポータル・要塞・ストロングホールド・枠・リスポーン地点）。ネザーの先に着いた後だけ |
| `mapLandmarks`・`inside` | 体の印の行 | 済む条件 `see:fortress`（`N ネザー要塞`・`inside` の「ネザー要塞」）、`see:end_portal_frame`（`Q エンドポータルの枠 … ×12 アイ入り k`）、`see:end_portal`（`e エンドポータル`）、`see:stronghold` ほか。別の次元の行（`[overworld] …`）は読まない |
| 結果 `ActResult.eye` | `{ from, bearingDeg 北0・東90, flew, to, broke, down? }` | 目玉の帳簿（下）。`down`（ほぼ真下へ沈んだ）は任意 |

## 2. 済む条件の足し（`minecraftPlanDone.ts`）

- `see:<fortress|bastion|spawner|blaze_spawner|nether_portal|end_portal_frame|end_portal|stronghold|village>`: その印が今の frame に見えている。場所の条件なので、子が開いている親は閉じない。
- `crystals<=n`: 体が数えたエンドクリスタルの残りが n 以下。体が数えていない時は「未」（不明を済みにしない）。
- ロッド・パールの数え方（`acquired`）: `have:blaze_rod>=7` は「持っている棒 ＋ 粉・目玉になった棒」、`have:ender_pearl>=12` は「持っているパール ＋ 目玉になった分」で数える（早く粉にしても節が閉じなくならない）。`target` の検査・不足の言い方・進みの証拠も同じ数え方。
- 竜の討伐は節の条件では閉じない（体の `boss.verified`、既存の goal binding）。

## 3. 計画の後半（`minecraftFirstPlan.ts` の BEYOND）

出発の点検（ネザーの奥）→ ネザー要塞（`see:fortress`）→ ブレイズロッド7（`target`、`have:blaze_rod>=7`）→ エンダーパール12（`target`）→ エンダーアイ12（`target`）→ オーバーワールドへ戻る（`dim:overworld`）→ 出発の点検（エンド）→ ストロングホールド（枠の部屋 `see:end_portal_frame`、ポータルが開く `see:end_portal`）→ エンドに入る（`dim:the_end`）→ エンドでドラゴン（クリスタル `crystals<=0`、止まり木で剣）。最初の計画（Opus）にも同じ書き方を `minecraftCurrentPlanPrompt.ts`・`minecraftStrategy.ts` で伝える。

## 4. 段の知識（`minecraftLlmcV2Knowledge.ts`）

`stronghold` 段を足した（目玉の投げ方と交点、原点から 1,280〜2,816m の輪、下り方、枠の部屋、要塞でのリスポーン地点、入り方）。ネザーに死んだ時・ガスト、ブレイズの待ち打ち（湧き 10〜40 秒・棒 0.5 本/体・浮いた相手は追わない）、パールの当て 3 つとエンダーマンの屋根の穴（外の先例・この体では未確認と書いた）、エンドの順番（クリスタルを弓 13〜64m → 檻つきは登る → 止まり木で頭を剣 → 息を避ける → 縁に近づかない）と死んだ時の戻り方を書いた。体の S1・S2 が作る手の名前・引数が決まったら、同じ言葉に合わせる（今は既存の `attack`・`shoot`・`use`・`pillarUp`・`drop`・`pickup` の語）。

いつもの system 文（8,800 トークンの上限）は増やしていない（節目の長い一覧は meter だけに出す）。

## 5. live の事実と目玉の帳簿

- 行は `facts` に入る（通常版は全部、急ぎ・短縮版は竜・クリスタル・枠・最後の死だけ）。ネザーの先（竜の依頼で、ネザー以外の次元にいる、または棒・粉・パール・目玉を持つ）に出る。竜の依頼でなければ出さない。
- 目玉の帳簿（`minecraftEyeLedger.ts`）: 行動結果の `eye` を 1 回ずつ記録（オーバーワールドだけ、新しい 8 個、45 分・4,000 マス内）。task の checkpoint（`minecraftEyes`）に入るので、要約・再起動で消えない。
- 交点（`minecraftEyeTriangulation.ts`、純粋関数）: 前向きだけ（投げた先の後ろで交わる線は使わない）、交わる角度 8° 未満は出さない、誤差の見積り（飛んだ距離が短いほど方位が悪い・遠いほど大きい）が 300m を超えたら出さない。3 本以上は重み付き最小二乗で、合わない 1 本は外す。出す時は「計算上の見積り ±Nm・k 本が一致」と原点からの距離を言う。出ない時は最後の線の横 100/200/400m の投げ位置の案。交点に近づいたら、交点の手前（誤差と同じだけ）から投げ直す案。**実測の方位の精度は未確認**で、誤差の仮定（位置の誤差 0.2 マス、方位の下限 0.5°）は S2 の結果で見直す。

## 6. ペースの目安（`minecraftLlmcRoad.ts`）

ネザーの後ろに、要塞 2,700・ロッド7 4,500・パール12 7,800・アイ12 8,100・枠の部屋 10,800・エンド 11,200 秒（先例のネザー 55 分→討伐 3:56 の各区間を、持ち主の 30 分に足した。ものさしで、手は決めない。最初の数走で見直す）。討伐は 12,700 秒前後を想定。

## 7. 無人の通し（止まりの常時検出と立て直し）

保留しない依頼（`--hold-on-failure` でない依頼）でも、止まり（節が進まない・同じ所で止まる・待ちの繰り返し・死）を毎判断の前と結果の後に見る（`minecraftLlmcWatch.ts`。目的別の進みは Codex の C のまま、竜との戦いは「与えたダメージ・壊したクリスタル」も進みに数える）。止まりを見つけたら、次の判断の前に強いモデル（Opus、最初の計画と同じ）へ**履歴なしの短い brief**（8k トークン以内）を送り、`plan.update` の ops（add・split・set・move・drop・forbid・caution・lift、12 個まで）と今の節と一行の理由を受け取る（`minecraftLlmcReplan*.ts`）。ops は今の計画と観測に照らして検査し（目標と条件の不一致・準備の節・観測が満たしていない「済み」は通さない）、計画の次の読みで取り込む。

- 上限（走っている時間の時計で）: 最短 10 分おき・1 時間に 6 回・1 実走 30 回・1 つの節に 3 回。数える回数は、頼んだ時点で増やす（答えが来なくても）。
- 節に 3 回立て直しても進まない時は、判断に事実を 1 度言う（「続けるか、blocked にして別の道を計画するかを決める」）。頭は節を止めない。
- 強いモデルが「止まりに見えて進行中の待ち」と見たら ops を空にする（直さない）。
- 保留は、結果が不明で解放を確かめられない時と、体と頭の操作権が食い違う時だけ（従来どおり）。止めて直す診断の実走（`--hold-on-failure`）は今のまま。
- 費用: Opus 5.5 は入力 $4・出力 $20 / 百万トークン。1 回は入力 約 9k・出力 約 2k なので約 $0.08〜0.15（キャッシュの書き込み込みで上限は約 $0.15）。30 回で約 $2.5〜4.5。
