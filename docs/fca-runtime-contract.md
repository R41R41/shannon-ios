# Common FCA runtime — tasks, shared context, voice and bodies

Status: implemented on `codex/shannon/common-fca-runtime`, opt-in, not deployed. Design source: Syzygy `docs/architecture/shannon-fca-loop.md`.

## What runs

`configuredServerFca` attaches a durable Task Hub and one-step FCA runner to the existing API. Since Syzygy ADR-0009 S9 it is always on (`SHANNON_FCA_RUNTIME` is retired): the API refuses to start without Stage4 (`FCA_ACTION_THREADS_REQUIRED: … set SHANNON_ADR8_STAGE4=on`) or without a key for the task model (`FCA_PROVIDER_REQUIRED: … set <names>`; Haiku, the default, takes `SHANNON_HAIKU_API_KEY`, `SHANNON_ANTHROPIC_API_KEY` or `ANTHROPIC_API_KEY`). Stage4's existing mind worker remains the sole scheduler writer. Owner-alone native text conversations attach a conversation task to their existing foreground respond lease. Their existing model, sentence stream and conversation writer remain authoritative. Correlated owner-alone cascade voice also binds to the existing foreground conversation task. Own-time keeps its existing execution path. Minecraft and avatar touch have separate opt-in body adapters as described below.

There is one ancestor task per scope. The same `runFcaStep` handles every child. Each task has its own goal, completion criteria, inbox and complete native model rounds. The first tool set is `task.create`, `task.list`, `task.get`, `task.send`, registered in the common tool registry and offered by the conversation runner only while a trusted foreground task identity is bound. Admitted owner-request background tasks also use the same configured registry-gated read/write executors and revision-pinned skills, described in [skill import and shared tools](skill-import-and-shared-tools.md). Shared memory keeps its dedicated binding. Own-time authority is not promoted to owner authority. Parent/scope/operation identity comes from execution context, never tool arguments. These tools contact other tasks inside Shannon; they do not send messages to people.

A first-class API at `/v1/fca/tasks` supports GET list (offset) or one task (id), and POST commands `create`, `send`, `stop`, `resume`. It requires a paired principal in the configured owner scope and a fresh owner-alone check. The Minecraft device-token filter executes before this route. Mutation bodies cannot supply scope, parent or audience. Create takes title, goal, completionCriteria and requestId; send takes target id, message and requestId. Calls acknowledge durable admission rather than task completion. Responses expose task projections, never native history, signed thinking blocks or inbox contents. Existing action-thread stop and stop-all also stop the corresponding FCA task or ancestor and descendants, including dormant tasks.

## State, execution rights and recovery

- `agent_tasks` and `agent_task_events` remain canonical. A row's `task_kind` (written in its INSERT; ADR-0009 S8) distinguishes these from Agent Host tasks (`codex`); the additive `fca_*` columns are the runtime's own data. FCA rows never enqueue Host start/steer/interrupt commands, never receive Host results, and never enter Host task-tree migration, offline/busy accounting or command-lease recovery.
- `fca_task_checkpoints`, `fca_task_messages`, `fca_task_history` and `fca_task_segment_receipts` hold subordinate state. The canonical authority and subordinate writes commit on one SQLite transaction. Task phase is derived: ready is queued; executing is running with an active step; waiting is running without a step; a known stop is paused/fca_stopped; unresolved execution is paused/fca_unknown.
- Each bounded segment obtains an existing `agentTask` lease with source `fca:<taskId>:<admissionRevision>` and a hashed per-task resource. Task ancestry is independent of action ancestry. Waiting commits and releases its segment; a dormant parent occupies no inference slot. The existing background limit remains two, leaving the existing foreground slot available. This slice does not add a competing lease manager or redesign concurrency capacity.
- Child creation and its initial context commit atomically; retry identity includes that context even after it has been consumed. Inbox receipt/wake is atomic. Message identity includes source, target and text; a conflicting reuse is refused. A message received during a model call remains available to the next round. A final answer with unconsumed new input cannot prematurely finish the task.
- History, result and the original segment-completion receipt are committed atomically. A lost finish response is recovered by exact lease read-back or acknowledgement reconciliation, never by rerunning the model/tool. No new segment starts while its predecessor has an undelivered receipt.
- A dispatched operation whose outcome was lost stays unknown and cannot auto-resume. A proven not-sent expired lease can safely return to ready. Cancellation is durably receipted only after local model/tool promises unwind; the original-lease outbox then reconciles the worker acknowledgement, including a request lost before it was applied. A task whose admission claim reply was lost can retry only a proven unsent, expired admission.
- Unknown is never replayed, but it does not hold the runtime forever (stabilization 2026-10-12; one unknown exit since Syzygy ADR-0009 stage 1, S5). `UNKNOWN_EXIT_MS` (10 min; for a research or generic work task `UNKNOWN_EXIT_MODEL_ONLY_MS`, 3 min, owner decision 2026-10-13) after a task became `fca_unknown` (compared as parsed instants), a task without a pending receipt leaves by `unknownExit`: every FCA task only calls models, so it is retired (`unknown_retired`): the internal root and a conversation close the unknown step and wait for their next message (a conversation fails its step's sources closed, as after a known failure; a message the lost step may have acted on is not run again, see the inbox rule below); any other task becomes `failed` with `fca_recovered_unknown`, keeps its `unknown_since` as the mark of a result never confirmed, its parent receives the usual result message, and a pending parent stop can finish. An unknown nightly sleep is retired the same way and its bound job closes as `failed`/`fca_unknown_retired` (no separate expiry), so the next pending night is admitted; the stuck night is never re-run. The owner's next turn revives a stopped or unknown root and that thread's conversation at once, and a due nightly sleep revives a stopped root, so stop-all stops the work in flight without disabling conversation or sleep. Every status change is written by the one state machine (S4, `taskStore.ts`); a move it refuses (an unknown task made active, a finished task moved) throws `TASK_TRANSITION_REFUSED` and writes nothing. The tick starts a ready task only while its slot class (`research`, or `sleep`) has room by the slot tables (S6), instead of two tasks at most.
- A task never waits on a message already delivered (fix 2026-10-14; production ab990c87 retired the root's unknown step to waiting while the result of a failed child, received just before that step, was still in its inbox, and only a new message woke a waiting task). Every path that returns a task to waiting on messages wakes it when a visible message is pending (`taskInboxRedelivery.ts`): the unknown exit of the root, the revival of a stopped root, and the tick's sweep (`wakePendingInboxes`, which also wakes a root a release before this fix left waiting; it starts from the scope's running tasks and asks only the inbox index `fca_task_inbox` whether an unconsumed message exists, never reading the message table, which is never pruned). A nightly sleep's closed receipt still never wakes a task by itself. After a failed step of the root, each pending message the step saw (recorded in its `fca_step_started` event) is delivered once more, exactly once (`fca_inbox_redelivered`), when the step never got past its decision request; it is consumed by the failed step, never run again, when it was already delivered once more or when the lost step may have acted on it (its decision answered, a tool or a child started, a message sent from the task after the step began). Two failures of the same message therefore end it: no spin. A provider server error's one retry keeps the step's messages pending for that retry.
- A step held (`FCA_EXECUTION_HELD`, `FCA_HISTORY_HELD`) before it asked for its decision, with no bounded executor started in it (no body skill, reflex or Minecraft lifecycle operation: `stepOutcome` unset), no model call in doubt and no write in flight, is not unknown (Minecraft run 8, 2026-10-14: held right after a compaction, the task was paused and retired). Before its decision a step has run only internal work and model calls whose results it keeps (a committed history summary among them), so it is committed as `continue` with no history and no message consumed (`held_retried` in its log line), at most three times in a row (`fcaHeldRetries`, reset by a normal commit); a lost lease cannot commit and the step stays unknown. Any other hold stays unknown. A held step logs its closed reason (`Shannon FCA execution held task=<id> reason=<owner_not_alone|execution_disallowed|permit_denied>`); a permit whose dispatch or renewal throws asks again, as the heartbeat does, until the lease is at risk.
- A decision the provider definitively refuses (an HTTP 4xx other than 408, 409 and 429, with no paid or tool outcome in doubt) is a known failure, not unknown (fix 2026-10-12): the internal root (fix 2026-10-14) closes the refused step at once (`fca_step_rejected`, its segment receipted) and returns to its inbox under the rule above, so the messages it saw are run once more and a second refusal consumes them; the owner-requested non-root, non-conversation task commits `failed` at once, its parent receives the failure as its result message, and its progress carries a code-authored failure report (status `failed`), which the activity view shows and a call in that thread speaks like a `task.send` report. A task retired from `fca_unknown` gets the same kind of report. Every step that throws logs one line `Shannon FCA step <stopped|failed|unknown> task=<id> code=<closed code>`, and every FCA 4xx is counted and logged content-free like the conversation's (`anthropic_request_rejected`).
- An owner-requested research or generic task that completes without having sent its parent a `task.send` report gets its completion summary as its report (`result:<step>`, fix 2026-10-13), so a call hears a finished result without being asked. Every report also gains a short spoken form (`report.spoken`), written once when the owner's app reads it; a capable client speaks only that form (see [conversation work](conversation-work-contract.md)). Each decision of the FCA model carries the owner's clock (`ownerClock`, `SHANNON_AUTONOMY_TIMEZONE`, default Asia/Tokyo) so relative dates are his days, not UTC's.
- A finished owner-requested research or generic task directly under the root or a conversation leaves its report in the Talk it came from as a report card (owner decision 2026-10-13, written once by the runtime's process, shown only to the owner alone while every source stays visible): see [rich chat](rich-chat-contract.md). Reports are written as Markdown whose form follows the content (tables, ```` ```chart ```` blocks, numbered steps, https images).
- Which report reaches him (`fcaReportGate.ts`, owner decision 2026-10-13): a report said in the voice turn that asked for it (`report.heard`) keeps its report card in the Talk at once (sources and full report on screen, also at night) and is never said or announced again by a call; of the siblings of one request (the same words folded, a contained request only when it is at least 60% of the other, or admitted by the same turn and sharing at least two non-generic topic pieces; never by time alone) one answer is delivered, the first, and a failure is dropped while a sibling answered or still works, or when a later failure of the request exists; a failure older than 60 min, and a result older than that once he has talked about the same thing in that Talk after it finished, are dropped; the card waits out owner-local quiet hours (23–7) unless he talked in that Talk within 10 min, and the card scan looks again by id at work it holds, so newer tasks cannot push it out. The card scan asks the gate first, on the stored progress, and walks the sources (the visibility guard) only for a report the gate delivers: a drop is settled until the task, its stored progress or, for a sibling's drop, the siblings change; a hold is asked again when the quiet hours end or anything is said in its Talk (watched by a read only: no thread is created and the default Talk is not moved, nor by the gate's own read of the Talk); a held report's spoken form is asked for only once it is delivered, and a report the scan first finds deliverable long after it was written (held, dropped until then, or after a restart of the API) waits for its spoken form from then, as a new report does. A gate that cannot read the stored progress delivers nothing. Every task a scan looks at is decided again (a failure included), so none is asked on every scan. The source guard asks the skill reader once per skill and revision in a synchronous job; memory controls and the withholding of each read receipt stay per receipt time. The call's report (the 「いま」 route) applies the drops only.
- A voice turn waits up to 20 s after admitting its research (`voiceResearchTurn.ts`, `FcaConversationTurn.awaitWork`) and says the result in the same turn after her acknowledgement, marking it heard; later results arrive as before. A turn whose research runs on never ends with the out-of-time line. One request is one task: `delegate` reuses a running sibling with the same folded request, and a `web.research` of a turn with no admitted research becomes the turn's research, so a second one reaches it as a message.
- Stops are persisted before cancellation. Descendants cannot start new work. Active tasks remain stopping until the model/tool promises unwind and the existing action owner acknowledges cancellation. Parent completion cannot orphan unfinished children; a completion proposal with unfinished children yields instead. Resume is explicit for known stops; unknown execution needs reconciliation, not a new attempt.

A decision the provider could not answer, and a Minecraft step whose outcome was lost, do not end a run any more: see *Provider errors and lost Minecraft steps* below (2026-10-19).

Initial engineering bounds are depth eight, 64 nonterminal direct children, 256 nonterminal tasks per scope, eight tool calls per decision, and 1 MB of native history per committed segment, with bounded replay and complete-round compaction described below. Five consecutive rounds in which every tool fails pause the task and its children for inspection, preserving the repeated-failure safeguard across segment IDs. These are bounded first-slice limits, not a claim that those values are optimal.

Budget and own-time tasks (Syzygy ADR-0009 stage 2, E3/E4): a research or generic task the owner asked for has its own cap of 300 yen and 40 paid steps (`fca_task_budget`); at the cap the next step is not run, and the task fails with a report the owner's call can say. A Minecraft request the owner made, as admitted (`admittedMinecraftRequest`: bound to the body at creation by `minecraft.request` or the in-game intent, with the admission's completion criteria, directly under the conversation or the root), has a cap of 2000 yen and 300 paid steps instead (owner answer of 2026-10-13, Minebot validation lane). A child it starts and any other task that only touched the body (a body tool call also writes `fca_body_bindings`) keep 300 yen and 40 steps. Own-time tasks (origin `own_time`) are admitted only by the Executive (`SHANNON_EXECUTIVE=on`, `TaskOwnTimeStore`, at most two open): each sits under the root but inherits no source of it and sends it no result; it runs only while her own time is enabled, unpaused and within budget, whoever is present, with public reading tools only (`web.search`, `web.read`) and no task, memory or body tools; each step reserves 30 yen from her day's budget (2000 yen) before it runs and settles the actual yen after (also written to `autonomy_spend`), and stops at 150 yen or 10 steps.

## Provider errors and lost Minecraft steps (Minebot parity audit C-20 and C-21, 2026-10-19)

For an ordinary runner stop after repeated tool/completion failures or a wait without a counterpart, the optional `FcaStepPorts.prepareStop` preserves the owning surface while the current step lease is still live. The Minecraft adapter uses the existing head-take path only for an operator request admitted with hold-on-failure: it asks the body to freeze and capture the scene before committing the last result. The returned `committed()` publishes the operator hold after that result and checkpoint are durable, then the runner stops. A preparation failure is logged and does not discard the last result or prevent the stop. This adds no authority for an expired lease and makes no model call. A body refusal to freeze remains explicit; the operator's run watcher must park an unfrozen stopped run instead of leaving a logged-in body in a moving world.

`createFcaPlanTools.validateUpdate` lets a surface reject a model's proposed plan update atomically, after structural validation and before changing the tree. Minecraft checks newly completed food/descent-preparation nodes against their readable observed conditions: a reason containing "skipped" does not establish completion. Explicit `prep.state: skipped/unmet_now` remains the model's choice and is excluded from reached preparation. Historical completion is not revoked when food is later eaten; free-text conditions and absent observations remain unjudged. The adapter also enforces its existing no-fight-at-health-8-or-less rule independently of a lower requested retreat threshold, while allowing the flee stance. Vital facts report carried rotten flesh as emergency food with its hunger risk, without adding it to ordinary preparation food points.

Owner criterion: better than before, never worse; nothing is replayed unsafely. A body command whose outcome is unknown is **never sent again**; the task looks at the world again and the model decides.

**A decision is asked again inside its step** (`fcaProviderRetry.ts`, `decideWithRetry`, called by `fcaRunner.ts`). An attempt that carried no decision is asked again, visibly: an HTTP 408, 409, 429 or 5xx (529 overloaded included) answer (`FcaProviderError`), a request that got no answer (ECONNRESET, ETIMEDOUT, ECONNREFUSED, DNS and the like) or that ran into the SDK's or this process's 90 s deadline (`FcaNoResponseError`, `anthropicFcaFailure.ts`). Anything else (a refusal, a 400, an answer that does not decode, a stop) passes through at once, as before. The request is the same each time: a failed attempt changes nothing that the next one carries, and only a complete answer adds a history round, so a retry cannot duplicate or leave an empty round (`fcaServerErrorRetryHistory.test.ts`). Policy (`FCA_RETRY_POLICY`): at most 5 attempts, none started later than 120 s after the first began; the wait before attempt *n + 1* is 2 s doubling to 30 s with +-25% jitter, never shorter than the provider's `retry-after` / `retry-after-ms` (up to 60 s; a longer one ends the retries, and the step-level wait below is then never shorter than it); at most three failures that the provider may have charged (a timeout, a reset after the send); and no further attempt once the task's cap has no room for **one more request** (`FcaBudget.room`, `FcaStepPorts.retryAllowed`: what the task has confirmed, this step's bookings, estimates up to their share, and a request as large as the largest this step booked must fit within the cap, equal included). The request is the one built before the first attempt, except that a request asked again when it is 10 s old or older is rebuilt from the body's present observation (the body settles and its revision is read again, as before the first request; `FcaRetryParts.refresh`), so a decision made after a long outage is not discarded as stale (M-6). What the request carries anew is the body's and the observations' context, the progress and (a transient task) the live state; the revisions the decision is judged against are the new ones. Each further attempt runs the step's own gate again (audience, sources, lease permit), and when the request was rebuilt the whole gate runs once more after the rebuilding, which can wait for a reflex session, so that the last thing before a request is the gate (M-A); a stop ends a wait at once, also one that arrived before the wait began; a stop during a wait is a known stop (the failed attempt carried no decision). The fallback of a transient task to the legacy shape (its first decision refused for the betas) starts from the request in hand, not from the first one, and rebuilds it again, with the gate before and after, if that one is ten seconds old (M-B).

**Accounting.** A provider-answered error (4xx or 5xx) is no decision and no charge: it books nothing (before, a 5xx booked a whole-context upper bound, about a dollar a request, which the retries of one outage would have multiplied into the task's cap). A request the provider may have processed and charged (a timeout, ECONNRESET/ETIMEDOUT after the send, a stop that aborted it) books an unknown upper bound **sized by the request** (its estimated input tokens plus a quarter, written to the one-hour cache, plus the output ceiling), as `usageComplete: false`, in the usage ledger and the task's yen. A request that never left the machine (ECONNREFUSED, ENOTFOUND, EAI_AGAIN, ENETUNREACH, EHOSTUNREACH, connect timeout) books nothing.

**Estimates never end a task by themselves** (`fcaBudgetWiring.ts`, `TaskBudgetStore`, M-4). Such an upper bound is an *estimate*: it is booked in full but apart from the confirmed spend, in the task's own bucket (`fca_task_budget_estimates`, an additive table; the step still counts as a paid step). The cap check counts the confirmed yen plus the not yet reviewed estimates **up to 20% of the cap**; an actual charge that becomes known settles its estimate (`TaskBudgetStore.settleEstimate`; the row stays on record, marked `settled_at` with the `actual_yen`, no longer counts as an estimate, and the actual is added to the confirmed spend; nothing reads a lost request's bill back today, so nothing calls it yet). A charge booked under a key whose estimate was already reviewed or settled is a row of its own (`<key>+<n>`), open, never added onto a reviewed one (L-6). If only the estimates would take a task over its cap, the task is **paused, not failed** (`task_estimates`: stopped with the summary 「…確定していない利用料の見積りを含めると上限…に近づいたので、いったん止めました。再開できます。」), the estimates so far are marked reviewed, and the owner may resume it; from then on the confirmed spend alone decides the cap, as before. A task whose confirmed spend reaches the cap fails as before. Her own day's budget still counts everything that may have been charged.

**When the attempts run out** the step ran nothing: it is closed as `continue` with no history, no message consumed, and the task runs the decision again from a fresh observation after a longer wait (`taskRuntimeUnavailable.ts`; `fcaProviderRetries` in the checkpoint, reset by the next decision that comes back). The wait is the round's cooldown, never shorter than the `retry-after` of the failure that ended the retries (at most 5 minutes; before, a retry-after above a minute ended the round and the next one asked again about twenty seconds later, L-5), and it does not begin for a step that was stopped already (L-1). A Minecraft request goes through 4 such further rounds (waits of about 20, 40, 80 and 120 s, so about a quarter of an hour of an outage in all) and is then **paused as stopped, not failed**: `status paused`, `pause_reason fca_stopped`, the stop reason `fca_provider_unavailable`, and a summary the owner and `task.get` read; the owner may resume it. Any other task keeps one further round and then fails with its report, as before (but no longer sits `unknown` for three minutes after a 429, a reset or a timeout). An unclassified lost answer (`FCA_MODEL_RESPONSE_UNKNOWN` from an error nobody can classify) is still unknown.

**A lost Minecraft step goes on** (`fcaBodyRecovery.ts`, `taskRuntimeUnavailable.ts`, `minecraftOperationReconcile.ts`, `TaskBodyRecoveryStore`). A step of a Minecraft request (bound to a body, origin `owner_request`) whose outcome was lost leaves the task `fca_unknown`: an API restart or a Spot VM stop that expired its lease (its action `sent` from the step's first permit), a body that dropped or never answered a command (`FCA_BODY_OUTCOME_UNKNOWN`), a hold after the body began. Such a task is no longer retired as `outcome_unknown_closed` at the unknown exit: `retireUnknown` leaves it alone (`TaskRuntimeOptions.holdUnknown`) and a background pass (every 2 s) closes the lost step:
1. The step's body operations are read (`fca_body_operations` of its lease). If every one has its own settled receipt with the inputs released, or the step sent nothing, there is nothing to prove.
2. Otherwise the body is asked to release (`minecraftBodyRecheckWiring.ts` `releaseStep`, the same `recheck:<sha256>` command and proof as the re-check, at once, not after the unknown exit, with a backoff of 10 s doubling to 5 min, at most 10 times per lost step, M-2; the count is kept in `fca_body_release_attempts`, an additive table, so a restart does not begin it again, L-11; an answer of `recheck_busy` or `body_unavailable` wrote no row and is not counted). Only the body's own `stopped` receipt with every input released (`fcaReleaseEvidence`) counts. Without it the task waits (`unknown`), whatever time passes. After the tenth release the body did not confirm, the task is **paused** (`fca_body_paused`, reason `fca_body_release_unproven`, summary 「体が前回の操作の解放を確認できなかったため一時停止しています…」) and the body is asked no more: each ask writes one `recheck:` row, so a 10 s cooldown without end would have written about 8,640 rows a day per lost step. The lost step's action is **never closed without the proof**. A task the owner resumed meanwhile is stopped in the same way, and the owner's next resume begins a new count. The count and the "exhausted" mark are let go only once the pause or the stop has taken: a stop that fails is tried again at the next pass and does not start another round of ten asks (L-1).
3. With the proof, the operations nobody answered are closed as `cancelled`, inputs released, `reconciled: "release_proof"`, naming the proof's command (`reconcileOperations`): they are **never delivered again** (the row is settled; a later real receipt of the same connection replaces the closing when it is known, `MinecraftControlStore.settle`). The lost step's action is closed with `action.reconcile(lease, 'failed', 'fca_body_reconciled')`, which frees its slot, its task resource and the retained body.
4. A notice goes into the task's inbox once (`recovery:<action id>`): `{"kind":"body.recovery","gapSeconds":<n>,"lostOperations":[{"tool":"mc.<skill>","outcome":"no_receipt"|"cancelled"|...}],"existingChildren":[...],"sentNotes":[...],"instruction":...}`: how long ago the step was lost, the names of what the step sent the body and how each stood (never the arguments), the child tasks it may have made and the notes it may have sent, and the instruction that none of the operations was sent again and nothing may be assumed. The notice is **stored and verified in the inbox before the lost step's action is closed and before the task goes on** (sending is idempotent by that id): if it cannot be stored the step stays open, the task stays unknown, and the next pass tries again, so the model never resumes without having been told (M-1).
5. When the body is connected again (its frame is current), the task returns to the queue (`fca_body_recovered`, with the body's proof as the S4 `proof`), and its next step is admitted like any other: the budget cap (`before`), the owner-alone check, the leases and the slots all apply, the observation is the body's current one, and the model decides.

**The guarantees of this recovery cover body operations only.** A lost step may also have made a child task (`task.create`) or sent a note (`task.send`); those are neither undone nor closed. The notice lists the children made and the notes sent at or after the lost step began (the newest eight of each, titles and previews cut) so that the model does not make or send them twice (M-5).

Bounds: the body has `SHANNON_FCA_BODY_RETURN_MINUTES` (default 30, 1 to 720) from the moment the task became unknown, and the age of the request is measured from **when its step was lost** (the end of the action's lease while it is on record, else the latest sign of life the step left: its task's newest `fca_progress_observed` event or its newest body operation of the lease, made or answered, never later than the sweep of the action, else the step's `fca_step_started`; L-2: a long step is not dated from its start), not from when this process noticed, so a VM stopped for eight hours does not make yesterday's request young: a step already older than the window when it is noticed pauses the task at once as `stale` (`fca_body_paused`, summary 「前回の操作から時間がたちすぎているため一時停止しています…」), and the notice carries the `gapSeconds` when the owner resumes it (M-3). After the window the task is **paused as stopped, not failed** (`fca_body_paused`, summary 「体が戻らなかったため一時停止しています」), and a task recovered 6 times within an hour is paused the same way (`recovery_limit`). A paused task that has a lost step is not admitted when the owner resumes it until the step is closed (the recovery pass goes on for it), so a resume never starts a step beside an unproven body; while it waits, its summary says so (「前回の操作の結果を体がまだ確認できていないため、確認できるまで開始を待っています」, once, `fca_note`; L-7), and it is cleared when the proof came and the task starts (L-4). The same window holds for it, counted from the owner's resume (`fca_resumed`): a resumed task whose body does not return is stopped again as `body_not_returned` (L-3).

**A paused task does not keep the body held** (M-C). A task paused here (or stopped by the owner with no step running) keeps its lost step's action open, so the body stays retained and no new Minecraft request could take it. The recovery therefore goes on asking the body for the release proof while the task is paused, with no model step and no resume: slower than while it runs (a minute doubling to 30 minutes) and at most 20 times in all per lost step (`FCA_PAUSED_RELEASE_ATTEMPTS`, counted across restarts). When the proof comes, the step's unanswered operations are closed as above and its action is closed (`fca_body_reconciled`, log `held=paused`), which frees the body; the task stays paused. A step that sent the body nothing is let go of at once, with no proof and with no body connected. The notice the model is owed is **not** sent then: the task owes it (`fcaOwedNotices` in its checkpoint, written when it was paused), and it is sent when the owner resumes the task, with `gapSeconds` as it is at that time, before its first step, also when the action was closed by someone else meanwhile (L-5); the task is not admitted until it is stored. If the proof never comes (log `for=operator`), the body stays held: the pause summary then ends with 「体は、前回の操作の解放が確認できるまで新しい依頼に使えません。運用者が ops の minecraft release で体に確かめさせることもできます。」, which is removed once the body is free. Another task's failure no longer ends a pass for the rest (`code=pass_failed`). What the recovery keeps per lost step and per task is dropped when the step is closed and the task is no longer waited for (L-8). `fca_task_messages` has an index on `(scope_key, source_task_id)` for the notice's list of sent notes (L-9; the production table held 292 rows when this was checked, read-only). The owner's stop is respected: a task whose stop was requested is not taken back and leaves at its exit as before. A task that is not a Minecraft request keeps the unknown exit exactly as it was.

**A pause tells the owner once, and a resume takes its words away** (fourth round, M-1 and M-2). Every pause the runtime makes by itself leaves the report a failure used to leave, written once (`TaskRuntime.recordPauseNotice`, `TaskProgressStore.pauseNotice`; report id `paused:<key>`, tool `fca.result`, status `paused` (its own status, fifth round: not `failed`), the key being the step for `provider_unavailable` and `task_estimates`, and `<reason>:<revision>` for `fca_body_paused` with `stale`, `body_not_returned`, `fca_body_release_unproven` and `recovery_limit`, also when a resumed task is stopped again): 「<title>」は、<reason>。…再開できます。, the owner's own title and the closed reason, nothing else. The recovery's pause writes it in the same commit as the pause; a write that fails never undoes the pause (nor the stop of a resumed task): the notice is kept pending, one per task, and written at the next tick or pass while the task is still paused (fifth round, L-2, L-3). The notice carries its own spoken sentence (`report.spoken`: 「『<title>』は<reason>ため一時停止しています。再開できます。」, `pausedSpoken`), so no model rewords it and no 「…の結果が届いています」 line is made for it (M-3), and the conversation model sees the progress status `paused` with guidance that it is not a failure. The report gate knows a `paused:` report as its own kind (M-1): it is stale an hour after the notice, not after the task was made; it is not a failure for a sibling's drop (a real failure is not dropped for a sibling's pause); and it is dropped itself only as a failure is (the same request answered or still worked on) or by a later failure or pause of that request. When the owner resumes the task (`resume`), the summary a pause wrote (`pausedSummary`: the provider's, the estimates', and the recovery's own, with or without the operator's hint) are cleared and the report the notice replaced (unread, spoken or heard) is put back as it was (M-2); a pause summary still on a task at the first commit of a running step is cleared there as well. A pause report never stands in for the result: a completion writes its report over a notice that stood in for nothing, and a report that was there before the pause stays the report. `lostFcaSteps` takes the question "is this a body task" before it reads a step's detail, `bodyOperations` finds a task's operations by `task_id` (index `fca_body_operations_task`, made by the recovery's additive schema when the table is there) before it reads the lease's JSON, and the tasks that owe a notice are found by the checkpoint's `fcaOwedNotices` array, not by matching text (L-1, L-2). A pass that finds the task no longer unknown pauses nothing and logs nothing, and a failure for one task stops no other (`code=expire_failed`, L-5). The estimates' words are recognised by a marker and a tail, not by the digits of the cap (L-4), and each index of the recovery's schema is made on its own, so one that cannot be made never turns the release attempts' table off (L-6).

New journal lines (content-free): `Shannon FCA decision retry reason=<http_<status>|no_response|timeout> attempt=<n>/5 waitMs=<ms> task=<id>`; `Shannon FCA decision unavailable reason=<...> attempts=<n> task=<id>`; `Shannon FCA step retried task=<id> code=<closed code>` (a further round, as before, now also for 429 and no answer); `Shannon FCA step paused task=<id> code=<code> reason=provider_unavailable`; `Shannon FCA body recovery task=<id> code=<waiting|reconciled|resumed|paused> ...` with `for=body|for=release`, `action=<id> operations=<n> unresolved=<n>`, or `reason=<body_not_returned|stale|recovery_limit|fca_body_release_unproven>` (`stale` with `gapSeconds=<n>`), `for=notice`; `Shannon FCA decision request refreshed task=<id>`; `Shannon Minecraft body re-check origin=recovery action=<id> code=<...>`. Task events: `fca_body_recovered`, `fca_body_paused`, `fca_note`.

## Model and observation

`anthropicFcaModel` makes one native Anthropic call per decision, with the shared Shannon persona. It returns task tool calls, a wait proposal or a completion proposal. Internal control-call receipts mean only that the decision was received; the runtime owns lifecycle acceptance. Provider-required content/signatures and matching tool results remain intact. There is no nested hidden tool loop.

The existing configured small-model credential policy supplies the key. `SHANNON_FCA_MODEL` can explicitly select a supported native 1h-cache model; the absent value uses the existing Haiku default. This first opt-in endpoint is not yet routed through the native app's primary-model switch. `cacheHaikuRequest` establishes mandatory one-hour caching; actual native usage is recorded to the existing chat usage ledger before cache validation. No read/write cache evidence means no accepted result. Unknown paid outcomes retain a conservative accounting estimate, and SDK retries are disabled. A decision already sent when its step is stopped may finish for up to 20 s (`FCA_MODEL_STOP_GRACE_MILLISECONDS`): its answer is discarded, its actual usage is recorded and the step stops as known; only a request still unanswered after that is aborted and recorded at the unknown upper bound (Minecraft run 10: a cancel aborted a ~73k-token decision, recorded at $1.01, and left the step unknown for three minutes). Deterministic cache tests establish request/receipt behavior; live cache hits and live cost for this new loop have not been measured.

Each segment has a distinct Observer run. Real context/native/LLM/tool/store spans carry task, parent, step, revision and operation correlation; output projection omits prompts, message bodies, native thinking/signatures and tool-result text. Observer remains a projection, not task authority. New task-tree UI/layout changes are outside this slice.

## Conversation, sources and scheduling

Each owner Talk has one conversation task under the single ancestor. The ordinary respond action supplies the lease: there is no second foreground model loop or completion-acknowledgement writer. Task tools preserve the existing session, deadline, streaming, tool receipts and gates. A successful task write suppresses a duplicate legacy Host proposal. A child is admitted durably during the conversation but cannot execute until the ordinary conversation writer commits its source experience, except conversation work (a research child whose context is the turn's `[Conversation work]`: the router's `current_web` and place admission, and `web.research`), which by the owner's decision of 2026-10-13 starts at once and binds its provenance when the turn commits (`TaskSourceStore.runsOnPendingOrigin`); until then the source guard judges its own words like any reply, and the bound turn in full afterwards. A failed source stops its unbound descendants, and conversation work already running on it through its step (a paid read in flight leaves by the unknown exit, never replayed). In one turn a `web.research` call never makes a second task beside the research the router already admitted for the owner's words while it runs: the same request (`sameRequest`) reuses it, and a different or refined question reaches it as a message (`FORWARDED_QUESTION`, once per question). A lost/unknown foreground outcome is held for reconciliation, never replayed.

Only source-visible inbox messages actually rendered for a model turn are consumed. New input arriving during inference stays for the next turn. Sources include conversation/replay/profile identifiers and trusted private-tool read receipts; they contain no copied prompt text. Current owner presence and memory/forgetting controls are checked when a source is reused. Background steps pin their admitted source set so an unrelated newly pending message cannot discard a valid result. Private tasks are not projected through the old Host-task prompt/notices/routes. Canonical task authority is unchanged.

Background admission uses a durable ordinal of successful admissions, not message arrival time or creation order. Continuing tasks rotate fairly; pending segment receipts and unbound source tasks remain excluded. Conversation tasks never enter this background scheduler.

## Tool selection and research

One Jev request asks include/exclude for each allowed tool, using only names/descriptions plus the goal, state and recent results. Uncertain tools should be included. Invalid/missing answers or provider failure fall back to the full allowed catalog. The model always receives the full catalog metadata; only selected definitions are loaded. `tool_open` adds an allowed definition for the next decision without executing it. Selection is reused until relevant input, child state, catalog or a failed tool result changes it. The existing conversation difficulty questions remain separate from this single tool-selection stage.

The server keeps selection mode active even without Jev credentials (full-catalog fallback), so loss of Jev configuration does not switch replay protocols. When a configured Jev selection times out, falls back or answers invalidly, the menu is bounded instead of the whole catalog (Minecraft run 10, 2026-10-14: four such selections put all 139 tools, ~89k characters, in the request and passed the 100k-token price step): the task tools, then the previous selection, then for a body task the body's tools, up to 40,000 characters of definitions (`FCA_FALLBACK_DEFINITION_CHARACTERS`); every other tool stays in the catalog listing for `tool_open`, and the selection is asked again at the next decision. Native selected-tool rounds keep a stable top-level declaration and use the installed provider SDK's inline additions/removals. Existing signed blocks remain intact within a replay epoch. Branch-local stage-1 signed history must enter an explicit public replay epoch before adopting the selected-tool protocol; automatic migration of such in-flight historical experiments is not claimed. Production has not enabled either slice. The public-web executor uses the current tool runner, secret check, model search provider and usage ledger. It does not acknowledge the outer FCA action before its complete native round commits. An unknown search outcome holds the original segment and is never automatically retried.

Deep research (2026-10-13). Research children (`kind: research`) receive `web.search` with its narrowing and `web.read` (one page in full, cited spans), six searches and four page reads per step. Their task context asks for an answer-first Markdown report (`researchReport.ts`: `## 結論`, `## わかったこと` with a source link and short quoted span per finding, `## 未確認・注意`), at most 2,000 characters, which is what `task.send` and the completion summary carry into `report.text`; the spoken form stays `report.spoken`. In a call bound to a conversation task the voice model is offered `web.research` (domain `task_runtime`, voice only): it admits the same conversation-work research child the router admits for `current_web`, answers at once that the work was admitted (never a result), and the report is told when it arrives.

## Bounded working history

The history store retains append-only original complete rounds. Replay compaction selects an exact contiguous prefix by server-assigned round IDs, keeps recent whole rounds, and includes the actually committed lifecycle outcome. The summarizer receives public content, never thinking or signatures. Its native request follows the same one-hour cache, usage-before-validation, abort and no-retry policy as the decision model.

A summary installation checks the live lease, source visibility, summary revision, exact coverage and history tail. It starts an explicit new replay epoch: structured summary plus complete public recent-round transcript form one stable bootstrap message; old signed blocks stay in storage and are not reused under a changed prefix. New native rounds append unchanged to that bootstrap. The bootstrap and reset boundary survive restart. Current defaults are 64,000 native replay characters, 24 rounds, six recent rounds, 32,000 summary-input characters and eight compaction batches. The native budget measures a decision message without the parts each decision restates (`FcaHistoryCodec.measured`: catalog, recall, skill index, fixed instruction texts); the whole replay's bounds still count them. A compaction keeps at most six recent rounds whole in its bootstrap and fewer while they would pass a third of the native budget, down to the newest one, and summarizes the rest; while a compaction installed this step leaves a bootstrap above that third, another batch follows (never the last allowed batch). Minebot lane task 788da00a (2026-10-14, production ab990c87) compacted on every step: each stored round passed the budget by itself and the newest one went back into a 15–28k bootstrap; a summary now leaves room for several native rounds (`fcaTaskHistory.test.ts`: a summary every third step instead of every step). The codec's conservative token estimate of the whole replay (`FcaHistoryCodec.tokens`, `estimatedAnthropicTokens`: 1.1 a non-ASCII character, one per 2.2 others, over the JSON) is bounded at 75,000 (`maximumReplayTokens`), leaving about 25,000 for the instructions, the current decision and new definitions below Haiku's 100k-token price step (Minebot lane runs 1 and 3 sent second decisions of 102,796 and 109,442 tokens from replays well inside 200,000 characters). Each request logs `estimatedInputTokens` in `fca_request_size`, and one above 100,000 also logs `fca_request_price_step`; it is still sent. Inline tool additions/removals (`FcaHistoryCodec.reproducible`) are replayed byte for byte but measured against their own bound of 160,000 characters, not the 64,000, and the two together against 200,000 (review P3-1: about the 100k-token price step); each FCA request logs its sizes content-free as `fca_request_size` (`historyCharacters` is the whole replay with its inline definitions, `nativeHistoryCharacters` the part the 64,000 measures; Minebot lane run 1 logged 134,185 of which 81,625 were definitions, 52,560 native): they restate catalog definitions, sit in the cached prefix, and a new epoch re-adds whatever it lacks (Minebot lane 2026-10-14: 77 mc.* definitions were 46,652 characters of a first round, and every Minecraft task failed its second step with `FCA_HISTORY_RECENT_LIMIT`). A newest round too long by itself, with nothing older to summarize, is replayed for its next step as a fresh public epoch (`clippedReplay`): the existing summary and that round's public transcript, every message kept in order with its call id, the longest texts cut with the marker 「…（長いため後略: N字）」 (nothing offers the cut text back to the model). No signed block enters that changed prefix, nothing is stored, the stored round stays whole, and the replay is identical while the round stays the newest; the next step's ordinary compaction covers it. The goal and completion criteria are never in the clipped part: each decision states them again in its own message. Only a round that cannot fit even with every text at 400 characters still holds with `FCA_HISTORY_RECENT_LIMIT`. The summarizer's answer is read by the shared compaction rule (`checkedTemplate`): a template given as a JSON string or an object, items cut to 80 characters, the newest five kept, other keys dropped, a section it leaves out kept from the previous summary; each adjusted answer logs its shape content-free as `fca_summary_shape`. Only an answer with no usable summary (not one `fca_history_summary` call, no JSON object, or no item at all) is `FCA_SUMMARY_INVALID` (Minebot lane run 2, 2026-10-14, task 94e879f8: an exact shape check refused Haiku's complete answer and left the step unknown). Such an answer, or a finished summary response the decision checks refuse (truncated, refused, no call), never leaves the step unknown: that step replays a fresh public epoch of the existing summary and every uncovered round (`fallbackFcaHistory`), longest texts cut with the same marker and, only when even that cannot fit, the oldest rounds left out and counted (`omittedRounds`); its work is about linear (each round's shortest share measured once, then one common cut length found by halving: review of 8da89bc7, where re-clipping for each left-out round took 56 s for 40 rounds on the event loop); nothing is stored, and the next step's compaction asks for a summary again (one summary call per batch, no hidden retry). It logs `Shannon FCA history summary unusable` with the closed code. In the summary input and in any public epoch, a decision message is projected without the parts each decision restates (`catalog`, `recall`, `skillIndex`, fixed instruction texts), named in `restatedEachDecision`; the stored native message is unchanged.

## Shared emotion, prediction and memory (stage 3)

Each common FCA decision receives a versioned reading of the existing companion emotion, current feeling and source-visible recent causes/outcomes. There is one emotional state across tasks. `AffectCoordinator` uses the existing companion writer; `fca_affect_receipts` only deduplicates evidence by event ID and appraisal revision. Parent and child references to one event do not count twice; a changed appraisal applies its difference. Existing emotion transitions and decay remain authoritative. Emotion informs expression, caution and exploration, never facts or authority. Existing text/voice prompts read this same companion state; their established emotion-input path stays in place.

Provider request rules (live 400s, 2026-10-12, before any FCA decision had succeeded in production): a system message holding inline tool changes may not open the conversation, and (live 400, 2026-10-14, Minebot lane run 3: task a5ad9996 after its first compaction and the root fd99df55 from a clipped epoch, both [public bootstrap, definitions, decision]) it must immediately follow a user turn and be the last message or be followed by an assistant turn, never sit between two user messages; so every decision sends its current decision message first and any inline definitions after it, ending the request (the history keeps that order; a new public epoch is [bootstrap, decision, definitions], and a definition opened mid-task follows the next decision); strict schemas reject numeric, length and item-count keywords, so `fca_context` states its bounds in words and the decoder enforces them; and strict catalog tools broke the per-request strict limits (more than 20 tools, more than 24 optional parameters, and inside those counts "the compiled grammar is too large"), so only the fixed control schemas (`tool_open`, `fca_wait`, `fca_complete`, `fca_context`) are strict and catalog tools are offered non-strict, validated by their original executors. `tests/support/anthropicProviderRules.ts` answers a violating request with the same 400 (it also checks system-message placement and tool_use/tool_result pairing).

The native decision may include an optional inline `fca_context` block alongside actions or control decisions. It can declare a concrete pre-action observation, expected value and deadline, or appraise an already observed event. No extra model is required after each action. The server writes the expectation before dispatch and compares actual result fields/text deterministically; transport success is not the predicted fact. Missing evidence remains pending and then unobserved, not failure. Mismatch is not proof of causation. Free-text descriptions stay in FCA working/evidence records, not the closed numerical prediction ledger. The top-level native prefix and selected-tool replay protocol remain stable.

Evidence is fenced by the original live step/lease and becomes shared only after its exact canonical round commits. The committed lifecycle status, not a requested completion or `ok` receipt, decides whether a task actually finished. Evidence delivery uses durable retry receipts and never reruns the original action. Causes inherit both the original event's sources and the evaluating task's sources; another task pins that lineage before receiving it.

Recall starts from the goal, context and recent results alongside history preparation and tool selection. Deterministic recall is immediately available; optional existing semantic enrichment is bounded. Ordinary decisions do not wait for deep retrieval; explicit memory questions wait at most 1.5 seconds. Only IDs are cached, and each decision rereads current content, audience and forgetting controls. Late results can inform the next decision while the execution segment is live. Remaining retrieval is cancelled and drained before the segment's completion receipt is published; it cannot keep spending under a released lease. `memory.search` and `memory.read` remain available even if Jev's selection omits them. A body task (one that acts through a Minecraft body, `keepBodyTools`) never starts this recall since 2026-10-19 (production run 15: 2.3–7.3k characters of past episodes in every stored decision, 2.7 s a step, and seven of the eight a stale result). Its own recall (`bodyTaskRecall.ts`) makes a pool once a task (the deterministic search by the goal and by the game, and the memories nearest the goal by one embedding), leaves out records that teach nothing, counts the same record once (every death is one record, "×N"), and at each decision orders the pool by the situation the body gives (`recallCues`: night, threats, health, hunger, dimension, stage, recent failures, a death) and shows at most three, each cut at 240 characters, or none; what it shows is read again through memory's gate and becomes the decision's source. In the transient shape it is part of the live state. `SHANNON_FCA_BODY_RECALL_JEV` (off) lets Jev keep only the memories it is sure help now; a timeout or failure keeps the situation order. The embedding candidates are held in memory while the index's version is unchanged (`embeddingVersion`), and the scan bound is 50,000. `memory.search` still reads more when it matters. Its shared context drops the result texts, ids and operation ids of its own outcomes (`bodySharedContext`), and in the transient shape (the default) it is part of the live state, never stored. A body action after one that failed in the same response is not run (`FCA_EARLIER_ACTION_FAILED`): the guard that goes with the body rule's batch line. It holds for a body task's `minecraft_body` actions only (reads, the goal tools and every other tool still run), and a call not run is no event (`FcaEvidence.notRun`). In production a step that ran starts the scheduler's next tick at once (`continueAtOnce`, `taskRuntimeWiring.ts`) instead of waiting for the once-a-second one; `fca_decision_metrics` names the rest of a step (`other`) and the time since the previous commit (`gap`).

Task observations and genuine completed summaries are proposed as `task.experience` through the existing memory outbox and single writer. They become searchable canonical experience events without a fake chat thread or another model call. Pure lookups and redundant waits are not independent episodes. A Minecraft body's actions (`mc.*`, `minecraft.*`) are remembered as one episode per segment, not one per action (owner decision 2026-10-14): a routine action is held for its segment, which closes on a subgoal set or verified, a replan, a wait or completion, a paused or ended task, a segment quiet for `SHANNON_FCA_SEGMENT_STALE_MINUTES` (30 by default), or a notable action (a failure, an unknown outcome, a missed prediction, danger, or the first success of that action in the scope), so nothing safety-relevant waits; the episode carries the segment's actions as closed names and counts and each source id once (`fcaEvidenceSegments.ts`, `fcaOutcomeEpisode.ts`). A held action that cannot be shown now keeps its segment open until the next flush; nothing held is marked remembered unseen. The nightly learning uses a segment episode only when its closing row and each named action row match and the episode rebuilt from them is the stored one (`fcaSleepSegmentEvidence.ts`). Operation success is not whole-goal success; unobserved outcomes can be refined under the same episode identity. Episode, summary, fact, knowledge and external-read provenance follows recall and child/message propagation, including the ordinary conversation reader. Forgetting, correction, revoked reads and audience changes are checked again at use time; a process without a source resolver withholds derived private-read material. Overlapping provenance graphs are traversed with per-query memoization and cycle detection, so a long conversation does not repeatedly expand the same ancestors. Memoized source decisions do not survive the next query.

An indexed canonical-store check can prove that a scope has no task read-source provenance, allowing ordinary history to retain its fast path when no forgetting rules apply. An absent proof port is not that proof. The check reads current retained records rather than the FCA feature switch, so inserting a task episode or reopening with FCA disabled still enforces its source restrictions.

## Voice connection (stage 3)

The existing ASR → conversation/router → streamed response → TTS path remains the foreground executor. A capable client sends its stable utterance ID and `historyReceipt: "utterance-id"`; the same ID travels through the existing canonical history save. The Swift client scopes that ID per async turn rather than keeping a mutable global. Owner scope, device, thread and input digest bind the durable receipt. Duplicate generation is refused before another model call or task creation; a repeated history commit returns the original experience.

A generated turn stages its source and the exact inbox selection, releases its foreground binding, and holds descendants until the matching history commit. Newer input cannot steal the receipt. Failed generation stops unbound children; a played prefix can still be preserved by the existing partial-history path. **The receipt acknowledges canonical visible history, not completed audio playback.** No background task gains an independent speaking executor. Old clients, guests, uncertain speech, default OFF and a stopped root retain ordinary voice behavior without allocating an unfinishable FCA receipt.

## Minecraft and touch connection (stage 4)

A configured paired Minecraft body is always connected to the common FCA (Syzygy ADR-0009 S9 retired `SHANNON_FCA_MINECRAFT` and the old request queue). It requires the FCA runtime, configured body, Jev credential and Decisions credential. Its separate authenticated `/v1/body/minecraft/control` contract carries bounded world observations, concrete candidates, validated skill schemas and original operation receipts. The historical game-chat contract still carries no coordinates, inventory dump or screenshots. There is no other execution path.

The same task loop selects `mc.*` native skill tools, `minecraft.observe`, and `minecraft.reflex`. Each decision carries a bounded summary of the body's latest observation (`minecraftObservationSummary`, at most 6,000 characters: vitals, position, inventory, nearest threats and entities, the adapter facts, and the names of what was left out); `minecraft.observe` returns the whole observation. `minecraft.reflex` and the observation monitor's sessions all require a first-person picture, so neither is offered nor entered while the body cannot give one (`MinecraftControl.imagesUnavailable`): the body reports `rendererConfigured: false`, or a capture of its current connection came back without a picture and it has not reported `imageAvailable: true` since (tried again after ten minutes or on a new connection). There is no inner campaign/planning agent behind these tools. The paired adapter advertises concrete InstantSkills with bounded schemas; the server excludes planner, agent, script, arbitrary-command, chat and background-launch tools. Arguments are validated again at execution. Existing `minecraft.request/status/cancel` conversation tools refer to common tasks, preserving foreground source binding and owner-only visibility. Authenticated game-chat intent creates a task with the canonical incoming experience as provenance. Task, source and body binding are admitted atomically.

A task-owned observation monitor operates while the normal model or skill is awaiting a response. Jev checks danger, lack of progress and visual requests; an explicit reflex tool can also request a short session. The task publishes its objective, completion condition, current context and concrete candidate menu. The Decisions provider selects only a candidate ID. A session may make several sequential short choices without returning to Jev every time. Each choice uses fresh state and optionally a current/previous first-person image. Relevant target/item/precondition changes invalidate that choice; an unrelated observation update alone does not. Time, action count, inference count, image age and action duration are bounded.

Normal and reflex operations share the original task's existing action lease and Minecraft body resource. Handoff waits for an actual stop acknowledgement; cancellation intent is not proof that movement stopped. Reflex completion returns a new observation to the task; an old model decision or cancelled skill is never resumed automatically. Unknown physical outcomes hold the original operation and resource until reconciled. Inputs are released on cancellation, timeout and disconnect, but the API does not label an unacknowledged release as confirmed. Provider usage is recorded even for rejected or late responses. Decisions uses its own input-only pricing, with a conservative nonzero estimate when paid usage is unknown; live latency/cost remains unmeasured.

`fca_body_operations`, bindings and session receipts are subordinate operation journals, not new task or lease authorities. A command is executed once; a lost response or restart cannot silently reissue a movement, attack or placement. Since Minecraft run 6 (2026-10-14) a command handed in a poll reply is `delivered` until the body's next poll confirms it (`running`: listed in `activeOperationIds` or answered by its receipt); a delivered command that the next poll does not report never reached the body (the body polls one request at a time) and is handed again under the same id, which the body ignores if it has seen it, or, when it was cancelled meanwhile, settles as cancelled without a physical acknowledgement. The receipt wait counts its time from the last delivery and does not count a stall of the API's thread; after a stall it judges the frame only once the next I/O turn has read the body's polls, and before an outcome is declared unknown it asks the body once more (its next poll): a command still running there gets one more wait. An observation-triggered reflex starts within 10 s of a login, reconnection or respawn never, and before the task's first decision only for concrete danger (health at most 8, oxygen at most 6, a reachable hostile within 5 blocks, read from the frame's world state) seen in two frames in a row; the triggering fact, or why an entry was held, goes to the Observer. Since Minecraft run 10 (2026-10-14: 44 automatic sessions in 37 minutes with one body action among them; each session that starts during a decision leaves that decision stale, and the FCA's last 20 decisions were discarded) a task's automatic entries are governed across its steps (`reflexGovernor.ts`): after a session with no completed body action its mode waits 30 s (danger 5 s), automatic sessions hold the body at most 20 s in any minute, and a stuck body enters once per 2-block place until the FCA's next tool call (or 2 minutes); danger that is getting worse (health or oxygen lower than at the last danger entry, or health at most 4) is never held by these. A held entry is told to the Observer (`reflex_cooldown`, `reflex_budget`, `stuck_latched`; its sidecar `<database>.observer`, kept 15 minutes) and, with `SHANNON_MINECRAFT_FAST_JUDGMENT` on (off writes nothing new), once per change of reason, to the journal as `Shannon reflex entry held task=<id> reason=<reason>`. With `SHANNON_MINECRAFT_FAST_JUDGMENT` (Syzygy ADR-0011 stage 2, default off) danger is judged without an image before the image reflex, which then serves only stuck and visual (`fastJudgment.ts`, `minecraftFastJudgment.ts`): from the frame's hostiles, health and its fall, night and the time since the body arrived, deterministic rules pick `attack-continuously`, `flee-from` or `dig-shelter` (shelter first within 30 s of a respawn), never cut off a defensive skill of hers unless her health is at most 6, wait while the body's floor holds its safety lease or an ignited creeper is close, and re-judge the latest frame just before sending, dropping a changed, older than 1 s (by the API's receive time, not the body's clock) or other-life answer before it cuts anything off and again before it sends (a drop waits the danger cooldown and is counted by reason; `Shannon Minecraft fast judgment ...` lines carry `entryToDispatchMs`), flee after her `dig-shelter` failed in the same danger episode, and, when the body does not report `floorActive` at all, hold only while its `retreat` could run (a creeper within 4.5 m or a ranged attacker within 16 m). A session makes the decision being made stale only when it cut off a body tool in flight (or is her own `minecraft.reflex` call), sent a body action, left its control held or failed; a session that only observed and returned leaves that decision valid (runner semantics since run 10, where such sessions discarded 20 decisions). A task's cancel never cancels its own stop or release command: it waits for the body's acknowledgement, so a cancel during a session stops the step as known instead of leaving its body lease held until the unknown exit. A body retained by an unknown step is re-checked with the body itself (`docs/operator-minecraft-contract.md`, "The body re-check"). Frames and image bytes are ephemeral. Only the image from the current body connection is resolvable for inference. Remote references cannot cause URL/file fetches. ## Provenance by reference (owner decision 2026-10-15)

Switch `SHANNON_FCA_PROVENANCE_REFS` (default **on**; `off` restores both behaviours below for new rows).

- **Inheritance.** A Minecraft task created with `{ sources: 'asking' }` (`TaskChildOptions`: the in-game request and the operator request, both under the root) inherits nothing of the root's accumulated sources. The in-game request brings its own asking turn through `observeExternal`; an operator request has none. A Minecraft request made from a conversation (`minecraft.request`) already inherits only that conversation's `refs` (its current turn and the inbox reports that turn read), unchanged. Sources the task reads later (recalls, skill index, `task.get`, read receipts) are added as before.
- **Storage.** `fca_action_evidence.sources_json` and `fca_task_history.sources_json` hold `{"set":"sha256:…"}` instead of a copy when the list can be read back exactly and no row it names is still `pending`; otherwise, and for `[]`, the copy as before. `fca_provenance_sets(set_id, scope_key, step_ids_json, size, created_at)` keeps the ordered `fca_task_sources` step ids once per distinct list; the id is the sha256 of scope and list. `fca_task_history_summaries.sources_json` and the affect/memory outbox payloads still hold copies.
- **Reading.** `infra/sqlite/fcaProvenanceSets.ts` returns a copy as written and resolves a reference to the rows as they are now (same mapping as `TaskSourceStore.refs`). A set that is missing, of another scope, or names a missing/other-scope/pending row resolves to null: the row is not shown (prepare, outcome delivery, held segments, appraisal) and proofs fail (nightly task evidence). The source guard then judges the resolved list at read time exactly as a copy: who can see or hear (`ownerAlone`), forgetting, corrections and withheld replies, read receipts. Tests: `services/api/tests/fcaProvenanceRefs.test.ts`.
- **Schema.** Step `execution/013_fca_provenance_sets` (one additive table, pinned in `scripts/verify-schema-steps.mjs`, listed among the additive tables so `SCHEMA_UNCHANGED_AND_LEDGER_PINNED` holds across the deploy) is applied by the task runtime and the evidence store when the switch is on. No existing column or row is changed; rows with copies stay readable by both builds.
- **Measure.** `node --import tsx scripts/measure-fca-provenance.ts [steps] [rootSources]` (synthetic, deterministic fixture).

### Deploy and rollback

Deploy with the normal runbook. Before the restart take the consistent backup (`sqlite3 … ".backup <dir>/shannon.sqlite"` and `pragma integrity_check`) and `verify-schema-steps.mjs dump`; after the API starts, `check` must print `SCHEMA_UNCHANGED_AND_LEDGER_PINNED` with `execution/013_fca_provenance_sets` in the ledger.

Post-deploy watch item: the API log line `Shannon FCA evidence prepare outcome=… unresolved=N` (printed only when N > 0) counts evidence rows whose provenance reference could not be resolved; those rows are not shown to the task (fail closed). It must stay absent. After the deploy, and again after any restore or manual database edit, search the API log for `evidence prepare` lines containing ` unresolved=`; any hit means a set or source row is missing, so stop and investigate before relying on the evidence (switching the flag off does not repair it). `scripts/fca-provenance-expand.ts` reports the same count (`unresolved=`, plus `malformed=` for `{"set":…}` values this build cannot read) and refuses `--apply` while either is non-zero.

An older build reads a reference as unparsable sources and hides those rows (prepare/visibility fail closed; the nightly proof fails), and it cannot read history rounds by reference (`fca_task_history` rows with `{"set":…}` make the older `JSON.parse(...)` of a round yield an object, not a list). So:

1. **Containment without a source rollback (preferred).** Set `SHANNON_FCA_PROVENANCE_REFS=off` and restart the API: new rows are copies again, the root's whole set is inherited again, and rows already written by reference stay readable by this build.
2. **Source rollback to a build before this change.** At a quiet boundary (no FCA task running, `fca_task_checkpoints.step_id` all NULL), stop the six services and take a fresh stopped backup. Then either
   - **(a) restore** the pre-deploy backup only with the owner's approval (it loses FCA rows, tasks and memory written since the deploy; never the default), or
   - **(b) expand references in place** (no data loss): `node --import tsx scripts/fca-provenance-expand.ts <stopped db>` (dry run: counts), then the same with `--apply`. In one transaction it rewrites every `fca_action_evidence`/`fca_task_history` row holding `{"set":…}` back into the copy (resolved exactly as this build reads it) and prints `integrity`; it refuses and writes nothing if any reference is unresolved or malformed (a `{"set":…}` value that is not a reference this build reads), and exits non-zero when `integrity_check` is not `ok` (before or after the rewrite). Compare row counts before and after. `fca_provenance_sets` and its ledger row stay (an older build ignores both).
3. Then follow the runbook's source rollback (untar `source-before.tar`, delete the new files, restore `DEPLOYED_REVISION`, start API → mind → others) and run `verify-schema-steps.mjs check` against the post-deploy dump.

## Stage 5: scheduled sleep through the same FCA

Since Syzygy ADR-0009 S9 every night takes this path (`SHANNON_FCA_SLEEP` and the worker's old sleep batch are retired): the background worker schedules the owner's nights only and claims turn refinements only; it needs ActionThreads and the existing memory outbox. `SHANNON_SLEEP_MIN_MESSAGES` (default 3: a night with fewer user messages uses the local rules, not the model) is read by the API's sleep task from the API's environment; the worker unit no longer sets it. The worker still creates the existing scope/day-deduplicated `background_jobs` at the configured sleep hour; the API admits a fresh, never-attempted owner night into the same canonical Task Hub. Task creation, the immutable maintenance binding, and the original job claim share the store's SQLite connection and transaction. An already attempted legacy night remains on its old path. The API borrows this connection and never closes it separately.

A scheduled task has `origin=maintenance`, `kind=sleep`, under the one existing ancestor. A public task tool, HTTP task request, message, or external body event cannot create or escalate this origin. The existing mind worker continues to own all execution leases. Maintenance execution permission is separate from actual owner-alone disclosure: internal consolidation can continue with others present, while ordinary conversation/task/private-reader permission stays unchanged. Its catalog contains only the current `sleep.phase_apply`; it receives no general task, web, messaging, or body tools.

The ordinary `runFcaStep` executes memory → knowledge → skills → platform summaries/impressions → optional Aether skill-copy export → completion. Each decision performs at most one of that phase's original configured model calls. Memory and knowledge retain their original models and shared background budget; skill maintenance/proposal retains its own model policy, separate skill budget, nightly counters, maximum proposer calls and source/body checks. A skill proposer open commits its IDs, then the next common FCA step chooses its continuation; there is no hidden nested paid ReAct loop. Missing models or exhausted caps take an explicit model-free outcome, preserving the original available functions.

Checkpoints contain phase identity, IDs, versions and counters. Raw model outputs, source text and functions stay within one step. Every phase rechecks current source controls before inference and application. Memory, knowledge and people results go through the existing memory proposer/outbox. A checkpoint barrier waits for the sole worker memory writer's terminal acknowledgement before a dependent phase consumes them; this continuation makes no new model request. Known rejected/superseded proposals are counted separately from applied results. Failed or missing writer results remain unconfirmed. The skill store and idempotent Aether export retain their existing write paths; no second memory writer is introduced.

Sleep history uses deterministic compaction of its phase/receipt ledger, so a long writer wait can exceed the ordinary 24-entry working window without another paid summarization call. Original round coverage stays in canonical history. Normal knowledge retirement is not forgetting, including with skills disabled; its retained original sources remain checked. Self-interest inputs are captured once, registered with their evidence, and compared in full (including owner revision/generation) again under the same SQLite write lock before applying memory changes.

Observed task successes and failures can seed knowledge and skills without pretending the owner spoke them. The task experience must match the committed canonical task/evidence/history, operation, result, status, summary, source IDs and timestamp. Unknown, cancelled, nonterminal or uncommitted outcomes are excluded. Private document lineage is excluded from reusable task-derived material even while the private reader is authorized; original forgetting and correction propagate to the derived knowledge and skill copies.

The original night becomes completed only after every admitted phase and the final task segment receipt are confirmed. A lost paid result or unconfirmed write holds the task as unknown; process restart, lease expiry or switching the feature off does not return its bound night to the legacy worker or replay a paid call. Existing configured usage/cache checks run before accepting model output, the parent stop signal reaches every new phase call, and incomplete paid outcomes retain a conservative cost estimate in their original budget ledger. Actual cache hits, real latency and real expenditure remain unmeasured here.

A known stopped sleep task can resume explicitly only while its saved night identity still exactly matches the trusted current job. Once reconciliation has closed that night as failed, resume is refused with the existing `FCA_NOT_RESUMABLE` response and does not queue an unusable task. A valid continuation preserves the saved phase checkpoint; it does not replay already committed paid phases. Ordinary owner task resume behavior is unchanged.

Public sleep task title, goal, criteria, summary and parent notification are fixed code metadata. Ordinary `task.get/list` can inspect this status with owner permission, but neither the conversation bridge nor task-source inheritance copies internal sleep references into unrelated owner tasks. Avatar and native app behavior remain unchanged except for the origin caption “内部の記憶整理”; status, stopping, unknown and disclosure controls stay intact.

For a later authorized rollout, configure the common-runtime and sleep flags consistently in the API and existing background worker, keep the existing mind worker and sole memory writer enabled, and retain the existing nightly timezone/hour/minimum-message settings and model budgets. Observe the canonical job, maintenance task, phase checkpoint, outbox results and final segment receipt together. Turning the sleep flag off prevents new admissions; a bound unfinished night is held for explicit reconciliation rather than reclaimed by the legacy path. No configuration or production restart was performed during this implementation stage.
