Build 38の実機ログで、iPhoneは音声・データ欄と32件の接続候補を含む完成済みSDPをAzureへ送れていました。失敗地点はAzureからOpenAIへ接続情報を転送する処理です。

今回わかったこと

ice_gathering=complete、audio_sections=1、data_sections=1、candidates=32を確認しました。Azureの同時刻ログはOpenAIの400 invalid_offerです。

訂正：gpt-realtime-2.1-miniは現行の正式モデルです。モデル名は変更しません。

1

接続情報を改変しない

SDP末尾の改行を削除せず、iPhoneが生成した文字列をそのまま保持します。

2

公式と同じ搬送

独自のmultipart組み立てをやめ、標準FormDataに境界生成を任せます。

3

次の失敗を一度で特定

OpenAIのrequest IDと、資格情報・IP・SDP秘密値を伏せた理由だけをサーバーログへ残します。

検証済み

API 172件、iOS 77件、署名なしiPhoneビルド、差分検査がすべて成功しました。

会話DB、認証、既存トーク、iOSアプリ、App Iconは変更しません。TestFlightの再配信も不要です。

許可後にこちらで行うこと

  1. Azure上の対象ソースとSQLite一式を時刻付きでバックアップする。
  2. Realtime搬送の2ファイルだけを暗号化されたSSH経由で転送する。
  3. Azure上で型検査とAPIテストを実行する。
  4. shannon-ios.serviceだけを再起動する。背景ワーカーには触れない。
  5. ヘルスチェック、会話件数、接続状態、エラーログを確認する。

許可する場合：「Build 38 Realtimeサーバー修正のAzure転送・対象ファイルバックアップ・DBバックアップ・APIテスト・APIサービス再起動を許可します」と返信してください。

反映後の成功条件

  1. 現在のBuild 38で音声ボタンを押す。
  2. 「ライブ音声に接続できませんでした」が出ず、接続状態になる。
  3. 話した内容が途中から字幕に現れ、シャノンの字幕と音声返答が出る。

失敗時の安全な戻し方

旧ソースを戻して同じAPIサービスだけを再起動します。DB構造は変えないため、会話履歴や接続情報の移行はありません。

接続がまだ失敗する場合も、追加された安全なOpenAI診断情報をAzure側で確認できるため、再びTestFlightを作らず次の原因を判断できます。
