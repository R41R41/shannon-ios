# Minecraft lifecycle

Candidate implementation only; no live server, world or bot was operated for this change.

The common tool registry exposes `minecraft.lifecycle_status`, `minecraft.start`, `minecraft.stop`, `minecraft.login` and `minecraft.logout` from owner-private text/voice and the existing own-time worker. Server start and bot login are separate. Fresh operator status is available even when the world body is absent. Unconfigured or stale operator status offers no lifecycle operation.

API and own-time workers share `minecraft_lifecycle_snapshot` and `minecraft_lifecycle_operations` through SQLite. The snapshot contains closed running/bot state and human counts; raw player identities and credentials remain outside the companion database. Each command retains its original action lease, execution ID, issuedAt and origin; a self-directed step remains `own_time` under the existing pause, budget and activity gates. The tool adapter uses the existing body resource permit. The paired operator rechecks its original command via `/v1/body/minecraft/lifecycle/permit` immediately before an actuator, after fresh native reads.

The existing body device alone polls `/v1/body/minecraft/lifecycle`. It is configured with `SHANNON_MINECRAFT_LIFECYCLE=on`, existing Stage4 authority and `SHANNON_MINECRAFT_LIFECYCLE_SERVERS` as an explicit JSON array of server IDs already declared in `SHANNON_MINECRAFT_BODY_JSON`. The operator has its own default-off `MINEBOT_LIFECYCLE=on` and must remain in common-FCA mode. Its source is the isolated canonical Minebot repository worktree's `services/integration/configuredMinecraftLifecycle.ts`; see that repository's `docs/minecraft-lifecycle.md` for actual fixed-world, private RCON and journal configuration.

Start requires authoritative stopped state. Already-running is an idempotent no-op. Login requires the configured running server and verifies both native bot identity and the server UUID list; starting a process does not prove joining. Logout awaits physical body release and network end and cancels scheduled reconnects while keeping the operator running.

Stop first refuses nonzero or unknown other-player counts. Its final player test and shutdown are one native Minecraft server-thread command, which exempts only the configured authenticated bot UUID on an online-mode server. Offline mode exempts nobody. No unguarded stop or forced-kill fallback exists. A changed-stop receipt must prove both actual stopped state and the guarded command's native shutdown acknowledgement; a coincidentally stopped process after a lost acknowledgement stays unknown. RCON may retain a completed command-response frame when shutdown closes the socket before the response sentinel. The API rejects a stopped snapshot alone as shutdown proof.

Original IDs are reserved under a SQLite transaction and delivered once. An unresolved operation blocks new lifecycle operations, including a new execution or a replacement ID. The operator fsyncs its begin record before actuating, then its immutable receipt. Lost transport may resend a receipt, but never an action. An interrupted/uncertain effect remains unknown and keeps the original resource/acknowledgement held. A later native terminal acknowledgement can resolve the same original ID/connection/action only with actual release proof and a newer observation; receipt, native state and stop-guard times must be at or after the original issuedAt, even when transport delivers that original receipt much later; completion still requires its native postcondition and atomic stop guard. `minecraft_lifecycle_receipt_events` retains the earlier unknown evidence unchanged. A current state that happens to match the goal is not a later acknowledgement. Any other unresolved tool or paid-model outcome keeps the whole action held.

`services/api/artifacts/skill-packs/minecraft-lifecycle/draft-1/` contains an operator-authored procedure for these tools. Bundling creates no runtime authority and performs no import. It uses the existing owner-reviewed import contract, provenance, artifact hashes, disclosure checks and trial status. This procedure is separate from `standard10/draft-2`, whose reviewed bytes remain unchanged.

Offline validation covers cross-process status/queue sharing, delivery and receipts, live authority revocation, native stop proof, login distinction, restart/unknown holds, malformed native players, human-join races and a fake bounded RCON TCP transport. A configured paired-device live smoke test and production rollout remain separate work.
