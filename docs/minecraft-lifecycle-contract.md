# Minecraft lifecycle

Owner addition, 2026-10-30: [Minecraft streaming](minecraft-streaming-contract.md) permits audited operator start/stop/login/logout during streaming. This exception belongs to the exact operator action and never turns ordinary conversation or own-time authority into public authority. set_day remains owner-alone. Native stop admission closure, other-player checks, original leases and receipt proof are unchanged. Production rollout is recorded separately.

Candidate implementation only; no live server, world or bot was operated for this change.

The common tool registry exposes `minecraft.lifecycle_status`, `minecraft.start`, `minecraft.stop`, `minecraft.login` and `minecraft.logout` from owner-private text/voice and the existing own-time worker, and `minecraft.set_day` from owner-private text/voice only. Server start and bot login are separate. Fresh operator status is available even when the world body is absent. Unconfigured or stale operator status offers no lifecycle operation.

API and own-time workers share `minecraft_lifecycle_snapshot` and `minecraft_lifecycle_operations` through SQLite. The snapshot contains closed running/bot state and human counts; raw player identities and credentials remain outside the companion database. Each command retains its original action lease, execution ID, issuedAt and origin; a self-directed step remains `own_time` under the existing pause, budget and activity gates. The tool adapter uses the existing body resource permit. The paired operator rechecks its original command via `/v1/body/minecraft/lifecycle/permit` immediately before an actuator, after fresh native reads.

The existing body device alone polls `/v1/body/minecraft/lifecycle`. It is configured with `SHANNON_MINECRAFT_LIFECYCLE=on`, existing Stage4 authority and `SHANNON_MINECRAFT_LIFECYCLE_SERVERS` as an explicit JSON array of server IDs already declared in `SHANNON_MINECRAFT_BODY_JSON`. The operator has its own default-off `MINEBOT_LIFECYCLE=on` and must remain in common-FCA mode. Its source is the isolated canonical Minebot repository worktree's `services/integration/configuredMinecraftLifecycle.ts`; see that repository's `docs/minecraft-lifecycle.md` for actual fixed-world, private RCON and journal configuration.

**Its own lease (Syzygy ADR-0009 S7, 2026-10-13).** A start, stop, login or logout the owner asks for in a conversation is not run under the turn. The turn admits it under its own action of kind `minecraft` (the Minecraft slot), whose source is the operation's server-made id `lifecycle:<sha256>`, takes the body under that lease, and answers 「受け付けました」 at once (tool evidence `queued`). The operation then runs to its native receipt in the background (`minecraftLifecycleRunner.ts`); the turn's time limit, its end and its signal no longer revoke it, and the turn never holds the body. No command runs under a turn's respond lease: without its own action (no action threads) a conversation's request is refused as `unavailable`. Its accepted receipt reaches her as a 【知らせ:作業終了】 notice (`minecraft.<action>`, done/failed/cancelled, within an hour). An unresolved operation, a full Minecraft slot or a held body is refused at once as `conflict`, with nothing started. A delivered command is no longer cancelled because the operator's frames paused (an operator starting the server or spawning the bot may not poll for seconds); a stale frame cancels only a command not yet delivered, and the original authority, the deadline and the caller's signal still stop either. Unknown: the action closes `unknown` (`lifecycle_result_unknown`) and leaves by the action store's one unknown exit (`outcome_unknown_closed` after ten minutes); from then on the operation no longer blocks new lifecycle operations or the operator's serialization slot, and an action that held the body only for a lifecycle operation (a conversation's or an Ops request's own `minecraft` action, or a pre-S7 conversation turn) releases the body with its slot. A late original receipt still settles it; nothing is resent. A body held for play (an FCA step, the legacy request) still waits for its release proof. Own-time and FCA task steps keep running lifecycle operations under their own step leases as before.

**`minecraft.set_day` (owner request through the Minebot lane, 2026-10-14; body ea1ef4ce).** The lifecycle action `set_day` makes the operator run exactly `time set day` over its private RCON (the RCON secret stays in the body). The tool is offered only in text and voice to the owner alone, never in her own time, a task step or with anyone else present, and runs only as a conversation request under its own `minecraft` action through `minecraftLifecycleRunner.ts`, like a start: 「受け付けました」 at once, then a 【知らせ:作業終了】 notice. The API refuses it before admitting anything unless the fresh status shows the server running with zero other players; the operator rechecks authority and players itself. Accepted completion is `completed`/`changed` with `state.running === 'running'` and no stop guard (the body's reply carries ordinary state, no time of day); others online are `refused`/`players_present`; an RCON error or an unexpected reply is `unknown` with inputs not released. A body that predates `set_day` drops the command without a receipt: the command is cancelled at its 120-second deadline, the action closes `unknown` (`lifecycle_result_unknown`), and at the ten-minute unknown exit (`outcome_unknown_closed`) a 【知らせ:作業終了】 notice says the accepted operation closed without a confirmation from the body (reason `lifecycle_result_unknown`; this applies to every conversation lifecycle operation that leaves by the exit without a receipt). There is no Ops mapping: the Windows console has no command type for it, and `ops_lifecycle_dispatches` keeps its four-action check.

Start requires authoritative stopped state. Already-running is an idempotent no-op. Login requires the configured running server and verifies both native bot identity and the server UUID list; starting a process does not prove joining. Logout awaits physical body release and network end and cancels scheduled reconnects while keeping the operator running.

Stop first refuses nonzero or unknown other-player counts. Its final player test and shutdown are one native Minecraft server-thread command, which exempts only the configured authenticated bot UUID on an online-mode server. Offline mode exempts nobody. No unguarded stop or forced-kill fallback exists. A changed-stop receipt must prove both actual stopped state and the guarded command's native shutdown acknowledgement; a coincidentally stopped process after a lost acknowledgement stays unknown. RCON may retain a completed command-response frame when shutdown closes the socket before the response sentinel. The API rejects a stopped snapshot alone as shutdown proof.

Original IDs are reserved under a SQLite transaction and delivered once. An unresolved operation blocks new lifecycle operations, including a new execution or a replacement ID. The operator fsyncs its begin record before actuating, then its immutable receipt. Lost transport may resend a receipt, but never an action. An interrupted/uncertain effect remains unknown and keeps the original resource/acknowledgement held. A later native terminal acknowledgement can resolve the same original ID/connection/action only with actual release proof and a newer observation; receipt, native state and stop-guard times must be at or after the original issuedAt, even when transport delivers that original receipt much later; completion still requires its native postcondition and atomic stop guard. `minecraft_lifecycle_receipt_events` retains the earlier unknown evidence unchanged. A current state that happens to match the goal is not a later acknowledgement. Any other unresolved tool or paid-model outcome keeps the whole action held.

### Optional command `options`: `freshWorld`

`MinecraftLifecycleCommand.options` is optional and absent on every command that does not ask for it (a body that predates it sees the old command; the API's identity check compares it, so a resend cannot add or drop it). `options: { freshWorld: true }` is put only on a `start` of `shannon-home` that the owner newly asked for (a conversation, the Ops `minecraft.start`, the operator CLI) while the owner's 「新しいワールドで始める」 switch is on, the server is `stopped` in a fresh frame, no Minecraft-bound task is open and no lifecycle command is unresolved, **and the connected body advertised the capability**; never on a task step, own time, a recovery or a resend. The body then keeps the current world under another name (`<level-name>.before-regen-<JST stamp>`; nothing is deleted) and starts a new one before reporting `changed`. The switch, the record and the exact conditions are in [ops-contract.md](ops-contract.md#fresh-world-switch).

**Capability handshake.** Every body poll may carry `capabilities: string[]` (at most 64 names; only well-formed names `[A-Za-z][A-Za-z0-9]{0,31}` count, anything else is ignored and never refuses the poll). The poll frame is stored as it arrives, so the latest fresh frame (at most 3 s old) is the connected body's capabilities; a body that predates the field, or was replaced by an older build, sends none and so has none. The API attaches `options.freshWorld` only when that frame lists `freshWorld`, checked once when the decision is made and again just before the command is stored (if the body no longer says it, the command is the ordinary start). Otherwise it records `fresh_world_unsupported`, starts normally, and never tells the owner that a new world was made. An API that predates the field ignores `capabilities`, and a body never needs to know whether the API does.

**Receipt.** A start whose world the body really prepared carries `worldId` (the new places-world id, `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`) and `movedTo` (the name, in the server directory, the previous world is kept under, or `null` when there was none; `^[A-Za-z0-9][A-Za-z0-9._ -]{0,127}$`) beside the usual receipt fields. Both are optional; a receipt without them is an ordinary one. A malformed value never fails the whole poll (it would be resent in every poll, for ever): the API leaves out that one value (`withoutMalformedReceiptWorlds`), keeps and acknowledges the receipt, and writes a content-free `fresh_world_receipt_world_dropped` line to the activity record once (an absent `movedTo` is then "not known", never "there was none"); the body in turn never sends a value that fails these patterns. The receipt is told as a new world only when the stored command carried `options.freshWorld`. The same receipt sent again (a lost acknowledgement, an operator restart resending its journal) is acknowledged again but is not adopted, told or recorded a second time; only the first adoption of a receipt, or a recovery that replaced an `unknown` one, is. An `unknown` receipt that carries `worldId` / `movedTo` means the world **was** moved aside and the new one prepared while the start could not be confirmed, and the owner is told that. A refused/error receipt for a fresh-world start means nothing was changed (the body puts its world-id file back when a step after writing it fails while the server is still stopped); an unknown one means the state is not known and the world name must be checked. From the accepted receipt the API tells the owner (conversation line, Ops result, activity record, operator audit): 「新しいワールドで始めました（前のワールドは <movedTo> として残しています）」.
