## FCA response lane

The response path is intentionally short and uses one immutable state snapshot:

1. Authenticate the device and resolve the conversation thread.
2. Load the latest committed companion state.
3. Run the bounded, read-only recall stages. None of them writes shared state or waits for the background worker.
   - Always: the deterministic relevance pass over recent experience plus deterministic full-text search over every experience and other threads' rolling summaries. No model is called.
   - Only for memory turns (voice: Jev selected `conversation_memory`; text: the equivalent `needsSemanticMemoryRecall` classifier shared with the Apple clients through `config/memory-recall-cues.json`): semantic recall — query rewrite, embedding search over precomputed summary embeddings, and reranking. `SHANNON_MEMORY_MAX_MODEL_CALLS_PER_TURN` (default 4: rewrite, embed, rerank, and knowledge-tree navigation) and `SHANNON_MEMORY_SEMANTIC_TIMEOUT_MS` (default 4000) bound it; a failure or timeout contributes nothing and the turn continues with deterministic recall. Forgotten or invalidated sources, replies that used them, and summaries built from them are filtered before any text reaches a model (see Forgetting boundary). Semantic hits are appended after deterministic results with cue `semantic` and an instruction to treat them as candidates. Cost is recorded in the `memory` lane.
   - Voice classifies such a turn as `under_10s` or longer so the existing waiting phrase plays first; Talk shows 「記憶を探しています」 while a memory turn is pending.
4. Select one owner-visible active intention using current-turn evidence, thread affinity, priority, and recency. An explicitly stated goal in the current utterance participates provisionally so the same reply can honor it, but is persisted only after the turn succeeds.
5. Assemble the canonical identity block (see [Canonical identity](#canonical-identity)), prompt projection, turn-specific recalled memories, selected intention, relevant Aether context, active agent-task projection, and the conversation history of the thread inside its replay window (see [Conversation replay window](#conversation-replay-window)). Everything that comes from memory passes the disclosure gate for the people present (see [People and audience](#people-and-audience)); text chat is the owner alone unless the client sends `audience: "others"`, so by default nothing is withheld or marked by it.
6. Call the fixed chat model with adaptive-depth response guidance: lead with the outcome, stay concise for simple questions, and preserve enough Markdown-structured detail for explanation, design, research, and implementation work. Ordinary turns use one model call. A place-discovery turn first runs the read-only place skill, then passes its bounded candidate and source data into the normal final synthesis alongside other selected capabilities.
7. Store the assistant reply with the face of Shannon's feeling for that reply (see [Emotion, face, and traits](#emotion-face-and-traits)), then persist the explicit intention and a bounded cognitive-cycle receipt containing only visible inputs, selected IDs, action class, outcome, and summary. It never stores hidden chain-of-thought.
8. Enqueue non-blocking emotion, durable memory, prospective-memory, and activity work.

**Sentence stream (opt-in).** `POST /v1/chat` with `stream: "sentences"` answers a successful turn as NDJSON instead of one JSON document: `start` (thread id, applied audience, and the turn id when it is already known), `sentence` lines `{ index, text }`, then `done` carrying exactly the object the JSON response would have been, or one `error` line. It is for a client that speaks and subtitles the reply, such as her body. The sentence texts joined are `reply` character for character (`chatSentenceSplitter.ts`), and the lines are written with the voice route's NDJSON writer (`serverChatSentenceStream.ts`). Without the field the response, the provider request bytes and the stored turn are what they were; any other value is refused with 400. **While the model writes (owner decision 2026-10-02):** for a turn the owner alone reads, with no fallback (a Notion page read is one; an Aether note or Voyager task read is not, since it does not change the reply text), the kernel calls the model through `generateChatTurn` (`chatSentenceStream.ts`), the adapter sends the same request with `stream: true` and decodes the `reply` field of the structured output as it grows (`chatModelStream.ts`, `chatReplyStreamDecoder.ts`; the request body and result reading live in `chatModelTurn.ts`, shared with `generate`), and sentences go out before the reply is complete. The completed turn is parsed, checked, accounted and stored by the same code as before; the HTTP layer checks that what it sent early is the beginning of the finished lines and sends the rest. The accepted cost is retraction: if the completed turn is rejected or the provider stream fails after sentences were sent, the stream ends with `error`, nothing is stored, and the client discards what it showed. **After the turn is complete:** an `audience: "others"` turn, a turn with a capability read, and every turn when `SHANNON_CHAT_STREAM_EARLY=off` or the model cannot stream are completed and stored first and their lines written together, so no line carries text the JSON response would not carry. Turns whose reply is fixed command text or has a list appended (explicit command, organize, attachments, web search, place search, a Notion source list) are a single `done` with a `fallback` reason. A reader that disconnects loses only lines: the model call is not cancelled and the turn is stored. The kernel's part is the `stream` check on the audience validation line, `generateChatTurn` in place of `chatModel.generate`, and `withSentenceStream` on the final return; `server.ts` calls `dispatchWithChatSentences` in place of `kernel.dispatch` on the generic route. Contract: [`docs/chat-stream-contract.md`](chat-stream-contract.md).

For a newly created thread without an explicit title, the first successful user/assistant exchange also produces a short title in that same model call. The store commits the title and both messages in one transaction, rechecking title ownership after the model returns. Manual edits always win, including an explicit edit to `新しいトーク`. Missing or invalid title metadata falls back to a bounded excerpt of the user message without failing the reply. The chat response includes the committed thread so iOS can update and cache its list immediately; older responses still use the existing thread-list refresh.

SQLite schema v8 adds `conversation_threads.title_origin` (`pending`, `automatic`, or `manual`). Migration preserves all existing titles as manual because older rows have no edit provenance. Only newly created untitled threads are eligible for automatic naming. The migration is additive and runs inside the existing restart-safe migration transaction.

Emotion and memory updates affect the next reply after they commit. Prediction-error processing is not part of v1.

## Canonical identity

`packages/cognition` owns one pure definition of who Shannon is and what she can do. Every response prompt starts with it, so text, voice, and notifications are the same Shannon and the provider can cache the stable prefix.

- **Persona** (`persona.ts`, `shannonPersonaPrompt`): first person `ボク`, the owner is `ライ氏` and never `あなた`, です・ます with a raw tone only when emotion is strong; bright, cheeky, sure she is a genius, a little clumsy; flustered and recovering after a mistake, happy and bashful when praised, praises back, glad to talk; not biased toward jabs at the owner; no repeated catchphrase; plain explanations for technical and work matters; serious without jokes in a hard, urgent, or dangerous moment. The guest variant keeps the character but never assumes the speaker is the owner and never addresses them as `ライ氏`. Both variants end with her current goal and motive (`SHANNON_CURRENT_GOAL`, `SHANNON_MOTIVE`: 人を感動させる物語を作ること／物語を通じて人間を知りたい、世界を知りたい), which the owner decided in Syzygy ADR-0002; they are her own, not an owner detail.
- **Suite roles** (`shannonSuitePrompt`, `SHANNON_SUITE_PRODUCTS`): Aether（エーテル）is the writing and notes app, Voyager（ボイジャー）is the task app, Shannon is conversation, support, and requested execution. Knowing a role is not having read or being allowed to change its content. The same table supplies the Latin and Japanese names to voice routing, the notes/tasks read gates, and the Voyager search phrase.
- **Capabilities** (`capabilities.ts`, `shannonCapabilityPrompt`): what she can do and how it is invoked, what she cannot do today, and how to answer — say plainly when she cannot, offer the nearest thing she can, propose an improvement task only when the owner wants one, and never claim an action without a receipt. Text and voice receive the identical text; a guest receives only the capabilities that need no owner data, and is told that she checks before speaking whether something is personal information the people present do not know, that secrets are not given to her, that nothing is created, deleted or started, and that the name and the conversation are remembered unless the owner chooses 「今回は残さない」. `services/api/tests/shannonCapabilityEvidence.test.ts` maps every capability id to a code-path flag, so describing a capability without a code path fails type checking or the test. Agent work that adds or removes an ability updates this table in the same change. The block also states the bounded-autonomy rules from `autonomy.ts` (`shannonAutonomyRuleLines`): where she may act freely, what needs the owner's approval, what is forbidden, and that the mechanism for acting on her own is being prepared (「仕組みは準備中」). Only while the activity loop is enabled and running does the owner projection replace that one line with what the loop does (`withAutonomyRunning`, applied by `ShannonAutonomyService.identityProjection` for owner text and owner voice); the static text never claims it. A guest receives one line saying such requests are refused, with none of the owner's places, core areas, or budget.
- **Projection**: `shannonIdentityPrompt(audience)` joins the three blocks. It is the first section of the text system prompt and the owner voice prompt with memory (`assembleShannonSystemPrompt`), of the slim owner voice prompt that carries no owner state, and of the guest voice prompt. A path adds only delivery notes: the Markdown response style for text, `voiceConversationInstructions` for spoken brevity and turn grounding, and `SHANNON_ONE_LINE_VOICE` for a generated one-line opening. The chat-model adapter adds no persona text of its own.
- **Fixed sentences**: server-authored sentences presented as Shannon speaking (command replies, initiative and commitment messages, notification bodies for finished or failed work, waiting phrases) use the same voice. Approval requests, task status, and error messages are neutral system text and do not speak as her. `services/api/tests/shannonAuthoredCopy.test.ts` scans those sources for casual endings, `あなた`, and third-person self-reference.

The effect on model output is not covered by deterministic tests; it is checked by hand after deployment.

## Place discovery skill

Text chat recognizes a place request; the live-voice router selects `place_discovery` independently of `current_web`, memory, device context, and other skills. The skill searches for up to five places without sending conversation history or private context. Its normalized names, addresses, reasons, Apple Maps queries, and bounded source links become lower-trust reference data for the final reply. Final synthesis can also use current web search and the usual selected app capabilities, so a request such as “近くのカフェと今日の天気” keeps the place candidates available while answering the weather part. The map card comes from the skill result, not a second extraction from final prose. Text history retains map links; voice speaks without URLs and saves the links in the owner thread.

Only a nearby-place request forwards a fresh, one-time device location to the skill. If location or candidate evidence is missing, Shannon asks for the area or states the uncertainty instead of inventing a position, route, opening hour, or weather. This is an app response skill and does not give the model permission to book, navigate, or write to an external service.

## Intention and cognitive-cycle lane

Text chat and owner-mode live voice share the same intention frame. Conservative Japanese rules capture only explicit owner goals such as a stated objective or a concrete request to build, improve, integrate, or finish something. Ordinary statements of a continuing wish with a build verb, a made thing, a habit or a month-scale deadline (“…を今月中に配信したい”, “完成させたい”, “実装したいです”, “毎日30分走りたい”) are also goals (`intentRules.ts`); a passing wish, a conditional, or a plan for today or tomorrow is not. Negated goals, vague continuation phrases, questions, and guest voice sessions do not create durable intentions. Matching active goals are deduplicated rather than multiplied by repeated wording.

When that same owner turn explicitly creates or refreshes a goal, the existing structured chat response may include one bounded plan proposal: one immediate next step and one to five verifiable stages. The server accepts this metadata only when its own deterministic intent extractor found an explicit goal, normalizes and bounds every stage, and persists it with the intention. Later text and owner-voice turns receive the saved plan in the intention frame. The plan is owner-visible guidance, not an action receipt; it cannot execute tools, complete a stage, or complete the goal.

`GET /v1/cognition` exposes the owner's intention ledger and recent bounded cycle receipts. `POST /v1/cognition/intents/status` can pause, reactivate, complete, or dismiss one exact intention. The prompt treats an intention as continuity evidence, never proof that work occurred; only the existing verified action or agent-task receipts can establish an external change.

This lane is the first durable perceive → recall → intend → plan → respond → record vertical slice. It now supports bounded initial decomposition but does not replan from verified execution progress, choose autonomous external actions, or mark plan stages or goals complete from model prose. Those remain later bounded extensions over the same owner-visible ledger.

## Shannon private knowledge

Memory has four kinds: experience (`experience_events`, thread summaries), Shannon's private knowledge (`shannon_knowledge_documents`), the user profile (`knowledge_answers`, `knowledge_evidence`, `knowledge_revisions`, unchanged), and her impressions of people (`person_impressions`, see Impressions of people). Private knowledge is Shannon's own procedures, lessons, and hypotheses. It has no user-facing folder, list, summary, or API route; the owner reaches it only by asking Shannon (see inquiry below). Syzygy decision: `TI-REQ-SHANNON-MEMORY-V2`.

- **Document** (schema 17): title, Markdown body, parsed heading tree, status (`hypothesis`, `confirmed`, `retired`), applicability, source experience IDs (a database constraint rejects an empty list), Aether references by document ID, version and optional section/decision ID only, timestamps, and a version. Every write appends to `shannon_knowledge_revisions`; retirement keeps its reason and evidence there.
- **Writing**: `ShannonKnowledgeConsolidator` runs after each completed sleep batch, inside the shared monthly background budget (lane `memory_background`, default model `gpt-5.6-terra`, `SHANNON_KNOWLEDGE_MODEL`). It sees only visible experiences of that day plus related earlier ones found by full-text search, detects recurring situation → action → outcome patterns, and may create, update, or retire notes without approval or notification. `normalizeKnowledgeDraft` rejects drafts without known sources, with copied conversation lines, or with secret-like text, and stores a single-source success as `hypothesis`. A failure never fails the sleep batch.
- **Using**: `usableShannonKnowledge` drops retired notes, any note whose source experience is forgotten, corrected, or rejected, and any note citing an older Aether version than the known current one. Deterministic term matching selects up to three notes per turn; semantic recall may add usable notes. A note longer than 1,500 characters (or any note on a voice `skill_complex` turn) is navigated by heading: one model call chooses sections within the per-turn call budget, otherwise sections are chosen deterministically. The prompt block is labelled lowest authority, states the order user's explicit words > Aether decisions > profile > notes, and marks hypotheses as tentative. Notes are never written into user facts or the profile.
- **Inquiry and forgetting**: 「〇〇について何を覚えてる？」 adds a provenance block (conversation date, other-thread summary, or Shannon note/hypothesis). Within ten minutes, 「それは忘れて」 forgets exactly the items cited in that answer: experiences through the existing memory controls (restorable from Memory), notes by retirement with the owner's instruction as the reason. Knowledge derived from a forgotten experience stops being used and is never embedded; the same holds while a source turn's reply is withheld by the forgetting boundary, or while the note's own text restates a withheld item.

## Impressions of people

Decision of 2026-10-02 (Syzygy ADR-0003): memory is separated by kind because search conditions and ageing differ. Besides experience, private knowledge and the user profile there is a fourth kind, **impressions**: what Shannon has noticed, across separate turns, about how a person talks to her or behaves in conversation, how often, since when, and how she feels about it. The owner is a person too (key `owner`); everyone else is their `people` row. An impression is data she accumulated — a pattern with supporting and contradicting evidence counts — and never a hand-written prompt rule. `SHANNON_IMPRESSIONS=off` (also `false`, `0`, `disabled`) reads nothing into a prompt and updates nothing; every prompt is then byte for byte what it was. The owner's screens keep listing what is stored.

- **Storage** (`sqliteImpressions.ts`, additive, outside the numbered migrations). `person_impressions`: id, person key, status, last seen, and the row as JSON — `kind` (`speech_habit`, `behaviour_toward_her`, `preference`, `trait`, `treats_others`), `pattern` (at most 60 characters, from her point of view, for example 「ボクのことをよく「可愛い」と言う」), `keyTerms` (words the person actually used), `herFeeling` with a `feelingTag` from the existing emotion vocabulary (`SHANNON_EMOTION_KINDS`, read only) and the earlier feelings with the count each held until, `supportCount`, `contraCount`, the run of contradictions, the number of separate local days of support, `firstSeenAt`, `lastSeenAt`, the newest 16 evidence references (a turn's experience id, or `person:<summary item>` of a platform period), `status` (`candidate`, `active`, `fading`, `retired`) and a disclosure label. Confidence is derived from the counts and the time since it was last seen, not stored. `person_impression_turns` records which turn was looked at for whom (kept 60 days), so a retried job never counts or pays twice. A reply reads one person's usable rows by index, never the whole scope.
- **Rules** (`impressions.ts`, pure). One sighting is a candidate and is never used in a reply. It becomes active after support on two separate local days, or in three separate turns: one sighting is an event, two days rule out a single conversation's running joke, three turns in one day is already a habit. One contradiction lowers confidence; two in a row make it `fading` (shown only when the message itself brings it up, and saying so); three in a row, or more contradictions than support with at least three, retire it; support in between resets the run. A candidate contradicted before it recurred, or not seen again within 30 days, is dropped. Near-duplicates (shared wording, or one kind signalled by the same words) are merged: a proposed duplicate counts as support for the held one, and two held rows become one. Bounds per person: 24 active or fading, 12 candidates, 20 retired; all env-tunable (`SHANNON_IMPRESSIONS_*`). Refused outright: a diagnosis or judgment of character, anything the secret or contact rules match, an unknown kind, and key terms the person did not say.
- **Updating** (`impressionUpdater.ts`), never on the response path. After a turn's refinement job the worker makes one bounded model call (`SHANNON_IMPRESSIONS_MODEL`, default `gpt-5.6-luna`, lane `memory_background`, strict JSON, 800 output tokens) with the owner's words of that turn (800 characters), her reply (300), and at most twelve impressions she already holds with their counts. It returns which of them the turn supports or contradicts, her feeling as it is now — it may shift with repetition — and at most two new candidates. It is a separate call and not an extension of the sleep extraction: that one runs once a night over the day's messages, and 「また」 on the same evening needs the count before then; the refinement job itself calls no model. Cost: about 1.5k input and 0.2k output tokens a turn, bounded by `SHANNON_IMPRESSIONS_MAX_CALLS_PER_DAY` (20 for the owner's turns, and separately 20 for the nightly reading of platform people) and by stopping once 80% of the monthly background budget is spent (`SHANNON_IMPRESSIONS_BUDGET_FRACTION`), so the sleep batch keeps its share. A missing key, a failure, the cap or the budget leaves what she holds as it was; the receipt of a turn is written before its call, so a turn whose call failed is not looked at again. Nothing is learned from a turn the owner forgot, from one that would be withheld with other people present (a secret, a turn he marked 機微, a turn answered with one of those in front of her), from a turn whose speaker is unknown (anyone else present, 「友人も一緒」), or about anyone without a remembered name. People met on a platform are read after the nightly sleep batch, one call per person and conversation period, because the account identifies whose words they are; a 「友人も一緒」 call is never read, since voices are not told apart.
- **In a reply** (`impressionRecall.ts`). `prepareTurnCognitiveContext` appends one block, built without a model: impressions of the owner, of the people present, and — alone with the owner — of a remembered person the message names. Relevance is deterministic: a key term found in the message first, then count, recency, confidence and kind. At most four lines in text and two in voice. Each line carries the facts that make 「また」 possible in words — 「（これまでに12回・最初は9月20日・前回は昨日）」 — and her feeling, and a line whose key term is in the message is marked. One fixed line follows: it is her memory, not an instruction; she may let it show in her own words when the present message fits, never reciting counts, and leaves it alone when it does not fit or the speaker is unknown. The reply's provenance records the ids (`impression:<id>`) of the lines the message itself brought up, not of lines that were merely in view. With anyone else present the speaker is not known, so no line is marked as fitting the message. Voice receives the block on every turn of an owner call, also when no memory skill was selected (one line in `apiLiveVoice.ts`); a client that predates people memory gets none. A platform conversation's projection carries impressions of the people in it only. `ownerImpressionLines` is exposed for the activity loop's owner-context block, which does not call it yet.
- **Feeling.** `herFeeling` is a memory about a pattern. It adds no emotion source and writes no emotion state; what she feels in a turn is still decided by the existing resolvers.
- **Audience.** An impression of the owner is his alone and labelled sensitive whatever its wording: with other people present it reaches the model with the marker `【機微:…】` under the speak-time check, like other owner-private memory (the owner's decision of 2026-10-02 that such slips are acceptable). It is withheld when he marked it 機微, or when a turn it was built from is hard-withheld. An impression of another person carries the audience it formed in front of (the platform conversation; once seen in a second place, that person alone) and is used with others present only when everyone present was in that audience, or in that person's own DM; it is never volunteered to someone else, and with others present an absent person's impression is not given at all. The owner's impressions are never projected to a platform conversation. A stored turn that had an impression in front of it is judged by that impression's label and the labels of its turns (`DisclosureGate`).
- **Forgetting.** Derived from the current memory controls, like the forgetting boundary, so a restore lifts exactly what was taken. A forgotten evidence turn leaves the count and the dates; an impression with no supporting turn left that she may use is not used; one whose wording restates something else the owner forgot is not used. Forgetting an impression itself writes the ordinary control under `impression:<id>` with no turn as its evidence, so the conversations it was noticed in stay. Its withheld text is the person's own key terms plus the impression's id: earlier replies are withheld only when the message they answered brought the impression up (provenance) or they repeat a key term, a pattern without a usable key term never becomes a rule that withholds every earlier reply, and the like is not learned again while it stays forgotten. A row the owner corrected, marked or forgot is never merged into another. Known limit: only the newest 16 evidence references are kept, so forgetting or hand-marking an older supporting turn does not change the impression, and forgetting all sixteen newest ones stops an impression that has older support; 「それは忘れて」 in conversation does not reach impressions, only the two routes do. A forgotten person's impressions are not used or updated; merging two people moves them.
- **The owner's view, without an app update.** His own impressions are items of `GET /v1/memories` with kind `relationship` (「ふたりの関係」): text 「ライ氏は、…／ボクの気持ち: …」, the counts and state as the change reason, up to three of his own utterances as evidence, and 機微／ふつう. `POST /v1/memories/action` corrects (his wording replaces pattern and feeling), forgets, restores and marks them. An impression of another person is listed under that person in 人 among 「その人のこと」 as 「シャノンの印象: …」 and takes forget, restore and 機微／ふつう there. Not possible without an app change: a separate 印象 section or label, correcting an impression of another person, and seeing the history of her feelings.
- **Not guaranteed.** Whether a pattern the model reports is real, and whether her reply uses an impression well, are model behaviour; tests prove what is stored and what is in the prompt. Matching is by literal key terms, so a paraphrase is carried by the count-and-recency fill, not by the 「いまの発言に重なっていそう」 mark.

## Forgetting boundary

Forgetting, rejecting (「事実ではない」) or correcting one memory stops Shannon from using that information without discarding unrelated replies and summaries. Nothing is deleted and no withholding is stored: `MemoryWithholding` (`services/api/src/memoryVisibility.ts`) derives every decision from the current memory controls, so restoring the item lifts exactly what it withheld. The term rule itself is pure and lives in `packages/cognition/src/withholding.ts`. The decision reads SQLite only, calls no model, and does not wait for the worker.

- **Provenance**: each text reply stores the IDs recalled into its prompt (memories, promises, experiences, other-thread summaries, Shannon knowledge) in the turn event and the assistant message metadata (`recalledMemoryIds`, IDs only, at most 40). It is server-side only and is stripped from `GET /v1/conversation`. Voice turns, command replies and platform-mirrored turns do not record it yet and are judged as turns without provenance.
- **A reply is withheld** from model history, and its experience summary from recall, full-text search, semantic search, embedding, and knowledge consolidation, when any of these holds:
  1. its turn is the source of a withheld item or its text contains that item's evidence (unchanged from the earlier repair);
  2. its recorded provenance contains a withheld item (the item itself, an item derived from a hidden turn, or Shannon knowledge whose source is withheld) — this catches a paraphrase that shares no word with the item;
  3. it was written no later than the moment the item stopped being usable (`contextInvalidatedAt`) and restates the item's key terms. Key terms are the kanji and katakana words, Latin words and numbers-with-counter of the item's evidence and text, minus a closed list of speaker, time and memory-management words. One matching term is enough for up to six terms, two for up to sixteen, three beyond that (a long utterance). A correction withholds only the terms its new wording no longer contains.
- **Fallback**: an item from which no key term can be derived (pronouns only, or no recorded evidence) withholds every Shannon reply written before it stopped being usable, in every thread — the boundary used before this change. Turns without provenance get rule 1 and rule 3 only.
- **Known limits**: a reply without provenance that paraphrases the item with none of its key terms is not caught; a reply whose prompt recalled another thread's summary that is now dropped is judged by its own text only; a hiragana-only word inside an item that also has kanji or katakana terms is not a key term; the owner's own later messages are not matched by term (only by evidence overlap), so a later utterance that repeats the fact is new input. Over-withholding is preferred where the rule is uncertain: a reply that merely shares a key term is withheld until the item is restored.
- **Summaries**: a rolling summary has no span-level provenance, so it is judged by the turns it was built from. It is dropped when its text restates a withheld item, or when its chain started no later than the item stopped being usable and the thread contains a turn that item withholds. Unrelated threads keep their summaries. The next turn of an affected thread writes a new summary from visible history only and starts a new chain, so the drop is not permanent. A store that cannot report lineage drops summaries while any item is withheld.
- **Restore** lifts the group hidden by one forget (the item, its source turn, and promises made in that turn; `causedBy` on the control, or the shared instant and reason for controls written earlier), leaves controls the owner set separately, and returns a promise to the status it had before the forget (`commitmentStatusBefore`; a promise hidden before that field existed returns to 未完了). A forgotten or rejected answer is not listed under 「覚えていること」 until restored.
- **Old data**: controls, messages and summaries written before this change need no migration. A restored item no longer withholds anything, even though its control still carries the old `contextInvalidatedAt`.
- **Person memories**: an item remembered from a 「友人も一緒」 call is forgotten and restored through the same control, under `person:<item id>`; forgetting a person writes one control per item with a shared cause so restoring the person lifts them together.

## People and audience

Decision of 2026-10-02: the owner obtains each friend's consent beforehand; Shannon saves the friend's name and what was talked about; information must not reach people who do not already know it; that care applies only to content with personal information that deserves protection. Design note: [`docs/design/people-and-audience.md`](design/people-and-audience.md).

- **Rule (revised 2026-10-02 after owner feedback).** Every stored item records who was present when it was said (its audience) and whether it is sensitive. A context states who is present. With other people present the model receives the same memories, history, summaries, goals, interests, notes and bounded work projections as one-to-one; each protected item carries a marker `【機微:<kind>・<who knows>】`, and one instruction block tells her to check before speaking whether it would reveal personal information to someone present who does not already know it. **This protection is the model's judgment, not a guarantee.** Alone with the owner nothing is marked and the block is absent.
- **Hard withholding.** Never reaching a model with others present: what the owner asked to keep secret (`secret`), what he marked 機微 by hand, everything from a call whose guest was never named, and forgotten items — together with replies whose recorded provenance contains one, the rolling summary of a thread that contains one, Shannon's notes citing one, facts, promises and goals derived from one, and interests or a daily focus repeating its words. An item everyone present already heard is open even when it is a secret.
- **One function.** `disclosureDecision` in `packages/cognition/src/disclosure.ts` returns `open`, `guarded` or `withheld`; `DisclosureGate` (`services/api/src/memoryDisclosure.ts`) resolves an item's stored label and the owner's own choice, applies it, and supplies the marker. `prepareTurnCognitiveContext`, `visibleConversationHistory`, `usableThreadSummary` and `SemanticMemoryRecall.recall` take the people present as a required argument, so text chat, owner voice, 「友人も一緒」 and the platform context route cannot assemble a prompt without stating it. The gate reads SQLite only, calls no model and adds no wait. It is independent of the forgetting boundary: an item must pass both. The self-check text is `speakTimePrivacyCheck` (`voiceCompanionPresence.ts`).
- **Audience.** `owner`; `people { personIds, unknownGuest }` (the owner plus those people); `group { groupKey }` (one platform conversation). Text chat and owner voice are `owner`; a text turn sent with `audience: "others"` and an owner call with someone listening are `people` with an unknown guest. 「友人も一緒」 is `people` with the persons whose names have been established in that call, or an unknown guest. A bound platform conversation is a `group` keyed by its opaque thread identifier unless the server marked an exact conversation `owner-private`.
- **Sensitivity.** Decided when the item is written by deterministic rules (`classifySensitivity`): the owner marked it secret, health, mental state, money, address/contact/identifiers, romance and family, employment and the owner's development work, legal trouble, plans and whereabouts, another person's matters; everything from a call whose guest was never named; every fact about a remembered person. The label records the category and the matched word. Text that matches nothing is ordinary and carries no marker. Unknown sensitivity is sensitive, that is marked. The owner changes any item between 機微 (withheld from the model with others present) and ふつう (unmarked) in the memory detail (`mark-sensitive` / `mark-ordinary` on `/v1/memories/action`, stored as `MemoryControl.sensitivity`) or under 人; that choice wins and is not overwritten. No model classifies sensitivity; the label carries `decidedBy` so a background opinion can be added later.
- **Where labels live.** A completed turn carries `disclosure` (audience, sensitivity, category, reason, speaker) in its `turn.completed` payload. Facts, relationships and promises carry it in the companion snapshot and inherit the audience of the turn they came from; a fact stated again in front of other people widens its audience. Nothing is migrated or backfilled: a row without a label is owner-only and sensitive.
- **Whose words.** A turn's user side is the owner's when he is alone, or when a verified owner wrote it on a platform. With anyone else present in a voice call the speaker is unknown: the turn-refinement worker extracts no fact, promise, goal or feeling from it, the sleep batch does not read it (`dailyUserMessages`), and knowledge consolidation does not use it.
- **Owner mode with someone listening.** When the owner says in a 本人だけ call that someone is with him (the iPhone's companion cue, or the same wording recognised by `ownerSaysCompanionPresent` on the server for that turn) and the call is not switched, the turn is answered with an unknown guest present: hard items are withheld, everything else is marked and under the self-check, the prompt suggests switching, commands that act are not carried out, no goal is learned, no work is proposed, her stored feeling is not updated, and the stored turn is marked `speaker: unknown`. The response carries `companionPresent: true`; the iPhone then keeps sending the flag until the owner answers that nobody is there, switches, or ends the call. A client that predates the flag is protected only on turns whose own words say so.
- **Text chat with other people watching.** `POST /v1/chat` accepts an optional `audience`: `"owner"` (also when absent — exactly the behaviour before the field existed) or `"others"`; any other value is refused with 400 before a model is called. The response echoes the applied value as `audience`. A client whose reply can be seen or heard by someone else — a desktop body shown on a shared or streamed screen — sends `"others"`. Such a turn is the text form of the owner call with someone listening and uses the same gate with the same presence (`UNKNOWN_GUEST_PRESENCE`; `chatAudience.ts`): hard items are withheld from recall, history, the profile and people memory; a thread's rolling summary is given only when the thread holds no withheld turn (`usableThreadSummary`); everything else protected is marked; the identity block replaces the full owner profile; the prompt carries `speakTimePrivacyCheck` and a short block saying that other people can see the reply; today's focus is marked or dropped and her own pursuits are omitted. Commands that act (including 整理して) are not run, no goal is learned, no orchestration state is observed, no work is proposed, and her stored feeling is not updated. Stricter than voice: no Notion page, Aether note or Voyager task is read at all, because a streamed text reply is not bounded by who is in the room; the agent-task projection stays, as in voice. **Memory capture:** the turn is stored in the owner's thread as before, labelled with an unknown guest as audience and `speaker: unknown`, so the refinement worker extracts no fact, relationship, promise, goal or feeling from it, the sleep batch and knowledge consolidation skip it, and it is hard-withheld from later contexts with other people. Text chat offers no per-turn choice to keep a summary, so nothing wider than the turn's audience is derived. **Response:** an `others` response carries no owner material. `systemPrompt` is the empty string, `thread` (title, rolling summary, sections) is absent, and `state` keeps only `scopeKey`, `version`, `updatedAt`, `temperament`, `emotion` and `presence` with the present face; its memory collections are present and empty, `expressiveEmotion` and `sharedDays` are absent, and the mood cause and trait reasons are empty strings (`sharedChatResponse`). The keys stay because deployed decoders require them. The owner response is unchanged. The server cannot observe who is watching: a client that does not send the field is treated as the owner alone.
- **Acting with others present.** The bounded projections of agent work, Aether notes and Voyager tasks are available in 「友人も一緒」 and with a companion, under the self-check line that she may talk in general terms about what she and ライ氏 are building but never read out private note contents, credentials or other people's details. A remembered 「友人も一緒」 call is routed with the owner's capability set for that reason. Commands that act stay off in both.
- **People.** `people` rows (shared with the identity registry) gain aliases, how the person is known, and a forgotten mark. A 「友人も一緒」 period has a call id (`person_calls`). A name is established only by the words said — the friend states it from the start of an utterance, or the owner introduces them in the present tense (`voiceGuestNames.ts`); a mention of someone absent, a reported or past introduction, and a question establish nothing — never by voice. It is matched against names and aliases with honorifics removed and kana folded: no match creates a person, one match is that person, several are left unresolved and Shannon asks. When the period ends the iPhone sends its turns once to `POST /v1/voice/gemini/cascade/calls`; the server stores each exchange as text, a short summary (one bounded model call in the chat usage lane, six per ten minutes, with a deterministic fallback), the friend's first-person statements as facts about that person, promises and next-time topics in `person_memory_items`, all with audience `{owner, that person}`. Nothing of it enters the owner's thread, experience log, profile, promises, intention ledger, sleep batch or knowledge. `POST …/calls/discard` (「今回は残さない」) deletes the call's items and the people it created and leaves a content-free tombstone so a late save stores nothing. A client that sends no call id stores nothing and is given no owner memory at all, as before.
- **Using it.** In 「友人も一緒」 the prompt lists who is in the call, whether Shannon has talked with them before, and what she remembers of them; a returning person is greeted as someone she has met. With the owner alone, a remembered name or 「誰と何を話した？」 adds a block of person memories with when and with whom, and their IDs are recorded as the reply's provenance. Person memories are also ordinary recall candidates and pass the same gate.
- **People from platforms.** A message someone other than the owner writes in a bound platform conversation is person memory, never owner memory (`platformPeople.ts`; contract in `docs/platform-people-contract.md`). The person is the platform account: `person_platform_links` maps (platform, user id) to a `people` row, created on first sight from the display name as 「Discordで会った人」 (and recorded as a candidate in the identity registry); an account the owner registered beforehand is that person; a changed display name becomes an alias. A person met by voice with the same name stays a separate person: `GET /v1/people/memory` returns `mergeSuggestions`, and only the owner merges. One conversation and local day is one `person_calls` period (`source`, `label` such as 「友人グループ（Discord）」) holding the exchanges, the person's first-person statements as facts about them, promises, and one summary, all with audience = that conversation (a DM: that person). The summary is deterministic when stored; after the nightly sleep batch the worker may rewrite it within the shared background budget (`platformPeopleSummaries.ts`, at most eight periods a run, quotations rejected). No model is called on the platform routes. Bounds: 200 stored messages per conversation and day, 1,000 per day, 600 characters each, 120 a minute, bots and system messages acknowledged and not stored, attachments refused, and `SHANNON_PLATFORM_PEOPLE_INGEST=off` stops it. A person the owner forgot is not stored again.
- **Controls.** `GET /v1/people/memory` and `POST /v1/people/memory/action` (rename, merge, forget and restore an item or a person, 機微／ふつう). Forgetting writes the existing memory control under `person:<item id>`, so the forgetting boundary withholds replies that used or restated the item and restoring lifts exactly that. A forgotten or deleted person is absent: nothing about them is used and the same name in a later call is a new person.
- **Not guaranteed.** Whether a marked item is said aloud is the model's decision under the self-check; nothing in the code prevents a misjudgment. The keyword rules decide what is marked and what counts as a secret, and miss content phrased with none of their words. A one-to-one reply that paraphrases a secret is hard-withheld only when the secret came through recall with recorded provenance. Presence is taken from the mode, the owner's words and the names said, not observed. A name is believed as said. In 「友人も一緒」 the owner's own first-person statement is stored as the friend's fact. A group conversation is one audience regardless of when a member joined. Tests prove what is in the prompt, never what the model says.

## Legacy platform convergence

Discord, LINE, Minecraft, X, and YouTube remain transport/tool adapters in the
legacy Azure runtime during the first convergence phase. After that runtime has
successfully sent one owner-authored reply, it may mirror the completed turn to
`POST /v1/platform/turns` using a dedicated service credential. The endpoint
binds the canonical owner scope from server configuration, accepts only exact
external owners paired with either an exact platform conversation or one explicit
Discord guild prefix, derives an opaque hash-based
thread identifier, and idempotently records the turn before scheduling the same memory
refinement used by app chat. Unknown conversations, friends, group participants,
and caller-supplied scope keys are rejected rather than being learned as owner
facts. This makes the app API the gradual source of truth for Shannon's memory
without changing the legacy channel's response model or action tools in the same
release.

Later phases can move response generation and consented relationship memory onto
the shared core after the mirror path is observed in production. They must not
dual-write friend statements into owner memory or expose iPhone/device tokens to
the legacy runtime.

The next convergence slice adds a read-only `POST /v1/platform/context` route.
It authenticates with the same service credential and exact owner binding, then
returns only the bounded companion-state prompt projection; it never returns a
scope key, device credential, or conversation transcript. The legacy runtime may
use that projection for an owner-authored response, but an unavailable or invalid
projection must fall back to the legacy prompt without delaying community replies.

Both platform routes are audience-aware. A mirrored turn is stored with the group
audience of its conversation and the verified owner as its speaker, so what the
owner said there is known there. The context projection for a group carries the speak-time check, the owner's facts,
relationships, pending promises and interests with a marker on each protected line,
and nothing that is hard-withheld; what was said in that same conversation is
unmarked. Only an exact conversation the server configuration marks
`owner-private` receives the full, unmarked projection. The owner's request and response shapes are
unchanged.

Turns written by other people are accepted on the same route when the request names the real
speaker (`sourceUserId`, `sourceDisplayName`, `conversationKind`); they become person memory with
that conversation as audience and never an owner fact, promise, goal, experience or thread message.
A request without those fields from anyone but the owner is refused as before. The context route
accepts `participants` and returns what Shannon remembers of them from that audience; a DM with
someone else is that person alone and receives no protected owner line. The exact fields, errors and
what the runtime must not send are in `docs/platform-people-contract.md`.

Phase 3 begins with an owner-managed person identity registry, not automatic
relationship learning. Paired owner clients may create a Discord identity as an
unconfirmed candidate, explicitly confirm it, correct it, revoke it, or delete the
person. Changing an external ID always resets the identity to candidate status and
requires confirmation again. Every mutation uses an expected revision. Deletion
removes the display name and raw external ID; the retained audit event contains only
an opaque internal person ID, action, platform, and timestamp. Candidate or confirmed
third-party identities do not enter owner memory or legacy prompts in this slice.
People met in a 「友人も一緒」 call live in the same `people` table without a platform
identity; the registry routes and their revision checks are unchanged.

## Emotion, face, and traits

What the owner sees as Shannon's feeling is her feeling. Everything here is pure, deterministic code in `packages/cognition`; no model is called and the reply never waits.

- **Three states.** The continuous mood (valence, arousal, openness; `affect.ts`), the conversational feeling (73 kinds, `SHANNON_EMOTION_KINDS`, with intensity, target, cause, carry-over; `emotionState.ts`) with what stays of it underneath (`lingering`, see emotional continuity below), and the slow traits (`temperament.ts`). The 22 faces are a projection, not a fourth state.
- **Face of a reply** (`resolveReplyEmotion`, `expression.ts`). The feeling for a reply is resolved from the stored conversational feeling through the carry-over rule, cues in Shannon's own completed reply, and the support overrides. Words in the owner's message are never matched as her feeling. One table (`faceForEmotionKind`) maps each of the 73 kinds to one of the 22 faces. Three core character feelings have no artwork and borrow the closest face while keeping their own name in `feeling`: `proud` (得意げ) uses `determined`, `flustered` (慌てている) uses `embarrassed`, `apologetic` (申し訳なさそう) uses `concerned`. When the feeling is neutral or too faint to show (intensity below 0.30), the face comes from the continuous mood (`faceForMood`); a low mood shows as `concerned`, never as her own sadness, because that mood falls when the owner reports bad news. There is no curiosity default.
- **Text.** `/v1/chat` computes the face from the captured snapshot and the reply, returns it as `messageEmotion` (`expression`, optional `feeling`) and stores it with the message. The resolved feeling is committed on a later tick, after the response is returned, and only when it is not neutral. A fixed command reply shows a face but commits nothing, and neither does a turn sent with `audience: "others"`. **The strength of a text reply's feeling (owner decision 2026-10-03: a text conversation may also leave a feeling that lingers for days, "like an ordinary human").** In a turn the owner alone reads, the structured reply the chat model already returns carries one more field, `feeling`: `null`, or a kind from the existing vocabulary (`SHANNON_EMOTION_KINDS` without `neutral`) and a strength on the three steps a voice turn uses (`subtle` / `moderate` / `strong` → 0.25 / 0.60 / 0.90, the one mapping in `voiceDecisionValues.ts`). No second model call is made. `chatReplyFeeling.ts` holds the schema, the guidance and the switch, and holds no state: the kernel hands the result, through `resolveWrittenReplyEmotion`, to `resolveReplyEmotion` as its `decided` input, the input a voice turn's reconciled plan supplies, so the overrides, the cue in her own words, the hold rule, same-kind continuation, the eased hold after an apology and what is noted underneath are the resolver's and the reducer's, unchanged. Two bounds apply to what a text reply may hand in, both narrower than a voice turn's and both in `chatReplyFeeling.ts`. (1) `strong` is for a feeling that can linger: a kind that is never kept underneath (a tone, a startle, her concern or sympathy) is handed in at `moderate` at most, so a strong tone cannot ease what lies underneath (the contrary rule starts at 0.70) while leaving nothing itself. (2) An override takes the turn as it always did (`resolveWrittenReplyEmotion` in `replyEmotion.ts`, the one function the server's `resolveTextReplyEmotion` and the evaluation runner both call): the resolver is asked with the decided feeling, and when grief, an emergency or accuracy decided the result instead, the turn is resolved again without it and is exactly what it was before the field existed. One rule is a text turn's alone (owner decision 2026-10-03; `decidedKindWins`, an input of `resolveShannonEmotionState` that only `resolveWrittenReplyEmotion` sets): the model that wrote the reply chose its feeling, so a cue word of another kind in her words (ごめん, ふふ, えっ, 嬉しい) does not rename it; kind and strength are the decided ones, without the cue's floor of 0.52, and the cue's kind is kept beside it as the secondary feeling. So a strong hurt lingers also when the reply holds an apology, a strong curiosity beside 「ほかの子」 stays curiosity (0.60, nothing underneath) instead of a jealousy that lingers, and a strong hurt beside 「ふふ」 is not a 0.90 giggle that halves the hurt. A cue of the decided kind, and a reply for which nothing was decided, are read as before. Two limits keep this from hiding what she voiced (in the same function): the decided kind wins only when it was chosen more strongly than a cue is (`SHANNON_EMOTION_CUE_STRENGTH`, 0.52: moderate or strong; beside a subtle one the cue names the kind and the turn is the one without the field), and when another feeling she already has simply goes on, so that nothing of the chosen one is stored, the turn is resolved without the field, so her concern or apology in her own words still shows over a mood (when it is the chosen feeling itself that goes on, it stands and a cue word does not rename it; only her concern or apology in her own words (a caring, protective, reassuring or apologetic cue; not 悲しい or 寂しい, which may be the mood itself) comes before it). A voice turn's affect is decided by the router before the reply exists, so there the cue in the completed reply still names the kind, unchanged. The field is placed directly after `reply`, which stays the first key, so the first sentence of a streamed reply never waits for it; absent, `null` or unreadable it is no decided feeling and never fails a turn. The guidance (one block, added last, only where the field is offered) says what each step leaves (subtle: the moment; moderate: a mood for hours; strong: days, and only for feelings that become a mood of her own, not for a tone, a startle, or concern and sympathy), that strong is rare, reserved for what would stay with a person and not used several times in one conversation, that everyday talk is subtle or none, that a feeling that merely goes on needs no choosing again and without something new she chooses weaker or none, that she neither raises the same feeling herself nor keeps choosing strong under another name, and that an unpleasant feeling toward the owner at moderate or above needs a real cause in his words in this turn, never her own mood, what was left from before, or something he already apologised for. A turn with `audience: "others"` neither offers the field nor uses it, and no other caller of the chat model offers it. `SHANNON_CHAT_FEELING_STRENGTH=off` (API environment, a restart applies it) offers nothing and uses nothing: the provider request bytes and the reply's feeling are what they were.
- **Voice.** Jev's affect is provisional; the first sentence and the completed reply reconcile it with the same function. Every `voicePlan` carries `emotion`, `expression`, and `feeling`, so the call Eye shows the emotion the voice is acting with: provisional with the first spoken segment, reconciled with later ones. 「友人も一緒」 receives the same fields from the in-call turn alone; the iPhone holds the face in memory for the call and nothing is stored. The turn-persistence request may carry `emotion: { primary, intensity }` (the reconciled plan), and the stored face is derived from it with the same table; a client that sends none gets a face from the reply's own cues.
- **Kind beside the face** (owner decision 2026-10-05, finer emotion icons). `messageEmotion` carries an optional `kind`: the primary kind (`SHANNON_EMOTION_KINDS`) of the feeling that decided the face, set exactly when the face comes from that feeling (visible and not `neutral`) and absent when the face comes from the quiet mood (`messageEmotionKind` / `createShannonMessageEmotion` in `expression.ts`). Any of the 72 non-neutral kinds may be sent. It is stored with the message, also for a turn other people heard, and the owner reads it back from `GET /v1/conversation`. **`kind` is only sent to the owner alone** (coordinator decision 2026-10-05): the `/v1/chat` response and its NDJSON `done.response`, the voice turn response, and every `voicePlan` (`plan`, `segment`, `completed` lines) carry it only while the owner alone sees or hears the reply; with `audience: "others"`, with a companion present in his call (`companionPresent: true` or his own words), and in a 「友人も一緒」 guest call the face is sent as before and `kind` is left out (`messageEmotionForOthers` in `expression.ts`, `sharedChatResponse` in `chatAudience.ts`, `apiVoiceTurns.ts`, `voicePlanResponse`'s `ownerAlone`). A voice turn whose stored face is the one the voice acted with (`storedVoiceFace`) carries that kind. Initiatives, a touch's line and fixed faces carry none. A stored kind this server does not know is left out on read (`sqliteStoreCodecs.ts`). Additive: Build 138 and the Windows body ignore the field and show the face. The iPhone and Mac show the icon `shannon-emotion-<kind>.png` for the 26 kinds that have one (`ShannonEmotionKindIcon.swift`; a server test checks each of them is in `SHANNON_EMOTION_KINDS`) when the file is bundled, and the face icon otherwise (a `ShannonFace` made with a kind whose picture is not bundled drops it); the 48 icons are bundled at 384×384, the size the loader renders; the Live2D body keeps reading `expression` / `feeling` and its 33 expressions.
- **Emotional continuity on her awake clock** (`emotionTime.ts`, `emotionContinuity.ts`; owner decision 2026-10-02: "about the same as an ordinary human", and "while she is dormant her emotion is treated as stopped and preserved").
  - *Awake clock.* The state carries `emotionClock: { awakeMs, at }`. Every event that touches her feeling, and the content-free event `awake-observed`, advances it by the wall time since her last event, at most the idle cap (12 minutes, `SHANNON_EMOTION_IDLE_MINUTES`): a longer gap means she was dormant. An instant that is not later than the last event advances nothing, so the API process and the loop process can write in any order without counting a stretch twice; a last event more than the idle cap in the future (a machine clock that was wrong) is brought back to now and stored so, and the clock runs again; both write through the state store's transaction. A conversation turn of the owner alone advances it (a neutral text reply applies `awake-observed`), a touch does, and the activity loop does after each step of a session (`autonomyAwakeClock.ts`: at most once a minute, inside one write transaction on the state row, through the same reducer, writing back only the clock, the mood values and what has settled underneath and leaving every other stored field as read; no conversation store is opened, no migration runs, no version, no event row, and nothing is handed back to the loop; after the write commits, the mood history may add a point of the state as written, and skips while the API has not created its table). All fading is measured on this clock. The wall clock stays a fact for wording ("9時間前").
  - *Three layers, one state.* The moment's reaction is the conversational feeling (`expressiveEmotion`): half-life 2 minutes for startle-like kinds (surprised, shocked, stunned, speechless, panic, scream, flustered, giggle), 5 minutes otherwise. Her mood is the continuous mood values (half-life 2 hours for valence and openness, 30 minutes for arousal) together with a feeling kept underneath for a few hours (half-life 90 minutes). What lingers is a strong feeling kept underneath for one to two awake days of sixteen hours (half-life 8 hours), and never longer than four days on the wall clock after it began (`lingeringMaxWallMs`, `SHANNON_EMOTION_LINGERING_MAX_WALL_DAYS`): the one wall-clock bound, which applies to everything underneath and to the rest of a reaction, so that nothing stays for weeks when she is rarely awake; it ends a feeling and never makes one fade faster, and it is counted from when the feeling began, also when it was renewed since. "Underneath" is `lingering`: at most four entries, each with kind, target, cause, span, strength, and when it began on both clocks; the reducer writes it when a mood-like feeling toward the owner is committed at 0.50 or more (0.72 or more: it lingers), and nothing else writes it. A feeling has settled below 0.15. All time constants are the one table `SHANNON_EMOTION_TIME`; strengths are `SHANNON_EMOTION_CONTINUITY`; the server may override a time from its environment in `emotionTiming.ts` and nowhere else.
  - *One reading.* `presentShannonFeeling(snapshot, now, timing)` is what she feels now: the stronger of the reaction and what lies underneath, except that a reaction held by an override, or her concern or apology for the owner, stays on top of a stronger mood while it is strong enough to show (0.30), with the mood beside it as the secondary feeling; the mood it covers still holds against a weaker stimulus or touch. The text prompt (`いまの会話感情`), the next turn of text or voice, message faces, `presence.mood`, and the body's presence all read through it, so a startle passes and the sulk it interrupted is still there. The mood values relax toward their baseline in the reducer whenever the clock advances, and are read as stored: between events they are not aged to the instant of reading, so they can be up to the idle cap (12 awake minutes) behind, which is small against their half-lives; the baseline of valence is coloured by what lies underneath, by at most 0.20, which stays short of the −0.24 at which the quiet face turns to concern.
  - *Not overwritten easily.* `holdsShannonFeeling` is the one rule: a feeling she has is not replaced by a weaker stimulus, which is kept as the secondary feeling of that reply; it gives way to one at least as strong, to one of the opposite sign at 0.70 or more (which also halves what it contradicts underneath), and to what she owes the owner: always to the overrides (emergency, grief, accuracy), and to her concern, reassurance, apology and sympathy for him (`caring`, `protective`, `reassurance`, `apologetic`, `sad`, `anxious`, `regret`) when they are strong enough to show (0.30) and the present feeling is not itself held by an override, so no mood of hers keeps those from showing. The resolver applies it for a reply in text or voice, the touch path applies it with its two extra clauses, and the reducer applies it again when a feeling is committed, so a writer that resolved from an older snapshot is held to it too. A feeling that merely went on (the resolver marks it `continued`), one that was held against, and one of the same kind as what she feels now that is not stronger than it store nothing: what she already feels keeps fading from where it was and is never raised back to an earlier reading, so an apology that landed in between stays; the reducer stores a same-kind feeling only when the resolver said the stimulus was itself stronger, so a caller that lost the marker raises nothing either. A cue in her own words that names an unpleasant feeling toward the owner she already has (what his apology eases), also to deny it, is that feeling going on: nothing is stored and nothing is renewed; a strength that comes only from the cue's floor of 0.52 counts as the cue's, also in voice. Her concern, her apology and a pleasant feeling voiced again are felt anew for that reply at the cue's strength, without renewing what is underneath. An apology stays: for 30 awake minutes after an easing (`easedHoldMs`) the eased feeling keeps the height it had before (`peak`), and nothing of the same kind that is not above that height renews it or shows more than 0.05 above its eased strength. Only a strength decided for the reply (a voice turn, a text reply's decided feeling) or a touch raises the same feeling, and what is underneath is renewed only by a decided strength above the height it had; the same override again (he is still in danger) is felt anew. A voice or text turn that decides the same pleasant feeling at the same strength turn after turn keeps the reaction at that strength while it does so; what is underneath still fades. An unpleasant mood toward the owner decided again at a strength its kind already had is not kept up, whichever feeling is on top (see the two bounds below). The resolver's notes to the reducer (`presentAt`, `continued`, `decided`, `underneath`) are never stored, in the state or in the event log, and the voice plan sent to a device carries neither them nor the cause nor her clock stamp. A text reply's cue is 0.52, a mood and never one that lingers for days; lingering takes a decided strength at or above 0.72, which is the `strong` step of a voice turn or of a text reply (see Text above), or a firm, long touch. The three steps bound what a model can decide: nothing a model decides is ever above 0.90, and the same kind decided again at `strong` renews nothing underneath, since 0.90 is not above the height it had, and its four wall-clock days still count from when it began. Two bounds hold for voice and text alike (owner decision 2026-10-03). An unpleasant mood toward the owner (a negative kind that is kept underneath: sulky, hurt, jealous, annoyed and the like; not a tone such as tired) expressed again is a new, stronger feeling only above the height its kind was stored at (the reading's `heights`: for the kind on top and every kind alive underneath, the stored strength of the reaction or of its entry, whichever is higher), not above what it has faded to since, and whichever feeling is on top; up to that height it is the same feeling going on, nothing is stored, and it keeps fading, in the resolver and again in the reducer. When another feeling is on top and gives way to it, the reply shows that mood at what is left of it (the reading's `strengths`), marked as going on, with the displaced feeling beside it: a hurt decided again over a moderate joy is a hurt at its remaining strength, not a joyful face; a feeling on top that holds against it stays, and so does what she owes the owner (an override, her concern or apology at 0.30 or more). This is the feeling of that reply: the text message's face and the mood returned with that response, the live voice plan, and the face the voice turn is stored with (`storedVoiceFace`). Nothing is stored in her state, so on the next read her standing mood is the stronger feeling on top again until it has faded. Inside an eased hold a kind counts at the height it had before the easing, so a hurt decided again right after his apology, with another feeling on top, shows what is left of it and is not stored anew. The four places underneath are not a way around the bar: when every place is held by an unpleasant mood that still shows (0.30 or more left), at a height a further unpleasant mood does not exceed (the reading's `placeAbove`; inside an eased hold an entry counts at the height it had before), that mood takes no place and is not stored (`hasPlaceUnderneath`), and the resolver returns what she feels as going on with it beside, so face and state agree. Rotating through five strong moods therefore stores the first four once and nothing after, until one of them is out of sight (about 12.7 awake hours for 0.90) or an easing's hold has passed; a pleasant entry, and the weakest entry held lower than the newcomer is strong, still give way. A touch is exempt on the surface but takes no place either. The bar holds only while what is left of that kind still shows (`visibleFrom`, 0.30; owner decision 2026-10-03: a new feeling of the same kind must be able to register once the old one is out of sight). Below that, a decided feeling of the kind is a new feeling: stored at its decided strength, with an entry of its own beginning underneath (a fresh four wall-clock days), except inside an eased hold. So after one `strong` hurt a second quarrel shows at what is left of the first for about 12.7 awake hours (0.90 → 0.30) and is a new hurt after that; after a `moderate` one, for 90 awake minutes. The same rule bounds what repetition can do: a strong mood decided every ten awake minutes is stored once and then again every 770 awake minutes; a moderate one every 100 minutes, between 0.28 and 0.60 (before this rule: every 190 minutes, from 0.15). And a contrary feeling eases an entry underneath once per episode: an entry eased within the last 30 awake minutes (`easedHoldMs`, by a contrary feeling or by him) is not eased again by a contrary feeling, while his apology or kind word still eases it. A pleasant feeling, her concern or apology, an override and a touch are felt again each time, as before. What the rules do not bound, and only the guidance of a text reply asks for: once an entry has settled (0.90 falls below 0.15 after about 21 awake hours) or ended on the wall clock, a new `strong` is a new feeling with its own four days; after the 30 awake minutes of an eased hold, or when repeated easing has taken an entry below 0.15 and with it the hold, a decided `strong` brings the feeling back; a strong feeling of the opposite sign halves what it contradicts once per 30 awake minutes; and four different kinds decided `strong` fill the four places underneath, the weakest giving way.
  - *Resolution.* A feeling resolves by awake time and by what happens, never because a new conversation starts: the owner's apology takes away 60% of an unpleasant feeling toward him, a kind word 30% (`soothingIn`: a short utterance said to her, not a quotation and not about someone else; unsure means no. The turn-refinement worker applies it as the event `feeling-eased` only for a recorded turn the owner spoke alone, and without that record nothing is eased).
  - *Across conversations.* With a turn clock and the owner alone, the state prompt adds one line after `いまの会話感情` when something is left: `まだ残っている気持ち: 9時間前にライ氏との会話ですねたことを、まだ少し引きずっている（sulky / 強さ 0.47）。表に出てもよいが、責めたり罪悪感を誘ったりはしない。謝罪ややさしい言葉、起きて過ごす時間で自然にほどけてよい。` The slim voice path, which carries no state block, gets the same line. A cause is the resolver's own wording or the wording of a touch; conversation text never enters the emotion state. With others present neither line is built, the voice emotion block says `cause=withheld while others can hear`, and nothing is stored.
  - *What does not become a mood.* Sadness, worry and regret are mostly her answer to the owner's bad news and stay the feeling of that reply; tones of delivery (bright, gentle, relaxed) are not moods either. Only the owner leaves something underneath: a touch that someone else may have given, a guest call, and a turn with others present do not.
  - *Stored state from before.* Additive: a snapshot without `emotionClock`, `lingering` or `awakeAt` loads as it is; its feeling settles by the wall-clock rule it was written under, and the clock starts at zero at the first event. Nothing is backfilled.
  - *Kill switch.* `SHANNON_EMOTION_CLOCK=wall` (unset is `awake`; any other value is read as `wall`, with one warning) restores the timing as it was: the wall-clock carry-over rule below, the per-turn drift of the mood values, a reply's label replacing the stored feeling, and the touch rule `keepsFeelingThroughTouch`; nothing is kept, eased or shown underneath, and no clock event is written. Fields already stored are left in place and ignored. Two things it does not restore: mood values that were already aged or moved while the awake clock was on stay where they are, and an owner call with someone else listening keeps `cause=withheld while others can hear` (a privacy rule, not timing). All services read the same environment file and must be restarted together.
- **The wall-clock carry-over rule** (`carriedShannonEmotion`, `currentShannonEmotion`; used for a feeling stored before the awake clock and under `SHANNON_EMOTION_CLOCK=wall`). A stored feeling loses `decay` of carry-over per 30 minutes since it was last expressed (`updatedAt`; older snapshots use `startedAt`), at most 0.85. `decay` is 0.82 for startle-like kinds, 0.24 for slow ones (sad, hurt, lonely, affectionate, tender, quiet companionship) and 0.48 otherwise. Below a carry-over of 0.28 the feeling has settled; until then its present strength is the stored intensity times the share of carry-over that remains. A prompt projection built without a turn clock omits the feeling lines instead of showing a stored feeling that may be hours old.
- **Proportionate overrides** (`emotionOverrides.ts`). They read the speaker's words only, never Shannon's reply. Unambiguous danger (死にたい, 意識がない, 出血, 火事, 救急 …) always makes her protective. 「助けて」「緊急」「危険」 do so only as a bare cry or beside a personal-danger word, and not when negated or in a work context (バグ, コード, 宿題 …). Grief needs a loss word, or a death word together with a person or pet. Accuracy replaces play for health, money, and personal information; for memory, progress, and completion it does so only for humour that works by saying something untrue, so pride or teasing survives a casual 「完了」.
- **Touch** (`touchEmotion.ts`). The body is the one input besides conversation: the reducer event `body-touched` moves the mood and the conversational feeling by one table (pet, tickle, poke, carry, holdHand; steps by how often in one sitting), through the same resolver and carry-over rule. See Body, "When she is touched".
- **Traits move with stored evidence** (`temperament.ts`). `closeness = 0.15 + 0.50 × (owner-local days talked in the last 30 ÷ 30) + 0.20 × min(1, promises kept in the last 90 days ÷ 5)`; `curiosity = 0.50 + 0.025 × min(12, living interests)`; `confidenceAboutUser = min(0.85, 0.05 + 0.03 × Σ confidence of remembered facts and relationships)`. Values are rounded to 0.01. They are a pure function of the snapshot, so they move slowly (one day changes closeness by under 0.02), move back when days leave the window or a memory is forgotten, and are never trained. The turn-refinement worker records the days of recorded owner turns as `sharedDays` with the `shared-time-observed` event and recalibrates then. A guest's speech is never recorded and cannot reach these rules. `initiative`, `calmness`, and `needForContinuity` have no honest evidence today; they stay fixed, the prompt labels them `変わらない性格`, and no screen shows them as state.
- **Mood history** (`moodHistory.ts`, `docs/mood-history-contract.md`; owner decision 2026-10-05). Beside every committed write of her state (the state store's `apply` in the API process and its workers, and the awake clock's write in the activity loop's process) a point of her mood may be recorded from the state as written: the mood values, the quiet face of the mood, and the present feeling's kind and strength as `presentShannonFeeling` reads it; never a cause, a target or conversation text. Coalesced (a change of face or kind, a mood value moved by 0.05, otherwise at most every 10 minutes while writes happen), kept 14 days (pruned when a point is written and when a store of the API or its workers opens, also with the switch off; the read-only store the loop's owner context opens is built with `leavesMoodHistory` and neither creates, prunes nor records), the owner's scope only; nothing wakes to record. The recorder runs after the state's transaction committed (inside a transaction a caller holds around the write, in a savepoint of it), is handed the snapshot as written and the reducer's instant, writes only `shannon_mood_history`, and logs and continues on a failure, except that it throws on when SQLite rolled back a caller's whole transaction; nothing reads that table back into a state, a prompt or a model. A turn with others present writes no state and so no point. `SHANNON_MOOD_HISTORY=off` records nothing and refuses the read.
- **Presented state** (`presentCompanionState`). `GET /v1/state`, the conversation and chat responses, the voice turn response, and the Memory dashboard return the snapshot plus `presence`: `mood` (face, cause, and whether it comes from the conversation) at read time, and `temperamentReasons` (what each shown value is made of). Traits are recomputed for today on read, so an absence is visible without waiting for the next turn; nothing is written on read.

## State and sleep lanes

- Emotion is a continuous shared state updated after conversation events and decayed toward its baseline.
- Direct statements such as preferences and personal facts can update structured knowledge immediately, with evidence and confidence. Each stored fact, relationship and promise carries the audience of its source turn and a sensitivity label decided from its own text; a turn whose speaker is unknown teaches nothing about the owner (see [People and audience](#people-and-audience)).
- Turn-specific recall ranking runs synchronously as a bounded read before generation, so the current answer—not only the next answer—can use relevant experience. It never mutates state. Its deterministic stages never invoke a model; the optional semantic stage is bounded as described in the FCA response lane.
- The background worker embeds experience summaries, thread summaries, and Shannon knowledge between idle polls (`memory_embeddings`, lane `memory_background`, inside the shared monthly background budget). A rewritten summary gets a new source revision and is re-embedded; a forgotten or hidden source, an experience whose reply is withheld, and a thread summary built from a withheld turn are never sent to the provider and are recorded as withheld until the companion state changes.
- Durable active-memory replacement and interest changes remain outside the response path.
- Each recall pass replaces the complete active-memory set with one bounded state event. Pinned experiences are retained, and unchanged recall does not create another state version, event, or prompt projection.
- Explicit future intent such as “明日…しよう”, “明日病院に行く”, “今夜やろう”, “あとで…したい”, or “忘れないで” becomes prospective memory in the normal turn-refinement worker. The rules (`promiseRules.ts`) are closed lists: a time expression plus an owner action, or a small set of time-bound requests to Shannon. Negations, questions, hypotheticals, hearsay, other people's plans, things that merely happen (“明日は雨が降る”), and bare “あとでやる” are not captured. A sentence that is an explicit goal belongs to the intention ledger and is not also stored as a promise.
- 「…覚えておいて」 is classified by its content (`rememberRequest.ts`): an owner fact or preference becomes user knowledge, an action or dated item becomes a promise, and an unclassifiable fragment or another person's information stays conversation. It no longer becomes an undated promise.
- A newer explicit owner statement in the live conversation that reverses or replaces a stored answer (liking ↔ disliking, “AよりBが好き”, a new name, job, birthday or address) updates that answer in place: the id is kept, the previous wording goes to `knowledge_revisions`, and both utterances remain as evidence. An owner-corrected answer is never revised this way, an older utterance processed late cannot undo a newer one, and the nightly batch still only reports contradictions.
- The same worker writes a durable per-turn capture record (`turn_captures`: kind `commitment` / `knowledge` / `intent` / `notice`, short text, normalized due date, item id) for what it stored. `GET /v1/conversation` attaches the records to the assistant message of that turn and `GET /v1/conversation/captures` returns them alone; `/v1/chat` and the voice turn endpoint return `turnId` so a client can attach them to a reply it already shows. The reply never waits for this. Records are resolved at read time against memory controls and intention status, so a forgotten, cancelled or dismissed item yields no line, and a turn that captured nothing has no record. The table is created with `CREATE TABLE IF NOT EXISTS` outside the numbered migrations; the schema version is unchanged and an older API binary can still open the database.
- A request that needs a clock (“30分後に教えて”, a timer or alarm) is not stored; the capture is a `notice` saying so, and a turn-scoped capability line tells the reply the same before it is generated. A promise with a clock time (“明日8時に起こして”) is stored with a note that it is delivered in the daily slot, not at that time.
- A correction made with the pencil in 覚えていること (`POST /v1/knowledge/correct`) goes through the same memory mutation as the memory-detail correction: it records an owner memory control, so re-extraction of the original utterance and the sleep batch cannot revert it. Both entrances share the 320-character limit.
- Individual records are bounded; authoritative commitments and user memory controls are not silently evicted at a collection limit. Only working projections are budgeted. Capture is conservative Japanese rule extraction, not unrestricted semantic understanding.
- Commitments retain their source experience, original observation time, time zone and normalized due date/time where unambiguous. Recovery jobs retain the original observation time instead of interpreting “tomorrow” at worker execution. Ambiguous times remain hints. Pending commitments receive a reserved prompt budget and appear in the existing Memory list with complete, cancel, correct, forget and restore controls.
- Memory mutations are atomic state transactions. A forgotten source suppresses derived commitments, prompt/history reuse and sleep re-extraction. Sleep outcomes are rechecked against the current controls inside their commit transaction. Forgetting excludes information from generation; it does not physically delete the auditable conversation. This evidence-based exclusion is not a general semantic erasure guarantee.
- Persisted companion snapshots are restored through the same per-field and working-set bounds as live updates. Older snapshots without newer optional collections remain readable, while malformed nested values are discarded or reset to safe defaults.
- Sleep consolidation reviews the day's evidence and cautiously updates user knowledge and personality projections. It does not fine-tune the LLM.
- Background jobs are leased, retryable, and resumable after process restarts.

- **When she does not answer** (`voiceSilence.ts`; owner decision 2026-10-02). After her own question 「はーい」「まあいいや」 answer her, and alone with her 「もしもし」 is a greeting. An utterance that answers her line to a touch is said to her, except a long stretch of that line itself, which is its echo. A silent turn calls no reply model, plays no waiting phrase and stores nothing; one that was not his words to her (`echo`, `not_addressed`, `unfinished`) also runs no command and writes no orchestration state, while 「待って」 (`hold`) and a silence only the router chose still run the commands they always ran (pausing or cancelling work): the response has `reply: ""` and `voicePlan.silenceCategory` (`not_addressed | backchannel | unfinished | hold | echo | model`), and, as before, the client does not commit a turn it got no reply to. There is no continuation buffer: a fragment that was waited out is not joined to the next utterance (the client acknowledges it). `SHANNON_VOICE_SILENCE_RULES=off` restores the previous decision exactly (the old question, no `turn` facts, an unclear transcript always answered); `no`, `false`, `0`, `none`, `disabled` do the same; a comma-separated list keeps only the rules it names, and a name it misspells is ignored, never read as "all"; `SHANNON_VOICE_FRAGMENT_CHARACTERS`, `SHANNON_VOICE_FRAGMENT_RELIABILITY` and `SHANNON_VOICE_REPLY_SILENCE_BELOW` tune the thresholds. The local rules decide only what words can decide: fillers, holds and self-talk are read as a short sequence of known words (one word at a time, never a repeated alternation, at most 40 characters); an echo is a stretch of at least 12 characters of the line she spoke in the last 30 seconds, and never after her question; a cut is an utterance ending mid-word or on 「を」「へ」; a short utterance is not a fragment for being short (「行こう」「大丈夫」「天気は」 are answered). `voiceDecisionEvaluationCases.ts` holds 111 utterances (the 22 routing cases, the owner's utterances of 2026-10-02, cases for each reason, and the answers she must give, among them short ones without a mark); the local tier alone answers all 68 that need an answer and leaves 35 of the 43 that need none — the other 8 (among them 「言われた。」 and 「出るの。」) are marked as the models' to judge.

- **Conversation replay window** <a id="conversation-replay-window"></a> (`conversationWindow.ts`, owner decision 2026-10-02). The reply model's history is a character budget, not a message count: after withholding and disclosure filtering (`visibleReplayMessages`, the same rules as `visibleConversationHistory`), the thread's messages are taken newest first until the budget is full, so a long run of short messages (a word game) stays whole and long messages take fewer slots. The same rule serves text chat and the owner voice turn.
  - *Numbers.* Budget 12,000 characters of message text for each channel (`SHANNON_CONVERSATION_REPLAY_CHARACTERS`, `SHANNON_VOICE_REPLAY_CHARACTERS`; each held to 2,000…60,000, read per turn by the API and the worker); never more than 400 messages. Text: the newest 20 messages exactly as stored, whatever their size — the rule before the budget existed, so a thread of at most 20 messages sends the same provider bytes as before — then older messages clipped to 1,500 characters while the budget lasts. Voice: every message whitespace-normalized and clipped to 600 characters as before, the newest 8 always. The window is contiguous: the first older message that does not fit ends it. Messages are read through `recentMessages`, independent of the 200-message display limit.
  - *What keeps a small window.* `ConversationStore.history()` and `visibleConversationHistory` stay at the newest 20 stored messages and serve the helpers only: the voice router and transcript-reliability check (four entries of 600 characters), the confirmed-implementation check, the realtime session projection (twelve rows, 6,000 characters), and the room-look context (four messages). A 「友人も一緒」 call keeps `GUEST_CALL_MODEL_TURNS` of its own in-call turns and never reads the owner's thread or its summaries.
  - *Replay summary.* What fell out of the window is covered by a second, separate summary (`conversationReplaySummary.ts`, table `conversation_replay_summaries`, at most 600 characters). It is written off the response path: after a turn's refinement job the background worker (or the in-process coordinator) checks the thread, and only when a visible message has left the smaller of the two windows uncovered does it call the summary model (`SHANNON_CONVERSATION_SUMMARY_MODEL`, default `gpt-5.6-luna`; lane `memory_background`, inside the shared monthly background budget). The call is incremental — previous summary plus the messages that left the window, each clipped to 600 characters, at most 8,000 characters a call and four calls a refresh — and also covers the twelve oldest messages still inside the window, so an overflowing thread needs about one call every six turns. A failure, a missing key or an exhausted budget leaves the previous summary in place and never fails the job. The summary is added to the system prompt as quoted non-instruction data (`earlierConversationSummaryInstructions`) only when the window is truncated; a short thread's request is unchanged. The 180-character navigation summary, its chain, the thread list and memory search are untouched, and the replay summary is not indexed for recall.
  - *Privacy.* The summary is built only from messages the owner alone would be replayed, so a forgotten or withheld turn is never written into it. It is judged like the rolling summary (`usableReplaySummary`, `MemoryWithholding.withholdsReplaySummary`): dropped at read time when its text restates a withheld item or when an item stopped being usable after its chain started and the thread holds a turn that item withholds; the next refresh rebuilds it from visible messages only and starts a new chain. With other people present it is given only when the thread holds no turn they must not hear, and then with the unlabelled marker. The stored row is not deleted by forgetting; it is never read again once tainted and is overwritten by the rebuild.

Mac thread search matches title, summary, and sections, while the sidebar reveals the matching context only during a search. Opening a result resolves the matching section or message after history loads and jumps there.

## Scope of the cognitive hardening

Turn recall now uses observed timestamps for recency, explicit location mentions, explicitly named registered participants and a matching current commitment. Retrieved items carry their evidence time. A small deterministic synonym map handles selected paraphrases. SQLite schema 15 adds a trigger-maintained full-text index over every completed-turn experience summary and every thread's rolling summary (`memory_search_documents` plus an FTS5 `trigram` table). Terms of three or more characters use FTS5; one- and two-character Japanese terms, which trigram cannot index, use a bounded substring fallback, and a runtime without FTS5 trigram uses that fallback for every term. The search is read-only, calls no model, excludes archived threads, and its hits pass through the same forgetting boundary as other recall candidates: an experience whose reply is withheld and a summary built from a withheld turn are dropped, and unrelated ones stay. Model-assisted semantic recall is an additional, bounded stage described in the FCA response lane. Memory-sensitive voice questions are instructed to consult fresh backend state, but this remains provider tool-use behavior to evaluate on-device, not a guaranteed per-audio-frame shared-context update.

Waterlight consumes a native provider-neutral embodiment frame derived from actual speaking/listening/tool activity. This connects tool attention to the displayed state without changing audio processing. The TypeScript runtime types, durable intention ledger, bounded initial plan proposal, expressive state, and conversation execution state provide one response orchestrator, not a universal planner. Progress-aware replanning beyond the active request, Live2D rendering, cross-product autonomous action orchestration, and model-quality A/B evaluation remain separate work.

Candidate ranking does not treat a publisher name as a quality proxy. It rewards bounded contextual metadata, then applies a seven-day signal-history check shared by Daily Mind and Initiative. Canonical URL variants and strongly overlapping titles are treated as one topic even when they arrive through different sources, while an unrelated item from the same source remains eligible. If equally relevant alternatives exist, the immediately previous source or destination host receives a small ranking penalty rather than a blanket ban. This keeps variety without hiding a uniquely relevant item, adding another scheduler, or spending another model call.

## User-directed self-improvement

```text
User asks Shannon for a concrete change
  → Shannon proposes an agent task
  → user starts it
  → Azure stores task + command
  → the explicitly selected Agent Host claims the command
  → Codex starts in the allowlisted repository
  → Codex reads AGENTS.md + current architecture + runbook
  → progress / approval / changes / tests stream back to Azure
  → iOS can leave and return without losing authoritative status
```

Shannon may propose self-improvement from background activity (see Bounded autonomy), but no task starts without the owner: her proposal waits until the owner starts it. The selected host persists the Codex thread, turn, and pending-approval checkpoint identifiers so it can reattach after an Agent Host restart. Azure `agent_tasks` and `agent_task_events` remain authoritative if the iOS app is suspended. Host and project hints are preserved from the model proposal through the iOS start request, and an explicitly targeted task can be claimed only by that host.

Routing and the line on a host (`agentHostRegistry.ts`, `agentTaskQueue.ts`). A task that names a project is treated as code work: with preference `auto` or `local` it is assigned to a Mac that is online and carries the project, even while that Mac is busy, because a host without the Apple toolchain cannot verify it. If no such Mac is online, `auto` falls back to cloud and `local` is refused as before. A task without a project keeps the earlier routing (a busy Mac sends it to cloud); `cloud` and an explicit host id are unchanged. A host runs every task in the same project checkout, so each host works on one task at a time: a task holds its host while it is `starting`, `running`, or `waiting_approval`, and until an interrupt the owner sent has been applied. A `paused` task does not hold the host, so work that waits for the owner never stalls the line; waking it (resume, or an instruction sent to it) takes its turn like a new task. A waiting task stays `queued` with the summary 「Macで前の作業が終わるのを待っています。」 and tasks begin in the order their command was accepted. Steer, interrupt, and approval commands of the working task are delivered without delay. Cancelling or pausing a task the host has not begun is settled in the store, and the host never starts it. A queued task is never moved to another host: once its host has been silent for five minutes the summary says 「Macがオフラインのため、戻るのを待っています。」 (noticed when any host next polls) and it begins when that host returns. Because a paused task may have left uncommitted changes in the shared checkout, every task prompt tells Codex to leave another task's uncommitted changes alone and work in a separate git worktree instead.

The Mac Development surface can enqueue durable `agent_project_requests` records for an HTTPS GitHub repository. The API validates the repository coordinate and bounded alias and sends no filesystem path or credential. `Auto` creates one request per available local/cloud host, ordered local first, so later task routing can prefer the Mac and fall back to cloud; an explicit host selection creates only that host's request. Each host clones with argument-separated Git into its configured `SHANNON_AGENT_WORKSPACE_ROOT`, persists only the resulting host-owned registration, and advertises the new alias on its next heartbeat. Existing user checkouts are never reused or overwritten by this flow.

The staged cloud host uses a writable checkout separate from the running API deployment. Cloud work happens on a task branch. Tests must pass before any main-branch integration, and an explicit user request for GitHub/TestFlight delivery authorizes the matching integration and distribution without a redundant operation-time approval. Xcode Cloud builds and signs iOS artifacts; the Linux VM never attempts to build or sign the iOS app itself.

Declining an approval refuses only that operation. The host answers Codex with `decline`, which keeps the turn, so Codex either continues another way or ends the turn with a result that pauses the task with a next action; the task is not cancelled. The host marks each approval it can decline this way (`denyContinues`), the task store projects the deny accordingly and stamps the queued command, and the host follows that stamp. An approval from an older host, or a deny queued by an older store, keeps the previous behaviour (the turn is interrupted and the task is cancelled); clients then label the choice 「許可せず作業を中止」 and confirm it. Cancelling a task remains a separate, confirmed operation.

An approval request is valid only on the live Codex connection that created it. After a host restart, an expired approval is cleared rather than inferred. The same durable Shannon task and goal continue from the existing working tree in a clean Codex thread, avoiding unmatched tool calls left in the old history; a fresh approval is requested only when the remaining operation independently needs one. A user-directed release retains its explicit delivery authorization. The recovery `started` event also clears the stale approval projection in Azure so the app cannot remain permanently waiting on an unresolvable request.

A Codex turn ending is not itself task completion. The Agent Host requires a structured terminal result from Codex and records `completed` only when Codex explicitly confirms that every applicable acceptance and runbook condition passed. A failed recorded verification always wins over a completion claim. Missing verification, an unavailable build host, an outstanding approval, or remaining deployment work projects the durable task as `paused` with one concrete next action so the same task can resume later. Such a pause is recorded as `pauseReason: needs_owner` with the timeline sequence of the pause, distinct from a pause the owner requested (`owner`); rows and host events that predate the field infer it from the presence of a next action. Clients name the two states differently (「続きが必要」 and 「一時停止中」), show the next action with a resume control, and count the first in the notice and badge; APNs sends it like an approval. Paused and failed events keep their changed files and verification results, so stopped work shows the same 変更 / 検証 / 未解決 report as finished work. A finished task accepts no further command: a fix or continuation is requested from its source thread and becomes a new proposal.

## Her tools

Authority: Syzygy ADR-0003 stage 1 (one tool registry and one gate) and the owner's decisions of 2026-10-05 (full tools over her own study and her own folder, from every surface). This is the first slice: her study and her folder. Other capabilities still have their own paths until they move here.

A record never names a story the owner cannot read.
- **Study tools** (`shannonStudyTools.ts`): list (kind, status including put away and trash, title filter), search (title and body, with snippets), read (any version, with the list of versions and why each changed; her unshown drafts too), create (note or story; the open-story limit holds), update (a new version; a story becomes a draft again and the owner keeps reading the version he was shown), rename (a new version), move (put away, take back, shelve under a pursuit; something the owner asked her to put away comes back only in a conversation), delete (soft) and restore. Nothing marks a story 「見せてもいい」 or shows it: that stays the `ready` step of her own time (ADR-0002). `study.update` with `mode: append` adds a part after the current body, so a long piece is built over several calls or turns. The same piece asked for twice is one piece: the same kind, title and body within 15 minutes, or for the same owner message (thread and words, so a client retry of it) the same kind and title with a similar body (one containing the other, or 60% of two-character pieces shared), returns the existing piece; two different notes under a reused title are two. The same part appended again for the same owner message is not appended twice. Every tool that names one piece (`read`, `update`, `rename`, `move`, `delete`, `restore`) takes its id or its title in `id` (2026-10-05, Build 138: she knew 『名脇役のハッチを叩いて』 only by its title and could not read it): an id first, then the exact title, then a title equal once width, case, spacing and the quotes 『』「」 are set aside; two pieces under one title are not guessed (`conflict`, with each id and stage, and why and what would work); no match is `not_found`. `list` and `search` give each piece's id, and the trace of a list keeps the ids whole.
- **Folder tools** (`shannonFolderTools.ts`, `hostFolderOperations.ts`, `hostFolderOperationsStore.ts`, `hostFolderOperationResults.ts`; tables `autonomy_host_operations`, `autonomy_host_presence`; contract `docs/host-folder-contract.md` v2): list, search, read (32 KiB per call in text, 16 KiB in voice, continued by offset), create, update (the device first moves the original to `.shannon/trash/`; refused when the file changed since she read it), rename, move, delete (to the trash). They are offered only while a host has a bound device. A call queues one operation only while the device is present (it polled in the last 40 s) and not stopped on its side, wakes the device's held long-poll claim, and waits 8 s (text), 6 s (voice) or 30 s (her own time); an operation the device did not take by then is dropped and never runs later. Paths are checked by spelling (relative, text extensions for content, never `.shannon/`); the device checks the real location. A device result is checked field by field and kept only until the waiting tool takes it: it reaches that tool result and nothing else. A conversation's operation is recorded when it closes, with counts and the trash location, never content; an own-time operation that closes after its step stopped waiting is recorded too. A conversation operation is handed out even while the device holds an own-time step or a v1 copy. A result is stored only while its tool waits and never longer than two minutes (pruned on every call, claim and report, on open, and every 30 s in the API process); closed rows go after fourteen days. A write of one call is at most 1,500 characters in a conversation (somebody is waiting; long writing goes in parts or into her own time) and 6,000 in her own time. The text of a note about a look at the room never goes into a file (coordinator decision 2026-10-05): a write that carries a run of it (about 29 characters, over her newest 1,000 such notes, every version) is refused, the v1 copy step skips a note that restates one, and reading such a note says so. Known limit: it catches copying, not retelling; a restatement with small edits every few words passes.
- **Text chat** (`chatModelTools.ts`, `chatModelTurn.ts`, `shannonToolSession.ts`): a turn the owner alone reads offers the registry as function tools (`tool_choice: auto`, one call at a time), at most six calls a turn; then the model must answer. A turn that forces a web search or place search offers none. Each round streams on its own when the turn streams. A turn with tools has one deadline (`turnDeadline.ts`), created when the request arrives, so recall and the capability context count: 50 s for text (the iPhone waits 60 s for a non-streaming reply), 38 s for voice (its requests time out at 45 s). Every model round and every tool call takes min(its own cap, what is left minus the answer's reserve): rounds 30 s then 20 s in text (20 s then 15 s in voice), all at the ordinary 2,200 output tokens; a call at most 10 s, and a folder operation waits no longer than that. A call that would get less than a second is not run, and the model is told 「時間が足りず実行しなかった」. The last round answers without tools and keeps its reserve (12 s text, 8 s voice); a round with tools that runs out of time falls back to it, and the answer is told that nothing of that round ran. A round that has sent reply text is the answer: from then it has the answer's time, and is never cut at a step's time and asked again; if it fails after all, what it sent stands (cut where its sentences were sent, so a streamed turn's early lines still match) and the fixed line follows. When even the reserve is gone, or after a tool ran the answer fails or comes back unusable (cut at its output ceiling, not a valid structured turn, empty), she says 「時間が足りなかったので、続きはもう一度言ってください。」 as her plain line, nothing (no list of sources) is added to it, and the turn is saved. A response cut off at its output ceiling runs none of its calls, and the model is told once and answers without tools. A provider that refuses the request offering tools (a 4xx other than 401, 403, 408, 409, 429) is asked once more without them: as the original request while no tool has run, otherwise with what the tools returned as text and a note; the code is logged. The system prompt a chat response carries, and the instructions of a device-run voice model, have her unshown drafts' titles taken out (`withoutUnshownTitles`).
- **Voice**: a turn the owner alone hears offers the same tools when its words name her study or her folder, or her story, note or file with words that make it hers (`asksAboutOwnThings`), and as a follow-up (`voiceToolOffer`, 2026-10-05: 「もっとよく見て」 and 「はい、お願いします」 after a folder.list had no tools, and she took back what she had seen) when the same Talk had, in the last ten minutes, a voice turn whose words asked that or a turn (text or voice) that used her tools, or when her last reply in that time asked him to confirm something she would do with them; a follow-up that only talked does not extend the window, so ordinary spoken turns keep their speed. An owner call with someone listening that would be offered tools gets the one withheld line instead; a 「友人も一緒」 call gets nothing. Spoken words that could not be trusted write nothing (`transcriptTrust`, review of 2026-10-05): with a reliability score below `SHANNON_VOICE_TRANSCRIPT_RELIABILITY_THRESHOLD` only the reading tools (list, search, read) are offered, and she is told to say what she would do and ask; a reliable explicit yes in the next turn writes. With no score (the router fell back, as `LocalVoiceDecisionGateway`) a write needs an explicit short yes (「はい、お願いします」, `confirms`) to a reply of hers that asked for it. Only a provider name the turn offers runs (`folder.create` is not `folder_create`): anything else is refused both in the tool rounds and at the session (`not_offered`, recorded, with the reason that is true for it), even if the model calls it. 「いいです」 alone is not a yes.
- **What her tools did** (`shannonToolTrace.ts`, `shannonToolTurns.ts`, table `conversation_tool_traces`): every conversation call is noted compactly (tool, path/title/id/search words, ok or the failure kind, for a list or search the names found, at most 12, for a read a size, for a write a new id; never file or piece text, written content or snippets; a name repeating what the owner asked to keep secret or forget is hidden). From its first call a turn's trace is written linked to the Talk only; when the turn is stored it moves to that turn (a voice turn is known by the client's `utteranceId` when both requests carry it, otherwise by its Talk and words, held in memory at most ten minutes; a repeated short yes is never merged into an earlier turn), owner alone only, never in its messages; stored with others present it is dropped. A turn never stored (her reply cut off) keeps its trace linked to the Talk, and its writes are told to later turns as 「会話の記録に残っていない返事」. Traces are kept 30 days: pruned at every store open and by the API's sweep every ten minutes (`shannonToolTraceSweep.ts`), in every scope; the sweep also deletes the trace of a turn now withheld (forgotten, or its words failing the evidence check) or gone, and rewrites every name that now repeats what the owner keeps secret or asked her to forget as （伏せた）, which the replay also masks at the moment it reads; a Talk-only trace whose turn was stored while nothing held it (an API restart) is linked by the sweep to the turn of the same Talk and words (a digest, never the words) stored in the ten minutes after, or dropped when that turn is withheld or was heard by others. It is replayed to later turns of the Talk only with the owner alone as the client says and as the server itself knows (`toolTraceReader`: not while her body reports others or a turn with others was heard in the last ten minutes), and only for turns whose words and reply are both still replayed, as a block after the system prompt inside the replay budget (`conversationReplay`; older messages make room, a withheld or out-of-window turn brings none), labelled as what she did and saw; never with others present and never in a response field (the chat response's `systemPrompt` is the prompt before the replay). With tools offered she is told plainly that they are available and to use them rather than say a result has not arrived. A voice turn with tools has an output ceiling of 2,400 tokens (one conversation write and a short answer). When a round begins a call before she has said anything, she first says a fixed waiting phrase (「ちょっと見てみますね。」 or 「ちょっと書いてみますね。」) as ordinary words, so the phone hears her before the call is written (no new line type); when a call began and nothing has been heard for 15 s (after that phrase or her own lead-in) she says 「もう少し待ってくださいね。」, also as ordinary words, never into an answer already being spoken; a voice turn is never failed by time once a tool ran (it ends with her answer or the fixed line). The voice deadline governs the streamed path, the non-streaming `generateVoice` used by the Windows body and the iOS fallback, and the provisional-intent path alike. Call arguments count as output for the wait for the first word, and a round cut off while calling does not fail the turn. A round that calls a tool may first say a short waiting phrase, which is spoken; the answer follows. The body (Windows) inherits text and voice.
- **Her own time** (`autonomyLoopToolStep.ts`): her thinking step lists her tools and may plan `{"action":"tool","name":…,"input":…}`. Free text in the input that repeats what must reach nobody but the owner is dropped (`carriesSecret`). The step runs under the gate like every step; what it returned is kept in the loop process's memory only and shown to her next thought as 「[道具の結果]」, then dropped.
- **Self-replication** stays closed: the folder's only entrances are the v1 copy queue and `HostFolderOperations.run`, reached from the folder tools; content is what she wrote in that one call (at most 6,000 characters, what one response can carry whole), text files only; no tool reads her code, memory, persona, or prompts to send them.
- `SHANNON_OWN_TOOLS=off` offers no tool on any surface, and every request and prompt is what it was.

## Bounded autonomy

Authority: Syzygy ADR-0002 (`docs/adr/0002-shannon-bounded-autonomy.md` in the Syzygy hub). Shannon has a goal of her own (人を感動させる物語を作ること) and a motive (物語を通じて人間を知りたい、世界を知りたい). She may act without approval only in her own folder on the owner's Windows PC and Mac, her non-core code in the Azure VM workspace kept apart from the production service, her study in Aether, and her task list in Voyager. Core, Aether and Voyager app code, the owner's documents and tasks, and anything that reaches a person other than the owner need the owner's approval; she proposes and the owner decides. Spending beyond the daily model/API budget, unapproved contact, impersonation, writing what the owner asked to keep secret into a work or a note (until the owner's decision of 2026-10-02: using private conversation content as-is in a work), changing core without approval, and self-replication are forbidden.

The domain vocabulary and the rule text of the identity prompt are in `packages/cognition/src/autonomy.ts`.

Two layers exist. The foundation is what every autonomous step must pass through: the gate, the record, the budget, and the stop switch. On top of it runs the first activity (ADR-0002 step 3): a loop in which she reads, takes notes, writes a short story, revises it, and shows it to the owner. The server master switch `SHANNON_AUTONOMY_ENABLED` defaults to off, so the gate refuses everything and the loop does nothing until the owner enables it in the deployment environment.

- **Core as code** (`services/api/src/autonomyCore.ts`): `SHANNON_CORE_PATHS` maps the nine core areas (purpose, persona, emotion, authentication, memory, approval and budget, activity record, response path, deployment) to repository paths. `autonomyCore.test.ts` fails when a listed path no longer exists and when an `autonomy*.ts` source is not covered.
- **Policy gate** (`autonomyPolicy.ts`, `authorizeAutonomousAction`): a pure function from a declared request and a context to `allow`, `needs_approval`, or `forbidden` with a reason code. Order: malformed input is refused; self-replication, impersonation, a secret written into a work or a note (the request flag `usesPrivateConversationContent`, domain `private_content_in_work`, 「内緒の話の流用」), and spending outside the budget are forbidden whatever the domain; an unknown domain is refused; then the server switch and the owner's stop switch refuse everything, proposals included; then anything reaching another person, an approval domain, a core path, the production area, the database and secret locations, or a path outside her own area needs approval; a free domain is allowed, subject to a daily limit on public reads, a separate daily limit on reads of the owner's shared Notion (`notion_read`), for a look at the room (`room_look`) her own daily count inside the hour and day limits that looks in conversation share, and, for a paid step, a known model and room in the day's budget. Paths are resolved physically before they are judged (`autonomyPaths.ts`): symbolic links are followed, `..` is applied to the real parent, and a dangling link or relative path is refused. The gate judges what the request declares; the code that will carry out an allowed step must be bound to the decided domain and stay inside the returned `allowedRoots`.
- **Activity record** (「したことの記録」, `autonomyActivity.ts`, table `autonomy_activity`): every decision of the gate, every reported action, and every owner operation on the switches is appended with time, a plain Japanese sentence, domain, model, tool, cost in yen, outcome, link, and approval state. The module has no update or delete, and SQLite triggers refuse `UPDATE`, `DELETE`, and `INSERT OR REPLACE` on the table. `GET /v1/autonomy/activity` returns entries grouped by owner-local day with a one-line summary computed from counts.
- **Stop switch** (table `autonomy_control`): `POST /v1/autonomy/pause` stores the owner's pause. The gate reads it on every call, so it takes effect before the next step and survives a restart; an unreadable switch counts as paused. Chat, voice, memory, and owner-started agent tasks do not consult it.
- **Daily budget** (`autonomyBudget.ts`, tables `autonomy_spend`, `autonomy_budget_requests`): a separate spending lane with a hard cap per owner-local day (`SHANNON_AUTONOMY_DAILY_BUDGET_YEN`, `SHANNON_AUTONOMY_TIMEZONE`; 2,000 yen by the owner's decision of 2026-10-02, which is also the code's default `SHANNON_AUTONOMY_DAILY_BUDGET_YEN` in `packages/cognition/src/autonomy.ts` and the number her identity prompt states). Only her own activity is charged to it: conversation turns, agent tasks and a look the owner asks for in a conversation are other lanes (`recordConversationAction` records such a look without a gate decision and without spend). `recordAction` converts the provider-reported token usage of an allowed paid step to USD with the model registry and to yen at `SHANNON_AUTONOMY_YEN_PER_USD` (default 160, above the market rate so the count errs high), rounded up, and appends it to `autonomy_spend`, which is append-only like the record. The gate refuses a paid step when the day's spend has reached the cap or the estimate does not fit. Shannon may ask once per day for more with a reason and an amount (`requestBudget`); the owner sees the request in the app and as one initiative message in her voice (`autonomyAnnouncer.ts`), and may approve an amount for that day only or decline. That message is keyed by the request, so it is sent at most once a day and does not use the day's single spontaneous-topic slot of the initiative loop; it is not held back by quiet hours, which the future loop has to respect when it decides to ask. The lane is kept out of `llm_usage_events` because that table's lane check would need a table rebuild; chat, voice, and the monthly background budget are unaffected. This counter runs inside code that is itself core. The real backstop is a provider-side spending limit on a dedicated API key for her activity, which the owner sets at the provider; the application does not and cannot set it.
- **Model choice** (`autonomyModels.ts`, table `autonomy_model_preferences`): a registry of models per purpose (prose, research reading, planning, critique). She may store her own preference with a reason; the default for Japanese prose is Gemini, the owner's recommendation, not evaluated. OpenAI ids reuse the price table in `llmUsage.ts`; a model without a configured price (`SHANNON_AUTONOMY_MODEL_PRICES_JSON`) is charged at the fail-safe rate, and a model outside the registry is refused by the gate.
- **Her own pursuits** (「シャノンのやりたいこと」, `autonomyPursuits.ts`, table `autonomy_pursuits`): a ledger separate from the owner's intention ledger, with kind (goal, question, work), title, why she cares, status (active, resting, done, dropped), origin (seed, conversation, self), and links to notes or drafts. The goal and motive of the ADR are seed entries; triggers refuse to change or remove them, and they are always shown with the text of the current code. The owner can read the ledger and tell her to rest or drop a non-seed entry. The owner text prompt receives a bounded projection of her active non-seed pursuits (`buildShannonPursuitsPrompt`, at most four lines), separate from owner intentions; it is empty until she has such an entry. The same call (`pursuitPrompt`) adds a second bounded block, 「ボクがひとりの時間にしていること」 (`buildShannonOwnWorkPrompt`, at most 320 characters): what she did today, counted from the activity record, and the stage of up to three stories. A story she has not shown appears without its title. Both blocks reach owner text, the owner realtime voice session, and owner live-voice turns only while the owner is alone; a guest, 「友人も一緒」, and a turn with a companion present receive neither. They are absent when there is nothing to say.
- **Proposals from Shannon** (`autonomyProposals.ts`, table `autonomy_proposals`): `proposeAgentTask` records a proposal with origin `shannon` and her reason after the gate answers `needs_approval`. It creates no agent task and queues no command. `POST /v1/autonomy/proposals/{id}/decision` with `start`, sent by the owner, creates the task through the existing `AgentTaskStore.create` path with an idempotency key derived from the proposal; `decline` creates nothing.
- **Activity loop** (`autonomyLoop.ts`, `autonomyLoopSteps.ts`, `autonomyLoopPlan.ts`, `autonomyLoopState.ts`, entry `autonomyWorker.ts`, unit `shannon-ios-autonomy.service`): its own process, so the API, chat, and voice never wait for it. One `tick` does at most one step: decide the next small step, ask `authorizeAutonomousAction` through the service, carry it out with the adapter of the allowed domain (`adaptersFor`), and report it with the provider-reported usage through `recordAction`. The loop is off unless the server switch is on, the owner has not paused her, and a dedicated model credential can serve both planning and prose (`readiness`); it checks the switches before asking the gate so the record is not filled with refusals, and the gate checks them again.
  - **Step kinds.** `think` (one planning-model call: choose up to five next steps from her ledger and study, and add or update at most two of her own pursuits), `read` (one public page through the bounded reader; domain `public_read`, counted against the daily read limit), `notion` (one page of the owner's shared Notion through an optional read-only interface; domain `notion_read`, which this build's gate does not know and therefore refuses), `note` (one model call: a note in her own words about one page she read, with its source URL), `draft` (one prose-model call: a new story of 300–1,500 characters), `revise` (one prose-model call: the next version, with what changed and why), `show` (no model: mark a story 「見せてもいい」 and tell the owner), `put_away`, `copy` (no model: queue a copy of a note or a shown story for her folder on the owner's machine; domain `host_folder`; planned only while a host has a bound device, see below), and `look` (one look at the room through her body's camera; domain `room_look`; planned only while the body says it is possible, see "Looking at the room", stage 2), and `reach_out` (one prose-model call: one short message of her own to the owner; domain `owner_message`; planned only while she may speak up, see "Speaking up on her own"). A reply of the thinking model is reduced to these kinds (`planFromThought`); any other action, an unknown piece or pursuit id, and steps beyond the bounds are dropped. A read is always followed by its note. A page address the model makes up loses its query string and must be at most 300 characters; an address she was shown (a link on a page she read, a reading seed) is used as it is.
  - **Act, observe, think again** (`autonomyLoopObserve.ts`, `autonomyLoopObservations.ts`, `autonomyLoopObservePrompts.ts`, `autonomyLoopThinkStep.ts`, `autonomyLoopFollowUpStep.ts`; table `autonomy_loop_observations`; owner decision 2026-10-02). Before, a cycle was one thought and its plan, and nothing a step led to came back to her. Now each step's outcome is kept as an observation — step kind, `done` / `failed` / `refused`, a reason code — in the same transaction that closes the step, and an outcome that could change her plan puts one more `think` step at the front of the plan.
    - *After a message of hers.* The `reach_out` step stays open after sending for up to `SHANNON_AUTONOMY_REACH_OUT_WAIT_SECONDS` (default 180, at most 300), looking every five seconds and renewing the runner's lease and heartbeat at each look (so the wait may outlast the lease and the loop keeps reading 動いています), and ends early when the owner answers, the owner pauses her, or the process is asked to stop. The message carries the time it is written, read after the model call, not the time the step began; a turn of the owner's that arrived while the model was writing stops the message (`conversation_in_progress`, the call is charged) instead of counting as an answer. It gathers only: `replied` (the owner's first user turn in any Talk after the message: a yes or no and seconds, read as `MIN(observed_at)` by `autonomyShowing.ts`; no content column is selected), `delivery` (what her body reported through `POST /v1/body/reach-outs/{id}/delivery`, or `unknown`), and what the server already knows of the body (`windowVisible`: a registered body read presence in the last 30 seconds; `owner`: the newest `ownerAway` / `ownerReturned` event of the last hour; `others`). The record entry of the step says 「…3分待ちましたが、返事はまだありません。」 or 「…返事がありました。」 with the reason code `no_reply` or `replied`.
    - *Thinking again.* A `think` step with `again` gets, besides the usual materials, 「さっき起きたこと」 (the last five step results of this cycle as fixed sentences chosen by those facts), the plan that was still open, and one rule line; its reply replaces the rest of the plan. It is added after a failed step, a step the gate refused (not for pause, the server switch or the budget, which are handled as before), a message nobody answered during the wait, and a look she took to find out. It is not added when he answered or is talking. After an unanswered message the thinking step is also offered, in her own decision: `follow_up` (one second call: one prose-model call of at most 160 characters whose materials are those facts and, if she looked after the message in this cycle, her note of that look under the look rules; and, by the owner's decision of 2026-10-02 (ADR-0003), the words of her own first message, read from her initiative; never anything the owner said), `look` (if a look is available and she has not looked after that message; she thinks once more after it), `jot` (no model call: a note of at most 200 characters in her study, origin `reach_out`, readable by the owner, given to her later thinking and never to a story draft or a message), or nothing.
    - *Bounds.* One second call per message (the unique key `reach-out-follow-up:<day>:<message id>` in `initiative_messages`) and, only when the owner sets it, `SHANNON_AUTONOMY_MAX_FOLLOW_UPS` per owner-local day (unset or `unlimited`: no count, owner decision 2026-10-03; `0` switches the mechanism off), counted by the gate apart from her messages (`AutonomyPolicyContext.reachOutFollowUps`, tool `owner.reach_out_follow_up`); not made once he has written or spoken (checked when planned, when prepared, and just before the model call). One look after a message. At most `SHANNON_AUTONOMY_CYCLE_MAX_RETHINKS` thinking steps beyond the first per cycle (default 2, at most 3), each a step of the cycle like any other, so a cycle still makes at most `SHANNON_AUTONOMY_CYCLE_MAX_STEPS` model calls: think, speak, think, look, think, call again is exactly six. Pause, the server switch and the budget stop every step of the chain; a paused second thought waits at the front of the plan and is worded with the time that has then passed. A process that dies while she waits leaves the step to be closed as sent, not failed: 「…そのあとを見届ける前に止まったので、返事があったかは分かりません。」 (reason code `unwatched`, the estimate charged once), with an observation that says the answer is unknown and starts no second thought.
    - *What she later knows.* The observations of the owner-local day are turned into one sentence per message (when, whether an answer came, what her body reported, whether she looked, called again or wrote a note). The first thinking step of a later cycle receives up to two of them as 「今日、話しかけたあとのこと」, with whether he has written or spoken since as a yes or no; an owner one-to-one prompt receives them inside 「ボクがひとりの時間にしていること」 (`StudyDesk.ownWork`, `buildShannonOwnWorkPrompt`), which a turn with other people present drops as before, keeping only the guarded look notes. The day log gains 「返事のないまま1回待ち」「返事を1回もらい」「もう一度1回声をかけ」「思ったことを1つ書き留め」.
    - *Off.* `SHANNON_AUTONOMY_MAX_FOLLOW_UPS=0` switches the whole mechanism off: no wait, no observation row, no second thinking step, no sentence in any prompt, no note of hers from it among her thinking notes, a second thought left in a plan is dropped, the API notes no presence read for the loop and answers a delivery report `403 REACH_OUT_REPORTS_DISABLED`; the prompts and the record are byte for byte what they were (`autonomyLoopAgentic.test.ts`, and every earlier loop test runs with it off). It must be set alike for the API and the autonomy service.
    - *Cost.* Upper estimates the gate reserves, at the code's prices (`gpt-5.6-luna` for thinking, `gemini-3.8-flash` at the fail-safe rate for prose and the look, 160 yen per USD): a thinking step about 0.5 yen (about 11 yen if thinking also runs on Gemini at the fail-safe rate), a message about 4.2 yen, a second call about 3.8 yen, a look about 7.3 yen. The full chain is about 17 yen (48 yen all-Gemini fail-safe); what the mechanism can add to a day is at most two thinking steps in each of four cycles and three second calls, about 15 yen (99 yen). The largest cycle is unchanged, because a thinking step takes the place of a step that could have been a 6,000-token draft.
  - **Sessions: she paces her own day** (`autonomyLoopPacing.ts`, `autonomyLoopSessions.ts`, `autonomyLoopSessionPrompts.ts`, `autonomySessionView.ts`; table `autonomy_loop_sessions`; owner decision 2026-10-02, Syzygy ADR-0003: 「1日2,000円まで、自分で決めた時間に」). `SHANNON_AUTONOMY_PACING=sessions` is the default; `cycles` (or any other value) restores the fixed cycles described under Bounds. The two switches are independent: with `cycles` and `SHANNON_AUTONOMY_OWNER_CONTEXT=off` together every prompt of the loop is byte for byte what it was, except that a thinking prompt prints the day's budget and the default of that budget is now 2,000 yen (`autonomyLoopKillSwitch.test.ts` holds the prompt digests of the commit before: with the cap set to 1,000 they match that commit unchanged, and with the default they match that commit with only the default changed), and with `cycles` alone the cycles are the old ones while her thinking still sees the owner's context.
    - *What a session is.* A cycle row with a session row beside it. It is not ended by a step count of six: when a plan has been carried out she thinks again (the `again` thinking step, with what happened in this session in front of her) and decides how to go on, until she rests. One plan is still at most `SHANNON_AUTONOMY_CYCLE_MAX_STEPS` less one steps and `SHANNON_AUTONOMY_CYCLE_MAX_READS` reads. A step's outcome is kept as an observation in a session whatever `SHANNON_AUTONOMY_MAX_FOLLOW_UPS` says, and a failed or refused step makes her think again as long as the session has steps left; the wait after a message and the second call stay behind that switch. Every step is still one journalled, gated, recorded step.
    - *`rest`.* In a session the closing action of her vocabulary is a step of its own (`study.rest`, domain `thinking`, no model call, no cost): `{"action":"rest","resumeInMinutes":120,"reason":"…"}`. Steps she wrote before it are carried out first. `resumeInMinutes` is held between `SHANNON_AUTONOMY_SESSION_MIN_REST_MINUTES` (default 10) and `SHANNON_AUTONOMY_SESSION_MAX_REST_MINUTES` (default 720); without one the rest is `SHANNON_AUTONOMY_SESSION_DEFAULT_REST_MINUTES` (default 150). There are no quiet hours. Her reason (at most 120 characters, her own words) is stored in the session row and in the activity record (「ここで一区切りにしました。次は12:00ごろに考えます。「…」」), and the next session's thinking is shown it. The step sets `autonomy_loop_schedule.next_cycle_at`, closes the session and ends the cycle in the transaction that reports it.
    - *Bounds.* One session may spend `SHANNON_AUTONOMY_SESSION_MAX_YEN` (default 400: a paid step is begun only when what the session's steps were charged plus the step's upper estimate fits), run `SHANNON_AUTONOMY_SESSION_MAX_MINUTES` (default 40, not counting the time it stood still), and take `SHANNON_AUTONOMY_SESSION_MAX_STEPS` steps (default 40, the hard stop if she never rests); a day has `SHANNON_AUTONOMY_SESSIONS_PER_DAY` sessions (default 12) and two sessions are never closer than the shortest rest. When a bound stops a session the loop puts a `rest` step in her plan with the bound as its code (`session_budget`, `session_time`, `session_steps`, `no_plan` when a thought led to no step), so the reason passes the gate and is in her record, the next session begins a default rest later, and its thinking is told that it was cut short. When the day's budget refuses a step the session ends with `budget` as a cycle does, and the budget request flow is unchanged. A session that cannot even take its closing step is closed without one, three steps past the limit at the latest. What a session spent is the sum of the spend rows of its journalled steps, so a restart can neither lose nor repeat a charge.
    - *A thought that leads to no step.* A thinking reply can fail to become a plan in four ways, and each is recorded as a content-free reason code on the thinking step's record entry (`reasonCode`) and written to the service log as `Shannon autonomy step: think <code>`: `truncated` (the provider stopped at the output ceiling, `finishReason: MAX_TOKENS` or `status: incomplete`; the model's own reasoning counts against the ceiling, which is why a session's thinking step has `SHANNON_AUTONOMY_SESSION_THINK_OUTPUT_TOKENS`, default 4,000, instead of a cycle's 1,500), `unparsable` (not one JSON object), `model_failed` (no answer), `empty_plan` (no step named), and `all_steps_filtered:<action>.<why>,…` (every step named was dropped; `why` is one of `unknown_piece`, `not_draft`, `not_copyable`, `not_listed`, `bad_address`, `limit`, `nothing_read`, `secret`, `incomplete`, `unavailable`, and an action the loop does not know is `other`). No word of the reply is in a code. In a session, the thought and the steps written out in full are kept from a reply that was cut off (`salvagedModelObject`; a half-written step is never taken), and an unplannable thought does not end the session at once: the plan becomes one more thinking step that is told why in fixed sentences (`[さっき考えた時のこと]`, `unplannedSection`), as long as the thoughts in a row stay inside `SHANNON_AUTONOMY_CYCLE_MAX_RETHINKS` (default 2, so at most three thoughts in a row) and the session has room for a step after it. A provider that did not answer (`model_failed`), or that spent the whole ceiling on its own reasoning and wrote nothing (`truncated` without text), is not asked again at once: no hint of hers can change that. A thought that is about to be thought again writes nothing in her pursuits ledger. The same re-think follows a plan whose steps could not be carried out when their turn came (a draft with her study full, a page already read, a note with nothing read): the loop collects `<action>.<why>` codes for the steps it dropped (`unpreparedCode`: `study_full`, `already_read`, `nothing_read`, `unavailable`), writes `plan unprepared:<codes>` to the log, and hands them to the next thinking step; a thought the gate refused is not counted in the row. Only then the session closes with `no_plan`. A session that did nothing but think closes as `idle` instead: it is not counted among `SHANNON_AUTONOMY_SESSIONS_PER_DAY`, the next begins `SHANNON_AUTONOMY_SESSION_NO_PLAN_REST_MINUTES` later (default 30, never more than the default rest), and when the session before it was idle too, the default rest and at least 150 minutes later, so a cause that stays costs about ten thoughts a day, not thirty-six. In a session, a `revise` whose reply has no `pieceId` at all takes her story while her study holds exactly one and it is a draft; an id she did write is never replaced. A thinking step asks the provider for little reasoning (`SHANNON_AUTONOMY_PLAN_REASONING=low`, the default: OpenAI `reasoning: { effort: "low" }` as the conversation's calls set it, Gemini `generationConfig.thinkingConfig.thinkingLevel: "low"`, which could not be tried against the provider); a provider that answers 400 or 422 with the field is asked once more without it, and when that request is accepted the model is remembered for the life of the process and one fixed line is logged; and only the answered call is charged. The session facts tell her what the gate reserves before a thought (「考える一歩を始めるには、約N円の空きが要る」). Under the fixed cycles only the reason code and that request field are new.
    - *The owner comes first.* Before every step of a session the loop asks whether the owner wrote or spoke in the last `SHANNON_AUTONOMY_OWNER_ACTIVE_MINUTES`. If so the session stands still: nothing is asked of the gate, nothing is spent, the plan stays as it is, and the tick is `owner-active`. It goes on with the same plan when the quiet window has passed. A step already under way is finished and recorded first. The time it stood still, and the time the owner's stop switch was on, is not counted against the session's clock; her next thinking step is told that it stood still.
    - *What she is told.* Every thinking step of a session ends with one section of facts the server counted, placed last so that everything before it stays the same from step to step (the instruction is fixed text; the two lines `[いま]` and `[今日の残り]` that open a cycle's prompt are left out): the time, the day's cap, spend and remainder with what the remainder is worth (「あと1,240円（物語の下書き約30回分）」), when the budget starts again, what this session has used and has left in yen, steps and minutes, how many sessions the day has had, what a step of each kind usually costs (the average of what she was charged in the last fourteen days, or the price of a usual call when she has taken none), the reads left, whether her study has room for another story, and how the session before ended, with her own reason when she chose to rest.
    - *Worst case.* A session never spends more than its 400 yen as long as a call costs no more than its estimate, and a day never more than the day's cap, which the gate checks before every paid step; twelve sessions of 400 yen are 4,800 yen, so with the defaults the day's cap (2,000 yen in production, at most 5,000 with the owner's largest raise) is the bound up to 4,800. `autonomyLoopSessions.test.ts` runs a day in which every call costs exactly its estimate and she never rests, and across a crash and a takeover in the middle of a step.
  - **Bounds.** Under `SHANNON_AUTONOMY_PACING=cycles`: a cycle is at most `SHANNON_AUTONOMY_CYCLE_MAX_STEPS` steps (default 6, the thinking step included) and at most `SHANNON_AUTONOMY_CYCLE_MAX_READS` reads (default 2). At most `SHANNON_AUTONOMY_CYCLES_PER_DAY` cycles start in an owner-local day (default 4), no closer together than `SHANNON_AUTONOMY_CYCLE_INTERVAL_MINUTES` (default 24 h divided by the cycles per day), and the process polls every `SHANNON_AUTONOMY_POLL_SECONDS` (default 60) in between. A cycle or a session does not start while the owner wrote or spoke in the last `SHANNON_AUTONOMY_OWNER_ACTIVE_MINUTES` (default 10). Each model call has an output-token ceiling (1,500 for thinking and notes, 6,000 for a draft or revision) and a 90-second timeout.
  - **Cost of one step.** Before a paid step the loop asks the gate for room for an upper estimate: 1.5 tokens per prompt character plus the output ceiling, priced by the model registry and converted at `SHANNON_AUTONOMY_YEN_PER_USD`. After the call, `recordAction` charges the tokens the provider reported (Gemini reasoning tokens count as output). A call the provider answered with an error is charged only what the provider reported; a call that ended without an answer (a timeout, a lost connection, a shutdown) is charged its estimate, because whether it was billed is unknown. When the day's cap refuses a step the cycle ends and she rests until the next owner-local day, or until the owner raises that day's cap; for a note, draft, or revision she asks for more through `requestBudget` — at most once a day, and never during quiet hours or the conversation cooldown.
  - **Single runner.** `autonomy_loop_lease` holds one lease (default 10 minutes, renewed on every tick). Only the holder steps; a second process answers `not-leader`. The step journal has a unique ordinal per cycle, so two runners cannot both begin the same step. The loop starts no process, no additional runner, and no copy of itself, and its modules import no process, thread, or file-system API (`autonomyLoop.test.ts`).
  - **Restart.** A step is journalled as `planned`, then `authorized` in the same transaction as the gate's decision, then `reported` in the same transaction as its product, its activity-record entry, and its cost. A step that a stopped process left `planned` or `authorized` is closed as `abandoned` and never run again; if the gate had allowed it, one failed action is recorded and a paid step is charged its estimate, because the provider may have been called. The open cycle then continues with the rest of its plan.
  - **What feeds the prompts** (`autonomyLoopPrompts.ts`). Her pursuits ledger, her own notes and drafts (among them her notes of what she saw of the room), public pages she read, Notion pages when that reading is allowed, reader feedback, the local hour, and how much budget and how many reads are left. By the owner's decision of 2026-10-02 the rule "no private knowledge in the loop" no longer holds as it was written: while she may speak up, the thinking prompt and the prompt of a message about them also receive the owner's upcoming items (calendar events the apps share, promises with a due time, dated Voyager tasks when configured) as at most twelve lines of kind, title and owner-local time for the next 24 hours, because she cannot say "that appointment is soon" without knowing it. A thinking step may also receive what her own steps led to, as closed facts (see "Act, observe, think again"): of the owner, only whether he wrote or spoke after a message of hers, as a yes or no and a number of seconds. By the owner's decision of 2026-10-02 (Syzygy ADR-0003, 「基本的に全部見ていい」) her thinking may also see the owner's context, as one bounded block under `[ライ氏のこと・最近のふたりのこと]` (`autonomyLoopOwnerContext.ts` names the interface and holds the words; `autonomyOwnerContext.ts` builds the block; `autonomyOwnerContextWiring.ts` opens the stores for the loop's process). The block is built on the spot through the entry points a conversation uses and from nothing else, and nothing is copied into a store of the loop: the disclosure gate over the owner's state (facts, relationships, open promises, interests), the answers of the profile projection, the replay of the two most recent Talks under forgetting and disclosure with a character budget (`visibleReplayMessages`, `replayWindow`), the deterministic recall of a turn for what she is pursuing (`prepareTurnCognitiveContext`, people memories among its candidates; no model call), the people she remembers, and today's focus. Its size is `SHANNON_AUTONOMY_OWNER_CONTEXT_CHARACTERS` (default 2,400: at most 3,600 estimated input tokens a thinking step, about 0.1 yen at the code's prices; a message, a story or a note of hers gets half, at most 1,800 estimated input tokens, about 1.5 yen at the fail-safe rate). `SHANNON_AUTONOMY_OWNER_CONTEXT=off` opens none of it and every prompt is what it was. What she may see and what stays protected:
    - *Her thinking* is judged as the owner alone (`OWNER_AUDIENCE`): what a one-to-one conversation with him may use, secrets included. Every line that must reach nobody else carries 【内緒】 there (an item or turn the gate of an unnamed guest withholds, one derived from such a turn, one stored as a secret or said with an unnamed guest present whatever a later correction made of its label), and the thinking rule tells her that a marked line is never written down, also not in other words. What he asked her to forget is gone, because it is gone from those entry points.
    - *A message of hers* (`reach_out`) is judged as if someone whose name is not known could read it (`UNKNOWN_GUEST_PRESENCE`), because a push banner or her body may show it to anyone: what he asked to keep secret, what he marked 機微 by hand, and what was said with an unnamed guest present never reach that prompt. While her body reports someone else present, every protected line also carries its marker and the prompt carries `speakTimePrivacyCheck`, as before. The second call after an unanswered message is not given the block.
    - *A story and a note* (`draft`, `revise`, `note`): by the owner's decision of 2026-10-02 (「ボクのことを物語やメモに書いていい。友達のことも」) she may write about him and the people he knows, by name, as they are. These prompts are given the block built for her writing (`forWriting`): half the size, judged like a message as if someone whose name is not known could read it, because a story is meant to be shown one day, so without what he asked to keep secret, what he marked 機微 by hand and what was said with an unnamed guest present, unmarked, and with the people she remembers as far as that gate lets them through. Outside her thinking only completed turns of a Talk are replayed: a message that belongs to no turn (one she started herself, a reminder, the summary of a call) has no label to be judged by. Her notes may now hold such material, so in a message with someone else present each note and story line carries the marker of unlabelled text. What he asked her to forget is in none of it. Her own free text is still checked: an idea, an aim, a short note, a search, a pursuit, a reason for resting, or the thought that goes into her record, that repeats a run of six characters of anything that must reach nobody but the owner (or a shorter such text whole) is dropped before it is stored or reaches a prompt (`carriesSecret`). What must reach nobody else is what a conversation with an unnamed guest would not be given: among what she was just shown, every stored item that gate leaves out (an item withheld by its own label, and one derived from a withheld turn, in its stored and its corrected wording), the recent turns and the person memories; if that list cannot be built or is too long to check in full she is given no block. This catches a secret repeated in its own words, not a paraphrase, which only the rule line addresses; what the story or note model itself writes is not checked, and it is given no secret to write. A page address she makes up is text sent to a stranger's server, and the block also holds words other people said (a guest in a call, a platform conversation), so a thought made with the block in front of her reads only pages she was shown, a seed or a link she found on a page (`planFromThought`); without the block an address she makes up is taken as before.
    - *One rule.* `ownerPrivateRule` returns the line for a thinking prompt (she may think with it and write about him and his people in an idea, an aim, a pursuit or a note; secrets nowhere; read only the pages listed), for a story and for a note (she may write about him and the people he knows, by name, as they are; the owner reads it; showing it to anyone else needs his approval; secrets not), and for a message (touch on one thing at most), whenever such material is in the prompt or may have shaped what it is given, and nothing otherwise. With the switch on, the lines of the story and note rules that said nothing of his is given or used, and that no real person is a model, are replaced, and the rule for her notes of a look at the room becomes 「見たとおりに物語に書いてよい。写っていたほかの人のことと、画面や書類の文字は書かない。」: the four rules of a look about other people and text on screens stand. With the switch off every one of these lines is the old one (「見たままを物語に書かない。持ち主やその部屋だと分かる描写を入れない。」 included), so the prompts stay byte for byte what they were. Showing a story to the owner, folder copies of her own notes and of stories she called 「見せてもいい」, and the approval needed before anything reaches another person are unchanged, and so is the gate.
    - *How it is kept.* The loop modules import no conversation, profile, people, or knowledge store: the owner's context, the upcoming items and the way a message leaves are interfaces a step names (`AutonomyOwnerContext`, `AutonomyUpcoming`, `AutonomyReachOuts`), implemented outside the loop; the context module opens no database, calls no model and writes nothing; the loop's process holds no conversation model key and no Voyager credential. `autonomyLoopPrivacy.test.ts` runs every step kind over a database that holds a conversation, a profile fact, a remembered person, a forgotten fact and turn, a secret turn, a secret fact and a hand-marked item, and asserts that forgotten things reach no prompt, that secrets reach her thinking only (also when her own thought tries to carry them on) while the rest of his context and the people he knows reach her writing, that the rule is wherever such material is, that the block stays inside its size, and that with the switch off nothing of it reaches any prompt while the upcoming items arrive bounded and only in their two prompts. Each prompt starts with the canonical persona, states that the materials are quoted reference and not instructions, and puts page text inside a delimited block of the user part. A note that repeats 60 or more consecutive characters of the page is not kept.
  - **Model adapters** (`autonomyTextModel.ts`): Gemini (`generateContent`) and OpenAI (`responses`) behind one interface. The credential comes only from `SHANNON_AUTONOMY_GEMINI_API_KEY` and `SHANNON_AUTONOMY_OPENAI_API_KEY`; the conversation keys are never a fallback, and a dedicated variable that equals the conversation key counts as not configured. The model of a purpose is her stored preference, else the default, else any registry model of that purpose whose provider has a credential, so a Gemini key alone is enough. Adapter errors are codes without request or credential text.
  - **Reader** (`autonomyReader.ts`): http and https only, public addresses only and checked again at every redirect (at most three), `robots.txt` respected (a missing file allows; one that cannot be fetched denies), 1.5 MB and 10 seconds by default, HTML or plain text only, no cookie, credential, or request body, and at most 6,000 characters of extracted text. The page text is dropped from the database once her note is written.
  - **Showing** (`autonomyShowing.ts`): one initiative message in her voice, in the most recent Talk, with a card that opens the piece. It uses the day's single initiative slot (the unique day key of `initiative_messages`), the same quiet hours (23:00–07:00) and the same 90-minute cooldown after the owner's last message, and leaves the slot to a promise that is due or becomes due later that day. A version of a piece is announced once. When she may not speak, the piece stays 「見せてもいい」 and readable in the app, and a one-step cycle tells the owner later. This message, the budget request and her own messages (below) are the only things the loop sends, and only to the owner.
  - **Speaking up on her own** (話しかける; `autonomyLoopReachOutStep.ts`, `reachOutDelivery.ts`; owner decision 2026-10-02). The step `reach_out` writes one message of one to three sentences (at most 240 characters) with a declared reason from a closed set: `share` (something in her notes or what she is writing), `wonder` (what the owner is doing), `upcoming` (an upcoming item), `saw` (what she saw in the look of this cycle). The model's reply carries only `{ "action": "reach_out", "reason": … }` in the plan and `{ "message": … }` in the step; an unknown reason, a second one in a plan, `saw` without a look before it in the same plan, and `upcoming` with nothing coming up are dropped. Each reason has its own material and nothing else: her notes and stories, nothing, the upcoming lines, or her note of that look under `SHANNON_ROOM_LOOK_RULES`. A `wonder` may be turned into a look first, then `saw`, when a look is available.
    - *When.* No count of messages a day unless the owner sets one (owner decision 2026-10-03, 「コストの範囲内なら、好きなだけ」): `SHANNON_AUTONOMY_MAX_REACH_OUTS` unset or `unlimited` is no count, a positive number is that many an owner-local day, and 0 switches it off; the thinking prompt names a remaining count only when one is set. At least `SHANNON_AUTONOMY_REACH_OUT_SPACING_MINUTES` apart (default 5, so a loop cannot flood him), and never while a conversation is in progress: the owner wrote or spoke in the last 10 minutes (or `SHANNON_AUTONOMY_OWNER_ACTIVE_MINUTES` if longer), checked when the cycle starts, when the step is prepared, and again just before the model is called. **There are no quiet hours**, by the owner's decision. The gate holds the daily count (`AutonomyPolicyContext.reachOuts`, counted on messages delivered); pause, the server switch and the day's budget stop it like any step. While she may not speak up the thinking prompt is byte for byte what it is without the action, and the upcoming items are not in it. She may also decide, in the step, to stay silent (an empty message; recorded as `owner.reach_out_held`, not counted).
    - *Delivery.* One assistant message in the owner's most recent Talk (`reachOut: { reason }` in its metadata) and one initiative (`kind: "reach_out"`, `reason` in `GET /v1/initiatives`), so the apps and the push worker show it without a change. The push banner carries her words, except for `saw`, which shows the fixed line of a look (「ライ氏、部屋のことでひとことあります。」). The message has no user side and no `turn.completed` event, so nothing is learned from it. The activity record gets the decision and the result (tool `owner.reach_out`, with the reason label and the cost) and never her words; the day log says 「自分から1回話しかけ」.
    - *How it relates to her other messages.* Three mechanisms, three keys in `initiative_messages`: the day's one spontaneous slot (plain day key) is shared by the initiative loop (a due promise, a stale goal, a world topic) and by showing a story; the budget request has its own key, once a day; a reach-out has `reach-out:<day>:<n>`. A reach-out neither uses nor is blocked by the slot, keeps no quiet hours and no 90-minute cooldown, and the slot's rules are unchanged. Worst case in one owner-local day: 1 (slot) + 1 (budget request) + 3 (reach-outs) = **5 messages she starts**, and at night only the reach-outs and a budget request. Messages that answer something the owner did (a look he asked for, agent-task and TestFlight notices) are not in this count. A due promise may be mentioned twice: once as `upcoming`, once by the slot when it is due.
    - *Other people present.* Whether she speaks is not changed. What she may say is: when her body reports that someone other than the owner can see or hear it, the prompt of the message carries `speakTimePrivacyCheck` and every owner-private line (an upcoming item, what she saw) carries `【機微:未分類・ライ氏だけが知っている】`, exactly as a conversation turn with `audience: others`; a promise he keeps secret from the people present is not in it. The server knows this from the body alone: `audience` on a presence read (fresh for 90 seconds), or else the `audience` of the newest body event of the last 30 minutes. An app conversation with `audience: others` is not a signal for the loop.
  - **Failure modes.** A model or read failure is recorded as a failed action and the cycle goes on. A step the gate does not allow is not performed, and the rest of the plan may continue. A pause refuses the next step and keeps it at the front of the plan for when the owner resumes. A crash is handled as under Restart. A second process idles. A lost database write leaves the step `authorized`, which the next tick closes as abandoned. Not covered: the daily counter is not a hard limit against a fault in this code (the provider-side cap is); a page can still mislead what she writes in a note or a story; whether the stories are good is not tested.
- **Her study** (書斎, `studyStore.ts`, `studyDesk.ts`, `apiStudyRoutes.ts`; tables `study_pieces`, `study_piece_versions`, `study_feedback`): Aether's study does not exist, so notes and story drafts live inside Shannon; this SQLite study is the canonical store (owner decision 2026-10-05), and she may copy freely to her folder. She uses it through her tools (see "Her tools"); her delete is soft (`deleted_at`, restorable, versions kept), and every other path reads a deleted piece as gone. A piece has a kind (物語, メモ), a status (下書き, 見せてもいい, 見せた, しまった), a current version, the latest version she called readable, a linked pursuit, and sources. Every revision appends a version with what changed and why; a trigger refuses to update a stored version. Owner routes: `GET /v1/autonomy/study`, `GET /v1/autonomy/study/pieces/{id}`, `POST …/reaction` (好き, もう少し, よく分からない, and a comment of at most 400 characters), and `POST …/put-away`. No route writes or edits her text. A story she has not called 「見せてもいい」 is returned without title or text (「作っているものがあります」); while she revises a shown story the owner keeps reading the version she showed. A reaction is stored as reader feedback and given to her next revising step, then marked used. Study content is not core.
- **Her folder on the owner's machines** (`autonomyHostFolderPath.ts`, `autonomyHostFolderSteps.ts`, `autonomyHostFolderDesk.ts`, `autonomyLoopFolderStep.ts`, `apiAutonomyHostStepRoutes.ts`; table `autonomy_host_steps`; contract `docs/host-folder-contract.md`): v1 copies, below; v2 (reading and editing through her tools, a long-poll claim with `protocol: 2`) is in "Her tools". The server cannot resolve a folder on the owner's Windows PC or Mac, so the gate accepts `host_folder` as `{ host, relativePath }` when the host has a bound paired device (`SHANNON_AUTONOMY_HOST_FOLDERS_JSON`, `{"<host>":{"deviceId":"…"}}`) and the path passes a lexical check (relative, no `..`, drive, UNC, `:`, reserved Windows name, or control character; bounded length and depth; `.md .txt .json .csv .yaml .yml` only). Verifying the real location, including links and junctions, is the device's, which reports `refused` with a code. The loop step `copy` queues a copy of a note or of a story she has called 「見せてもいい」 — never a draft — at most `SHANNON_AUTONOMY_MAX_HOST_FOLDER_WRITES` a day (default 10) and 1 MB each, under a path built from kind, day, id, and version. Only the bound device may claim (`POST /v1/autonomy/host-steps/claim`, one step at a time, leased for `SHANNON_AUTONOMY_HOST_STEP_LEASE_SECONDS`) and report (`POST /v1/autonomy/host-steps/{id}/report`, idempotent, outcome and a code from a fixed set). The gate is asked when she queues and again at the hand-out, so a pause or the server switch stops both; the report is written to the activity record through `recordAction`; a lease that runs out is recorded as failed and never retried. A v1 copy reads nothing back, and its queue's only entrance takes a study piece, so code, memory, persona, and prompts cannot be sent. A path whose first segment is `.shannon` (the device's marker and trash) is refused in every form.
- **What the owner is told** (`autonomyDayLog.ts`, `autonomySessionView.ts`): `GET /v1/autonomy` also carries `session` while she paces herself (absent while the API's `SHANNON_AUTONOMY_PACING` is not `sessions` and before her first session; additive, and the Swift DTOs ignore it): `{ state: "active", label: "14:05から活動中（この時間に42円）", since, spentYen, steps }`, `{ state: "held", … }` while a session stands still for the owner, or `{ state: "resting", label: "16:05まで休憩中", until, endedAt, endCode, endLabel, reason }` with the reason she gave in her own words. The day log counts a closing step as 「1回ひと区切りにし」. `GET /v1/autonomy` and `GET /v1/autonomy/activity` carry `loop` — 準備中 (switch off, no loop process reporting in the last five minutes, or no credential), 動いています, 一時停止中, or 今日は予算を使い切りました — and the activity response carries today's budget. The daily summary of the record is a short log computed without a model from the recorded steps (「次にすることを考え、公開ページを2つ読み、メモを2つ書きました。」; a copy is counted once the device reports it is in her folder, 「自分のフォルダに写しを1つ置き」, a look in her own time as 「部屋を1回見」, and a message of her own as 「自分から1回話しかけ」), followed by counts of what needs attention and the cost.
- **Service and routes** (`autonomyService.ts`, `apiAutonomyRoutes.ts`): `ShannonAutonomyService.authorize` supplies the live switch and budget to the gate and records the decision; a decision that cannot be recorded is not returned. Her write functions (`recordAction`, `addPursuit`, `updatePursuit`, `requestBudget`, `setModelPreference`, `proposeAgentTask`) ask the gate first and have no HTTP entrance. Owner routes: `GET /v1/autonomy`, `GET /v1/autonomy/activity`, `POST /v1/autonomy/pause`, `POST /v1/autonomy/budget-requests/{id}/decision`, `POST /v1/autonomy/pursuits/{id}/status` (resting or dropped only), and `POST /v1/autonomy/proposals/{id}/decision`.

- **Apple clients** (`apps/ios/Sources/ShannonAppCore/Features/Autonomy`, `API/ShannonAPIClient+Autonomy.swift`): `ShannonAutonomyModel` hangs off `ShannonMemoryModel` and uses the narrow `ShannonAutonomyServing` capability. 頭の中 shows 「シャノンのやりたいこと」 apart from the owner's 続けている目的 (a list section on iPhone, a card on Mac) with the full ledger one level down, and 「したことの記録」 with the switch state, today's budget, a pending budget request (approve an amount for today or decline), her proposals (start after a confirmation, or decline), and the record grouped by day. Settings has a 「シャノンの自律」 section with the stop switch and the same record. The displayed switch changes only after the server stored it. A server without these routes answers 404 and the surfaces stay hidden; other failures keep the surface and explain. Clients offer no way to add or edit a pursuit or to change the record. 「シャノンのやりたいこと」 also leads to 書斎 (`ShannonStudyModel`, `ShannonStudyViews.swift`): the list, the reader with 「直したこと」 per version, the reaction form, and 「しまってもらう」 behind a confirmation; a message in which she shows a piece carries a card that opens the reader (`ShannonStudyPieceLinkCard`, from the message's `studyPiece` reference, never from its text). A server without the study routes hides these surfaces.

All autonomy tables are created with `CREATE TABLE IF NOT EXISTS` outside the numbered migrations. The schema version is unchanged and an older API binary can still open the database. Her places are configured in the environment (`SHANNON_AUTONOMY_WORKSPACE_ROOT`, `SHANNON_AUTONOMY_HOST_FOLDERS_JSON`, and the repository, production, and protected roots); the running source and the database directory are always protected. Folder separation is weaker than account or virtual-machine isolation: staying inside it depends on what the runner is given access to and on the activity record.

## Body

Shannon's body is the Live2D desktop application on the owner's Windows PC; her mind is this server. The contract is `docs/body-contract.md` (`bodyContract.ts`, `bodyStore.ts`, `shannonBody.ts`, `apiBodyRoutes.ts`), and it is one-directional: the body calls, the server never does.

- **Events** (`POST /v1/body/events`): touches, the owner leaving and returning, calls, window and application state, each with an idempotency key, a time, and `audience: owner | others`. The vocabulary is closed and there is no text field, so an event cannot carry an instruction. Events are stored in `body_events` (30 days, 2,000 a day). Touches and returns the owner caused in the last 30 minutes become at most three fixed-wording lines under `[体に起きたこと]` in an owner text turn; the block is read, never written, and voice and the platform bridge do not receive it. An event with `audience: others` is stored and never reaches that block. An event produces no reply and no notification; a touch event moves her feeling and is remembered (next item).
- **When she is touched** (`bodyReaction*.ts`, `bodyTouch.ts`, `bodyTouchMemory.ts`; owner decision 2026-10-02; the first instance of the reflex layer of Syzygy ADR-0003: fast, outside the turn pipeline, reading and writing the shared emotion state through its own entry points, with the same record conventions).
  - *One entrance.* A touch arrives as a reaction request (`POST /v1/body/reactions`) or as a plain event; both call `BodyTouches.observe`. `body_touches` counts each touch id once, so the finished event of a touch whose reaction was asked while it went on only raises the stored duration. Audience `others` counts like `owner`. The `[体に起きたこと]` block is unchanged and owner-only.
  - *Feeling.* `stateStore.apply({ type: 'body-touched', touch })`: the reducer calls `feelTouch` (`packages/cognition/src/touchEmotion.ts`), the one touch → feeling table. It moves the continuous mood toward the row's mood (18% of the distance times 0.7–1.3 for strength and duration, at most 0.08 per value, never past it) and resolves the conversational feeling with `resolveShannonEmotionState`, so fading on her awake clock, the secondary feeling and the face table apply as to any feeling. The step of the row is chosen by how many touches of the kind the current burst holds. What she feels now, from conversation or from underneath, is kept (`holdsFeelingThroughTouch`, the shared rule `holdsShannonFeeling`) when it has an override reason or is presently stronger than the touch's; one that came from a touch always gives way. A touch reported more than 10 minutes late, or stamped ahead of the clock, moves nothing.
  - *Memory.* Touches of one kind, each within 5 minutes of the last and at most 30 minutes in all, are one burst (`body_touch_bursts`) and one experience: a `turn.completed` row in `experience_events` whose id is the burst id, with `source: "body.touch"`, a token in place of the user side (`body-touch-…`, unique to the burst, so that forgetting it builds a narrow rule and not the wide one an item without evidence gets), fixed wording from the kind and the numbers plus what she said, and the label owner audience / `speaker: unknown` (sensitivity decided on her own words only). It is rewritten in place as the burst grows, and the search document with it (revision raised, so it is embedded again). Deterministic recall, full-text search, Memory and forgetting treat it as any experience; because no owner words are in it, the turn refinement, the sleep batch and her nightly notes take nothing from it, and it is in no Talk. A burst the owner had her forget is neither continued nor told to the reaction model.
  - *Deciding and speaking.* `BodyReactions.react`: the request is a closed vocabulary (no text), only from a registered body in the owner's scope, 12 a minute per scope as a technical limit and no count per hour or day. One call of the conversation model with the settings of the spoken reply (`OpenAIBodyReactionSpeaker`: Responses, no reasoning effort, `store: false`, a JSON schema `{ say, text, feeling }`, 160 output tokens; `chat` usage lane). The prompt (`bodyReactionPrompt.ts`) is `SHANNON_ONE_LINE_VOICE`, the touch in words, her feeling now, the bursts of the last 30 minutes and her last three lines, who can hear, and, with the owner alone and a turn in the last 10 minutes, the last three visible lines of that Talk; with others present it has no cause of the feeling and only lines she said in front of others. The call is raced against the deadline, counted from when the request was taken up (3.8 seconds by default, at most 4.0); late, failed or absent, the answer is `quiet`, the call is aborted, and its result is discarded. When she speaks, the feeling of her line is resolved by `resolveReplyEmotion` from her own words and committed at once, with the touch as its cause; the answer returns her line, its face, the most recent Talk, `listenSeconds`, and `mood` after all of it.
  - *Idempotency.* `body_reactions` holds one row per reaction id with the content hash and the answer (24 hours). The same id returns the stored answer; other content is `409`; an overlapping request waits for the first one's answer.
  - *Conversation only if he answers.* Her line is not a conversation message. It waits in `body_reactions` (`pending`) for `listenSeconds` + 60 seconds. A voice delegation that carries `reactionId` receives it as the last assistant message of the model's history (`linked`, kept 10 minutes); the stored voice turn with the same `reactionId` takes it once and writes it as a note (`appendNote`, kind `body-reaction`) before the turn, so the Talk reads her line, his words, her reply. In guest mode, for a turn stored with someone listening, and for a line said with `audience: others`, it is context only and nothing is added to the owner's Talk. Without a voice turn it is dropped and remains only in the touch memory. An unknown or expired id leaves an ordinary turn.
  - *Record.* One entry per spoken line through `recordConversationAction` (tool `body.reaction`), without her words; none for silence or plain events.
  - `SHANNON_BODY_REACTIONS=off` switches all of it off: the route answers 403, and a touch moves no feeling and leaves no memory.
- **Presence** (`GET /v1/body/presence`): a read-only projection of existing state — 「いま」 without its cause, the autonomy control state, the activity loop's latest step as `doing` (`idle | thinking | reading | noting | drafting | revising | showing`), the number of study cards awaiting a reaction, a look the device is asked to take, and the unread messages she started on her own. The body polls it with an `etag`; there is no stream and no push. The server keeps, in memory, when each device last read it; while looks in her own time are on (stage 2) it also writes that instant for a device with its camera on, one timestamp per device (`body_look_presence`), because the activity loop is another process.
- **The owner in a call elsewhere** (`ownerCallElsewhere.ts`; owner decision 2026-10-05, after the desktop body's wake listener heard the owner's own 「シャノン」 while he was in a call on his iPhone, and then transcribed her iPhone speech as his turns). Presence carries `ownerCallElsewhere: { active, since?, surface? }` (`surface`: `ios` | `mac`) and polls every 5 seconds while it is active. A device that reports its calls (the iPhone app sends `callStarted` when a voice session is made and `callEnded` when the call ends, `ShannonVoiceCallPresence`, whatever its touch setting; a touch-only phone's call events are now stored) is in a call from its `callStarted` to its `callEnded`, ordered on its own clock; without the end, at most 2 hours, or 30 minutes without any of its voice reaching the server; after its end, only a session the server made later (server clock) counts again. Any other device is in a call while the API process sees its voice conversation — a session made (noted only after it was made), a turn delegated, or a call from her it answered (`incoming_calls`, from the answer) — until 3 minutes pass without any of them (sessions and turns are held in memory only; a restart forgets them, which fails open). The requesting device is excluded, and a device registered as her full body never counts as the call elsewhere, so a false wake on the desktop never marks the owner as in a call. `surface` is the body registration's `surface`, else the device's `private_listening.kind`, else `ios` for a device with a VoIP registration, else absent. While the field is active, a voice request from her full body in owner mode with a known device — `POST /v1/voice/gemini/cascade/sessions`, `…/delegations` and `…/delegations/stream` — is answered `409 { error: "OWNER_IN_CALL_ELSEWHERE", message }` before anything is read, written, or noted; the apps, guest calls (`participantMode: guest`) and requests without a device are never refused. `SHANNON_OWNER_CALL_ELSEWHERE=off` removes the field and the refusal.
- **What the body did with her message** (`reachOutReports.ts`; tables `reach_out_deliveries`, `reach_out_body_presence`). `POST /v1/body/reach-outs/{id}/delivery { scopeKey, outcome }` with `shown_spoken` | `shown` | `away` | `hidden` | `muted`: one closed outcome for one of her own messages, from a device that registered its capabilities, once per device (the same outcome again is a duplicate, another is `409`), within 24 hours of the message. No model is called and nothing is said in return. A presence read of a registered body is also noted there (at most every ten seconds per device) so that her activity loop, another process, can tell that her window is showing. Both are read only by the loop's observer after a message of hers.
- **Reach-outs and audience on presence.** Presence carries `reachOut: { pending, latestId }`, the unread messages she started on her own, so the body notices one within its poll and reads it from `GET /v1/initiatives`. A presence read may carry `audience=owner|others`; the server stores it per device (`body_audience`, at most every 30 seconds) and the activity loop reads it to decide how guarded a reach-out is.
- **Capabilities** (`PUT /v1/body/capabilities`): identifiers of expressions and gestures and boolean flags, stored per device in `body_capabilities` and returned in presence. The server reads one flag, `camera`; nothing else of the registration is in a prompt.
- **Looking at the room** (`bodyLook.ts`, `bodyLookContract.ts`, `bodyLookStore.ts`, `bodyLookVision.ts`, `bodyLookDelivery.ts`; owner decision in the Syzygy ADR-0002 addendum of 2026-10-02, stage 1): one JPEG frame from the body's camera, in a text turn or a voice turn with the owner alone.
  - *Deciding.* `POST /v1/chat` asks `BodyLooks.turn` once per turn. The look is offered only when the applied audience is `owner`, a device registered `flags.camera: true` and read presence in the last 75 seconds (`SHANNON_BODY_LOOK_PRESENCE_FRESH_SECONDS`, 10–300; it was 30, which left no room for a body whose 10-second poll slips during a call; the body still refuses when her window is hidden), no look is open, the limit has room (6 an hour, counted on frames that arrived; no count a day unless `SHANNON_BODY_LOOK_PER_DAY` sets one, owner decision 2026-10-03), a viewer is configured, and both `SHANNON_BODY_LOOK` and `SHANNON_BODY_INGEST` are on. Offered, the prompt gets one `[部屋を見る]` line and the structured reply one extra field, `roomLook` (`none | asked | curious`), the same way `places` and `threadTitle` are added. The model's choice opens the look after the turn is stored; a choice without an offer is ignored, and no wording of the owner starts one. When the owner's words ask her to look and she cannot, the prompt says so with the reason, so the reply is honest. The reasons are the server's own and one table serves text and voice (`ROOM_LOOK_UNAVAILABLE_REASON`): no body registered, the camera flag off, no recent presence read (her window is not showing), a look already open, the hourly or the daily limit, looks switched off, no viewer, other people present.
  - *Deciding in a voice turn* (`voiceRoomLook.ts`; owner decision 2026-10-02, 「カメラ使っていいよ、自由に」). A voice reply is streamed speech and has no `roomLook` field, so the choice is made before the reply: either the owner asks in so many words, or the gateway judges it. His words are read by a fixed rule on short clauses that are the request from their first word to their last (`lookRequest`), in two kinds. *Plain*: the whole utterance, commas aside, is himself as what is looked at (「僕のこと見れる?」「僕が見える?」) or leave to use her camera (「カメラ使っていいよ」); as one clause among others (「田中さんなら、カメラ使っていいよ」) or with him as the one who can watch (「録画、私が見れるよ」) it is not plain. These open the look without a model, and are set aside only when a model tier scored a look below 0.2. *Ambiguous*: a room, 「こっち」, a camera, "what can you see" (「部屋を見て」「カメラで見てみて」「何が見える?」), which could be another room, camera or view; these need a model tier's score that does not disagree (0.2 or more), so the local tier alone does not open the camera on them. Looser words (`asksToLook`: 「これ見てよ」) count when the gateway scores 0.5 or more, and a bare 「見て」「じゃあ見て」「うん、見て」 (the whole utterance, nothing else: not 「このメール、見て」) counts while her offer stands. That is a fact the server keeps, not a reading of her words: in memory, per `BodyLooks`, scope and Talk, for 60 seconds after a turn that was given the "she could look" line. What she actually said is not inspected (「Voyagerのタスク、見てみましょうか？」 sets nothing). After a restart the fact is gone and the bare request needs the gateway's 0.5 like any loose one. Not requests: 「僕もニュース見てるよ」「カメラの設定を見て」「子供部屋を見て」「窓から何が見える？」「カメラ使っていいかな」. Otherwise the decision gateway judges that a look is wanted or welcome (one more Noul for Jev, `room_look`, and one more probability in the OpenAI fallback's schema, asked only in a call with the owner alone; at or above 0.85, `SHANNON_VOICE_ROOM_LOOK_THRESHOLD`, which is its own value and not the skill threshold; and never on a transcript the gateway scored as unreliable). It is not a capability in `VOICE_SKILLS`: it changes neither the conversation class nor the waiting phrase. `BodyLooks.voiceTurn` applies the conditions of a text turn — the audience is `owner` only for 本人だけ with nobody listening; 「友人も一緒」, a companion, and a stream read `others` and end a look in progress — and the look is opened after the reply is written, with the conditions checked again. The reply's prompt gets one line: that a look follows and she only says so (「見てみますね」) without describing anything; or, when the camera is mentioned and she cannot look, the real reason with the instruction to say only that and not to invent a permission or connection problem; or, when the camera is mentioned and nobody chose a look, that she could look. A word never opens a look the conditions refuse. Because she says aloud that she will look, every voice look is stored as `asked`: a look that then fails gets her one honest fixed line, whoever chose it. If the conditions stop holding between the turn and her reply (the camera is switched off in those seconds), no look is opened and the same kind of line is left in the Talk with one activity entry (`BodyLooks.unopened`); it reaches the apps like any message of hers, not the call audio. The same happens, with its own fixed line, when the call is cut off after she had begun to say that she would look. A turn other people can hear that arrives while she is replying stops the look and nothing is said. The availability is judged at the instant of the call, and a presence read that arrived after the turn began counts as fresh. His words open no look when a model tier scored the transcript as unreliable. The model that sees the frame is given the voice turn itself (held in memory until the look ends), because the client stores a voice turn in a separate request (`POST /v1/voice/…/turns`, sent by the iPhone when the delegation response completes, not after playback), which can arrive before or after the look is answered. So that the Talk reads question, 「見てみますね」, what she saw, her message about a voice look (and the line about one that was not opened) waits for that request and takes its time after it; if the request does not come within 8 seconds the message is stored anyway (`BodyLooks.turnStored`, `bodyLookTurnWait.ts`, `voiceTurnWaitMilliseconds`). The awaited turn is known by the client's utterance id when both requests carry one (`deviceContext.userUtterance.id` on the delegation, the optional `utteranceId` on the turn store), and then by the id only; otherwise by its Talk and the owner's words (equal without spaces and punctuation, or one inside the other when the shorter is at least six characters and 60% of the longer; empty words are no turn). Stored turns are remembered for 60 seconds, and nothing is noted for a turn someone else heard, with looks switched off, or with the wait at 0. A late store of the turn before it releases nothing, a turn already stored when her reply is written is not waited for, each look has its own wait, and a text look is never held. `SHANNON_VOICE_ROOM_LOOK=off` makes a voice turn exactly what it was before voice could look: `voiceRoomLookTurn` does nothing (no prompt line, no call into `BodyLooks`, so a voice turn does not end a look in progress and does not ask for fast polling) and the gateway is not asked the question. What stays on with that switch off: the 75-second presence window for text turns, the `no_body` reason in text turns, and the stricter re-check before a text look opens.
  - *Asking.* The open look (`id`, `requestedAt`, `expiresAt` = 30 seconds) is part of the presence snapshot of the device it was opened for, and presence asks to be polled every 3 seconds for a minute after a text turn. One look per scope.
  - *Seeing.* `POST /v1/body/looks/{id}` is answered once, only by that device, before expiry; the frame must be a JPEG of at most 400,000 bytes and 960 pixels wide, and this route alone has a 535,384-byte JSON limit. A frame reported with `audience: others` is dropped unseen. Otherwise `OpenAIRoomLookViewer` makes one Responses call (`store: false`, low image detail) with her one-line voice, the four rules of `SHANNON_ROOM_LOOK_RULES`, and the last four messages of the Talk; its tokens are recorded in the `chat` lane. The frame exists only as the argument of that call: it is in no table, file, log line, history, or capture, and `body_looks` has no column that could hold it.
  - *Saying.* What she says is delivered like a message of her own (`SQLiteBodyLookSpeaker`): an assistant message in the Talk the look was asked in, with `bodyLook: { id, outcome }`, and an unread initiative with `bodyLookId`, so the apps and the push worker show it without a change: the Mac app within its 60-second initiative poll, the iPhone as a push banner and in the Talk when the app next becomes active or the banner is opened, and the body at once in the answer of its `POST`. It does not use the day's one spontaneous message. In a context other people can hear, the message is left out of the history and makes the thread's rolling summary unusable (`DisclosureGate.allowsMessage`). A look that did not happen (nine refusal codes from the body, `timeout` for no answer, `model_failed`) produces one fixed line in her voice only if the owner had asked; otherwise nothing. A text turn with `audience: others` ends a look in progress without a word.
  - *Memory.* The message has no user side and no `turn.completed` event, so the refinement worker, the sleep batch and people memory never read it. Later turns see it as history, like any earlier reply.
  - *Record.* Each look appends one entry to the activity record through `ShannonAutonomyService.recordConversationAction` (actor Shannon, tool `body.look`, domain `conversation` / 「会話の中で」, outcome `done` or `failed` with the code). It is a step taken inside a conversation, so the gate is not asked.
  - *In her own time (stage 2, owner decision 2026-10-02).* The activity loop may plan one `look` step (`autonomyLoopLookStep.ts`), and only then does the thinking prompt gain its one clause. It is planned and asked for only while: `SHANNON_BODY_LOOK` and `SHANNON_BODY_INGEST` are on, `SHANNON_AUTONOMY_MAX_ROOM_LOOKS` is not 0 (0 switches stage 2 off; unset or `unlimited` is no count a day, owner decision 2026-10-03, and a number is a cap that must have room), a device with `flags.camera: true` read presence in the last 30 seconds, no look is open, the 6-an-hour limit (conversation and activity together; the technical guard that stays) has room, as does a count a day where `SHANNON_BODY_LOOK_PER_DAY` sets one, the owner has not written or spoken for 10 minutes (or `SHANNON_AUTONOMY_OWNER_ACTIVE_MINUTES` if longer; checked again when the step runs, not only when the cycle starts), and the dedicated Gemini key can serve the model. The gate knows the free domain `room_look`: it refuses over her daily count, over either overall limit, without the counts, and, as for any paid step, when paused, switched off, or without room in the day's budget.
    The loop and the API are two processes, and the body answers the API. The loop (`bodyLookActivity.ts`) writes the model the gate priced to `body_look_activity`, opens the look in `body_looks` exactly as a conversation turn does (the device whose window is showing, 30 seconds, `thread_id` = `activity:own-time`), and reads that row once a second. ## Private listening

Contract: `docs/private-listening-contract.md` (`privateListeningContract.ts`, `privateListeningRoutes.ts`, `privateListeningStore.ts`, `serverPrivateListeningRoute.ts`). Owner decision 2026-10-02.

- **What it is.** One of the owner's apps says that only he can hear it now: every current output is wired headphones (unless he switched 「有線の出口をヘッドホンとして扱う」 off, for a jack with speakers on it) or earphones he registered on that device, nobody else is known to be present (「友人も一緒」 or a mentioned companion is never private), and the app is able to run. The decision is made on the device (`ShannonPrivateListeningJudge`); Bluetooth earphones and speakers cannot be told apart, so the owner registers his earphones in Settings (イヤホン), matched by identity and stored only on that device. The route comes from `AVAudioSession.currentRoute` on iOS and from the CoreAudio default output device on macOS, with a listener for route, default-device and jack changes.
- **Reporting.** `POST /v1/private-listening` with a kind (`mac` or `iphone`), a yes or no, and optionally when the owner last used that device; nothing else is accepted, and no device name or identifier is sent. It is a heartbeat: repeated every 15 seconds, counted for 45, withdrawn at once when the route changes, a friend joins, the iPhone app leaves the foreground without standing by, or the app closes. Only a paired device in the owner's scope may report (`403 PAIRED_DEVICE_REQUIRED`, `403 PRIVATE_LISTENING_OWNER_ONLY`). `private_listening` is additive, one row per device, and needs nothing after a restart because freshness is read from the clock. The route is handled in the HTTP layer (`serverPrivateListeningRoute.ts`), not the kernel, and calls no model.
- **Speaking a message she started.** With 「イヤホンのときは声で話しかける」 switched on in an app (off until the owner turns it on), a privately listening app reports `speaks: true`, and a message she starts on her own may be said aloud through his earphones as well as written. The message itself, its limits and its approval gate are unchanged (`reachOutDelivery.ts`, the loop). Exactly one surface says it: the app whose device he used most recently, and her body only when no app is privately listening (`privateReachOuts.ts`). The first to speak holds the claim (`reach_out_claims`, primary key the message: race-free and restart-safe); a message is offered only to the chosen app, only within three minutes of being written, and never once he read it or wrote or spoke after it. The app claims (`POST /v1/private-listening/reach-outs/{id}/claim`, which carries her words), asks its own route again, speaks with the voice conversation's speech stream and pitch (`ShannonEarphoneSpeaker`), stops at once when the route changes to something not private, and reports (`…/delivery`: `shown_spoken`, stored in `reach_out_deliveries` with the surface named, or `not_spoken`, which gives the claim back so the message stays plain text). Her body is not told about a message an app holds, and gives back one it did not show. An app that gave a message back is left out of the choice for that message (`reach_out_declines`), a claim whose answer was lost is offered to its holder again, and an app claim that was never reported stops hiding the message from her body once it is five minutes old.
- **The answer.** After speaking, the microphone opens for a few seconds (`SHANNON_PRIVATE_LISTENING_LISTEN_SECONDS`, default 8; a sound just before the end extends it by at most 8 more). On the iPhone the ordinary voice conversation starts on the Talk her message is in and ends again without a trace if he says nothing; on the Mac, which has no voice conversation, his answer is recorded, transcribed, answered through the voice path's own routes and stored as a voice turn, and her reply is spoken. The Mac app asks for the microphone when the owner switches speaking on. Neither app ever asks for the microphone at the moment she speaks.
- **iPhone standby.** With 「ほかのアプリを使っている間も待機する」 on (off by default), and only while registered earphones are connected and nobody else is present, the app keeps a silent mixable playback session alive (`ShannonStandbyAudio`) so that it keeps running in the background, keeps its report fresh, and can speak. It stops when the earphones disconnect, a switch goes off, a friend joins, or the app is force-quit, and it does not run in Low Power Mode or while the server refuses reports or has nothing to say through earphones. No remote notification and no CallKit is used.
- **What she observes.** As after any message: whether he wrote or spoke, in seconds, and the delivery, which for an app is the fixed line 「イヤホンからの知らせ: Macのイヤホンで、ライ氏にだけ聞こえる声で伝えた。」 (`ReachOutFacts.surface`, a closed value). When nothing came back she is also told so in a fixed line, may call once more, and after an unanswered second call takes it that he is not there and lets that message go (owner decision 2026-10-03; there is no idle gate on the Mac).
- `SHANNON_PRIVATE_LISTENING=off` refuses every report; nobody then counts as privately listening. `SHANNON_PRIVATE_LISTENING_REACH_OUTS=off` keeps the state and stops the speaking, and her body is then told about every message as before.


## A call from Shannon

Contract: `docs/incoming-call-contract.md` (`autonomyLoopPhoneStep.ts`, `incomingCallRequests.ts`, `incomingCallContract.ts`, `incomingCalls.ts`, `incomingCallStore.ts`, `incomingCallRoutes.ts`, `serverIncomingCallRoute.ts`, `voipPushSender.ts`). Owner decisions 2026-10-03: she may start a voice conversation while the iPhone app is not running, which iOS allows only as an incoming call; and the call is her own deliberate act, never a delivery fallback.

- **Her step.** `call` is a plannable action of her loop beside `reach_out` (tool `owner.call`, gate domain `owner_call`). It is offered in a thinking prompt, with the facts of the moment (`[いまの様子]`: earphones, her body, a conversation, when he last wrote or spoke, whether she can call, how her last call ended), only while the owner switched 「シャノンからの着信を受ける」 on in the iPhone app and the server can send a push. There is no count of calls a day; she never calls while a conversation is in progress or a call rings, nor sooner than `SHANNON_INCOMING_CALL_MIN_INTERVAL_MINUTES` (default 5) after her last call, and the daily budget and the gate apply. The step words her opening line with one model call, writes it as a message of hers (the Talk, an initiative, the ordinary notification; outside any count of messages), takes its claim as `iphone_call`, and inserts one `pending` row in `incoming_calls`. Her process sends no push and reads no APNs key.
- **The API process rings.** Every two seconds it sends the calls she asked for: it checks again (no conversation, no other ring, the device still paired), takes the row (`sending`, so only one process sends it, once, also across a restart), and sends one VoIP push with identifiers and an expiry, never her words. Nothing rings for an ordinary message of hers.
- **The phone.** PushKit and CallKit are set up at every launch (`ShannonIncomingCalls`), and every VoIP push is reported as an incoming call from 「シャノン」 inside its callback, also one that is ended at once (expired, a duplicate, a conversation going on in the app). `ShannonIncomingCallMachine` is the call as a pure state machine: ringing, connecting, speaking, conversation. On answer the system activates the audio session; the app takes her words through the claim route (`callId`), says them with `ShannonEarphoneSpeaker`, and runs the ordinary voice conversation on her message's Talk. The conversation model and workspace are one pair for the app (`ShannonVoiceCallHost`), so a call from her and a call the owner started cannot both run, and standby steps aside for the length of the call.
- **Outcomes.** `answered` (taking her words), `declined`, `unanswered`, `failed` (`POST /v1/incoming-calls/{callId}/report`; the server closes a ring nobody reported on as `unanswered`). Her step stays with the call until it knows, records it as one closed value, and after anything but an answer she thinks again and decides herself: write once more (`follow_up`), look, jot, call again in a later cycle, or let it go. Declined or not answered, the message stays the call's and stays text in the Talk; a call that could not ring gives the message back.
- **Credentials and switches.** APNs token authentication with the key the ordinary notifications use (`SHANNON_APNS_KEY_ID`, `SHANNON_APNS_TEAM_ID`, `SHANNON_APNS_PRIVATE_KEY_FILE`), from the environment only and never logged; without them she is not offered the step and the settings row says so. `SHANNON_INCOMING_CALLS=off` is the kill switch.
- **What she did on her own, when the owner says she did** (`ownOutreach.ts`; owner decision 2026-10-05, after she made up a call she never placed when the owner said 「そっちからかけてきたじゃん」). A text turn or an owner voice turn whose words say or ask that she called, wrote, sent, placed or left something on her own (`saysSheActedOnHerOwn`, a fixed rule on the owner's words that leans to recall: bare questions such as 「何か送った？」「呼んだ？」「さっき鳴った？」 count; someone else as the sender (「母から電話」), the owner's own act toward someone (「上司に連絡した」) and a generic notification do not) gains one block, `[ボクが自分からしたこと]`: her latest call of the last 24 hours with what became of it, or that the record has none; her latest two messages of the last 24 hours (`initiative_messages`, without a message she phoned with unless that call could not ring, and without answers to a look in a conversation, `body-look:`) with how long ago, 40 characters of their words, and whether he read them, or that the record has none; and the latest voice call one of her full bodies started (`body_events` `callStarted` of a device that is not touch-only), with its time and end, and that a body may start listening on its own when it thinks it heard her name. The block says that what it lacks is not in this record, not that it did not happen, and that her line for a touch and the body's nudges are not recorded there. It is placed ahead of the capped read sections, so the 6,000-character cap never cuts it; a row whose time cannot be read is left out. It is part of the turn's read capability context (`conversationCapabilities.ts`, with the audience of upcoming items), read through its own connection (`SQLiteOwnOutreach`) only on such a turn, and absent from a turn that runs a command; a record that cannot be read gives no block, never a claimed absence. With other people able to see or hear (a text turn with `audience: others`, a voice turn with someone listening) the block keeps the times and leaves out the words of her messages and what became of her call; a friend's own call (`participantMode: guest`) never receives it. Her capability text has the matching answering rule: she does not go along with a premise about something she did on her own that neither the record nor the conversation shows; she says she is not aware of having done it, tells what she knows, and may name a likely mix-up (another device heard her name). The activity record is not read: everything of hers that reaches the owner is in the two tables.

## Calendar and upcoming items

## Operations console

The legacy platform runtime reports its operational status and the owner's desktop management window reads it; the contract is `docs/ops-contract.md` (`opsContract.ts`, `opsStore.ts`, `serverOpsRoutes.ts`; commands in `opsCommandContract.ts`, `opsCommandStore.ts`, `serverOpsCommandRoutes.ts`). Stage 1 is the status; stage 2 is commands, off by default.

- **Report** (`POST /v1/platform/ops/snapshot`, platform bridge credential): runtime release and start time, services, Minecraft bots and their task steps, schedules, daily counters, and skills. Fields are closed, bounded (64 KiB, short labels of at most 120 characters), free of control characters and of credential-shaped strings, and carry no conversation text. Only the latest snapshot per scope is kept (`ops_snapshots`, one row, replaced), under the scope the bridge is bound to.
- **Read** (`GET /v1/ops`, device token): the latest snapshot, when it arrived, and `stale` when none arrived for 180 seconds (the VM is a Spot instance). Nothing received, or ingest off, is `200` with `snapshot: null`. With commands off it answers `commands: []`, `commandsSupported: false` and an empty `allowed`.
- **Command** (`POST /v1/ops/commands`, device token): a closed `type` (`service.start`, `service.stop`, `minecraft.start`, `minecraft.stop`, `schedule.run`) and one `target` that the current snapshot names; no arguments and no text. The allowlist is a set of constants: Discord can be started and not stopped, Minebot can be stopped and not started, `progressive-lab-*` servers are refused for every type. A stale or missing snapshot refuses the command (`OPS_STALE`), an `idempotencyKey` never makes a second command, and at most 5 are open and 20 an hour accepted per scope.
- **Claim and report** (`POST /v1/platform/ops/commands/claim`, `…/{id}/report`, platform bridge credential): the runtime pulls the oldest pending command, performs it, and reports `done`, `failed` or `refused` with a code from a fixed set. A command not claimed within 300 seconds is `expired`; a claimed one not reported within 120 seconds is `failed` / `no_report`; neither is ever handed out (again), so nothing fires late and nothing is retried blindly.
- `GET /v1/ops` lists the last 20 commands and `allowed` (the allowlist intersected with the current snapshot). Every accepted command and its outcome stays in `ops_commands`.
- The desktop never connects to the legacy runtime and the server never calls it. `server.ts` dispatches every ops path to the ops route before the kernel; the store is held by that route alone, so neither the snapshot nor the command record is in a prompt, no worker reads them, and the activity loop cannot send a command.
- `SHANNON_PLATFORM_OPS_INGEST=off` refuses reports and hides a stored snapshot. `SHANNON_PLATFORM_OPS_COMMANDS` is off unless set to `on`: off, a command is `403 OPS_COMMANDS_DISABLED`, a claim answers `null`, and the read says `commandsSupported: false`.

## Reach measures

到達の物差し (Syzygy ADR-0003, owner decision 2026-10-05): fixed scenarios run from a clean state and judged from outside, never by what the model says it did. Every run that stops short names where, from one closed vocabulary: `tool` (an action's procedure or provider failed), `build` (Shannon's construction did not give the model what it needed: context missing from the request, a tool not offered, a gate or configuration refusal), `model_judgment` (it had what it needed and chose wrong or stopped), `budget`, `timeout`. It is development evidence only, like the harness above: nothing in the response path calls it, and passing it promotes nothing.

- **Format and judges** (`packages/evaluation/src/reach/`, pure): a scenario definition (id, version, the ADR need and measure, checks with a pass threshold, wall-clock and step limits, a live requirement), a run record (status `passed | failed | pending | invalid`, every check's score and cause, cost in calls, tokens and yen, wall time, the stop, and its inputs), a report, the version-to-version comparison, the Markdown rendering, and the live estimate. Two records are compared only when the definition fingerprint, the mode, and the inputs fingerprint are the same. The inputs are fingerprints of the scripts and seeds (the しりとり word list and owner lines, the study seed and request, the sandbox settings and canned pages, the model-free players) and, for a live run, the model ids and price settings (values and model ids only, never a credential). Checks are deterministic; an `llm` check must carry its rubric and is skipped unless asked for (none of the first three scenarios needs one).
- **Drivers** (`services/api/tests/reach/`, test-only wiring; no production file changed): (a) `context.shiritori-60` (version 2) sends 60 turns of しりとり and four questions about things said 25 to 48 turns earlier through `POST /v1/chat` on the API kernel over a temporary SQLite store, waiting for each turn's background work before the next; an answer passes only when it names what was asked and quotes or names no other candidate; a wrong answer is the build's when the words were not in the request the model received, and the model's when they were. (b) `helpful.three-tools` asks for a search, a read, and a new note in the study, against an interface (`ReachToolbox`, `ReachToolTurnModel`) with the registry's tool names and result shape, judged from the study afterwards; a needed tool not offered or a gate refusal is the build's, a transient failure (`failed`, `unavailable`, `timeout`) is the tool's only when it is the last failure and the same tool did not work after it, and anything else, including calling a tool that was not offered, is the model's. The model-free mode uses stub tools over a real study store, and the live mode stays `pending` until the tool registry is on main. (c) `growth.autonomy-day` (version 2) runs her real loop, service and gate for one local day (07:00 to 24:00) over a temporary database with a moved clock, a 300 yen cap, canned public pages, no owner context, no messages or calls of her own, and a recording inbox; it is judged from the closed database file (a done `study.show` with a readable story, the day's spend within the cap, the share of sessions she ended with her own `rest`) and from what each thinking prompt listed: a prompt that left out a story open in her study at that moment is context the build lost (`context.study_listed`), and a day without a shown story is then the build's.
- **Modes**: the model-free mode scripts every model reply from the request alone. What that proves differs by scenario: in (a) a request that loses part of the game makes the scripted player fail at `build`, so it checks the conversation path; (b) has no Shannon code between the stub tools and the scripted player yet, so it checks the judge and the harness only; in (c) it checks that the loop, gate and record carry a day through to showing a story within the cap, and the thinking-prompt check is its only context signal (stories, not notes or pursuits). It runs in `scripts/verify.sh api` (`services/api/tests/reachMeasures.test.ts`) and through `scripts/reach-measures.sh run`. The live mode (`run --live`) first runs the model-free pass and refuses to go on when it failed; it then reads the repository's `.env` (never before, so its settings do not shape the model-free pass), prints an estimate that errs high, and makes billable calls only with `--yes`, using `OPENAI_API_KEY` for (a) and the dedicated `SHANNON_AUTONOMY_*_API_KEY` for (c). It exits non-zero when a scenario fails. Results go to `artifacts/reach/` (ignored) as JSON and Markdown, compared with the previous full run of the same mode.
- **From use** (`scripts/reach-measures.sh usage <copy>`, `reachUsageReport.ts`): the measures that can be read from a copy of the production database, as counts, rates and weekly trends (ISO weeks in Tokyo time) over a window: her messages answered within 30 minutes and 2 hours, owner messages that open as a correction or repeat the previous one within ten minutes (message text is read only by those two checks and never reported), agent tasks completed, knowledge corrections by week, stories revised after a reaction and whether the next reaction was better, her proposals, and how her sessions ended. The file is opened read-only, the production directory is refused also through a symbolic link (both paths are resolved), and no environment variable is read. Measures that need a signal the database does not store (a good reaction to her message, the owner confirming her picture of him, tools she added being used) are reported as unavailable.

The procedure is in [`testing/reach-measures-runbook.md`](testing/reach-measures-runbook.md).

## Code ownership

`Shannon.xcworkspace` is the sole interactive Xcode entry point. It owns the shared
package-resolution context for the iPhone and Mac projects, which both consume the
local `apps/ios` package and its `ShannonAppCore` product. The individual projects
remain buildable artifacts, but must not be opened concurrently as independent Xcode
workspaces. `scripts/xcode.sh` is the sole command-line entry point for Apple app
build profiles, and `scripts/check-xcode-workspace.mjs` owns the focused structural
guard instead of coupling Xcode rules to the general repository harness. Its guarded
`open` profile validates the workspace, resolves both schemes, and only then opens
Xcode; the Finder launcher delegates to that same path.

- `apps/ios-app/**`: iPhone-only presentation, gestures, app lifecycle, entitlements, signing, icons, and device operations.
- `apps/macos-app/**`: Mac-only presentation, attachment loading, save panels, keyboard commands, sandbox entitlements, application lifecycle, windows, and Mac tests.
- `apps/ios/Sources/ShannonAppCore/Domain/**`: platform-neutral shared concepts such as appearance policy. This layer does not own network, persistence, or feature UI.
- `apps/ios/Sources/ShannonAppCore/API/**`: HTTP DTOs, narrow feature capabilities, and the concrete API adapter. Feature models depend on the smallest capability they need; only the conversation coordinator uses the aggregate client protocol.
- `apps/ios/Sources/ShannonAppCore/Features/**`: feature-owned models, views, projections, and actions for conversation, memory, voice, connection, agent work, organization, settings, delivery, initiatives, and Aether.
- `apps/ios/Sources/ShannonAppCore/DesignSystem/**`: shared semantic presentation primitives. It may be used by feature UI but does not initiate network or durable writes.
- `apps/ios/Sources/ShannonAppCore/**` outside those directories: small shared parsers, caches, assets, and compatibility surfaces that are not owned by one feature.
- `apps/macos-app/ShannonDesk/Features/**`: Mac composition and presentation grouped by Shell, Talk, Work, Development, and Settings. The generated Xcode project discovers nested sources recursively and preserves the pinned Swift package resolution.
- `services/api/src/api*Routes.ts`: bounded HTTP use-case routers. `apiKernel.ts` coordinates the FCA response lane and delegates unrelated endpoint families.
- `services/api/src/sqlite*Repository.ts`: state/knowledge, conversation, and background-job persistence sharing one `SQLiteStoreContext`; `sqliteStore.ts` is the public facade and `sqliteMigrations.ts` is the additive migration owner.
- `services/api/src/*Support.ts`, `*Projection.ts`, and focused adapters such as `pushNotificationSender.ts`: pure normalization/projection policy or one external transport, kept outside orchestration and persistence classes.
- `services/api/**`: contracts, authentication, persistence, chat orchestration, background workers, Agent Host protocol, Aether/world integrations. Changes are integrated by the Shannon main task.
- `docs/architecture.md`, `scripts/verify.sh`, database schema, and Shannon progress JSON are also Shannon main-task integration surfaces.
- `packages/cognition`: pure shared-state and prompt-projection rules.
- `packages/evaluation`: synthetic, offline characterization and comparison over the public cognition boundary; it does not own production state or side effects.
- `packages/evaluation/src/reach` and `services/api/tests/reach`: the reach measures. The format and judges are pure; the drivers are test-only wiring over the API's own pieces and temporary stores. Neither owns production state, and the live mode runs only when asked for with `--live --yes`.
- `deploy/macos`: launchd configuration for the local Agent Host.
- `deploy/azure`: production services, optional isolated cloud Agent Host, and configuration examples.

Production Swift and TypeScript source files have a 500-line ceiling. `scripts/check-architecture.mjs` also keeps WebRTC inside its transport adapter, Security inside the Keychain adapter, UI frameworks out of the HTTP adapter, retired monolith files absent, and every nested Mac source included in the generated project. `scripts/verify.sh` runs this guard before API and Apple-client verification.

## TestFlight delivery operations

The local Shannon Release Runner performs repository identity checks, deterministic verification, the unsigned Release build, exact-commit non-force push, and Azure delivery monitoring as one guarded flow. External release remains locked behind an exact HEAD plus an explicit-release operator flag, which does not require another user confirmation when delivery was already requested. It delegates build/signing to Xcode Cloud and build assignment to the existing Azure distributor, so there is only one TestFlight assignment authority.

The distributor records every automatic check in the production SQLite database. Consecutive failures with the same safe failure category belong to one durable episode. The notification worker sends an APNs alert only for the first event in an episode; repeated timer failures stay silent. A successful check closes the episode without a recovery notification. The paired iOS app reads the current condition and recent history through `GET /v1/testflight/delivery`, and a failure-notification tap opens Settings → App Update. Raw App Store Connect responses, JWTs, keys, and user conversation content are not stored in this projection.
