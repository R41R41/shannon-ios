# Minecraft起動と結果不明通知の修正

状態: 実装候補。元の道具・実行権限・記憶・キャッシュを保った不具合修正。

## 起動依頼が実行されなかった原因

本番の音声・テキスト入力の時刻と、Anthropicへの道具付きリクエストの400拒否が一致した。Minecraft lifecycle操作の記録は0件で、起動命令は送られていなかった。Observerから実際に選ばれた11道具を確認し、架空の短い入力と同じ入力定義で再現した。`tool_choice:auto`では「compiled grammar is too large」の400、定義をデータとして読める固定呼出し口では200を確認した。道具を使わない`none`の200は、この不具合の検証成功とは扱わない。

Anthropicにはstrict道具20個、任意引数24個、union引数16個という合計制限に加え、組合せの内部grammar制限がある。[公式説明](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#schema-complexity-limits)。今回の実選択は明示上限内でも内部制限に達した。

修正は、初期と追加時の実リクエスト全体の合計を調べ、載らない道具は入力定義をデータとして示し、固定`tool_call`から元の道具へ接続する。開いていない道具・許可されていない名前・不正な入力は拒否し、元の入力検証、聞き取りの確度、同席条件、deadline、取消、lease、身体所有権を通す。実行結果と呼出しの記録も元の経路に残る。

明示的なgrammar容量400では、そのリクエストが未受理であることを根拠に、未受理の追加定義だけをデータへ直して一度続ける。受理済みの署名付き履歴・固定先頭・実行結果は変えず、外部操作を再実行しない。通信の結果不明や5xxに、この再試行を適用しない。内部制限に達するターンでは1通信増える。制限に達した形を後続ターンへ学習して避ける最適化は別課題。

固定先頭は`tool_open`と`tool_call`の2個になるため、配備直後にキャッシュが新規作成される。同じ修正後の架空リクエストを再送した実確認では、1時間キャッシュの読み取り4,837トークン、新規作成0を確認した。これは実APIの確認であり、実会話の体感速度やMinecraftの操作成功の保証ではない。

## 消せなかった通知

「結果不明」は成功／停止とは確定できない元の記録であり、「すべて停止」でも解消されない。通知だけを読んだことを保存する独立の確認操作を追加した。元の状態・資源の保留・予算・記憶の出自フラグを変えない。確認後も「裏の作業の記録」から結果不明の行を読め、新しい不明結果は再び通知される。

詳しいUI・API・単一writer・世代照合の契約は[結果不明通知の確認](action-notice-acknowledgement-contract.md)を参照。

## Windows管理画面

Windowsの操作は別の旧運用APIを経由していた。本番のMinecraft起動記録は完了していた一方、ログイン操作は報告が届かない状態になっていた。native場所記憶pluginが、Mineflayerの世界準備前に`world.getColumns`を呼び、body processを落とす初期化順序の不具合を確認した。native候補で、世界準備後の初期走査を保って修正し、17件の対象試験を通した。Windows画面の操作ミスやAnthropicのエラーと混同しない。

新規の`shannon-home`起動・停止・ログインとbotログアウトは、既存Windows画面とDTOを保ったまま共通lifecycleへつなぐ。元の操作ID、保存済み対応表、元actionの単一writer IPC、leaseと身体資源の権限を照合する。新規対応行を旧consumerへ二重配送せず、過去の失敗／不明コマンドを採用・再送しない。後着のnative受領結果は元のOps履歴へ反映し、不明actionの状態や保留を一括解除しない。managerの停止は従来どおりサービス管理状態の操作で、物理ログアウトと混同しない。

RCONにも別の不具合があった。命令と空の完了markerを一括送信する旧transportだけが、実サーバーで応答前に切断されていた。同じ認証・同じ`list uuids`の既存直列通信は成功した。修正後は命令を一度送信し、応答を受けてからmarkerを別送する。分割／複数packet、認証、サイズ、ID/type、取消、timeout、途中切断と未知結果の扱いを維持する。場所記憶と合わせた38試験と、修正後の実サーバーへの読み取りが通った。実停止・ログインの成功とは区別する。

稼働中のhome Javaがbackendの`shannon.service`と同じcgroupに入っていることも確認した。`KillMode=mixed`のbackend再起動はゲームを巻き込むため、配備helperはこの状態で停止する。プレイヤーがいるサーバーを配備の都合で停止せず、独立した管理への移行と実本番の到達点は別途記録する。

実本番反映、実ログイン、配布・実機確認の到達点は共有知識とstatusの証拠へ記録する。単体試験と実APIの架空入力を、実Minecraftの成功と扱わない。
