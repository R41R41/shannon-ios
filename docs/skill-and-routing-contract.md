Syzygy ADR-0008 (accepted 2026-10-07) puts Jev in front of the choices a turn makes: which tools the model is given, how hard the turn is and which model answers it, and (later in this stage) which headings recall walks. Stage 2 also gives her a procedural memory (skills). This file is the contract; the plan and the owner's answers are in the Syzygy hub (`notes/adr0008-stage2-plan.md`, until stage 2 ships).

**Nothing of stage 2 is deployed until the owner has approved it** (ADR-0002 core: response path, memory, the gate, deployment). Core areas: `autonomyCore.ts`.

**Model weights are never trained.** The competence table and the value table change which choice looks good from outcomes; the models stay fixed (`AGENTS.md`, product invariants).

## The registry's summaries

Every tool of the registry (`shannonTools.ts`) has a summary (`TOOL_SUMMARIES`, `toolSummary`): one line of at most 60 characters, in her words, that tells it apart from the others (`shannonTools.test.ts`). It is what Jev's menu chooses from and what the model reads of a tool whose schema it was not given. It is kept beside the registry, not in a definition, so nothing that carries a definition (a provider request, a turn's session, a test's trace) changes with it.

## The Jev client (step 2)

`infra/models/jev/jevChoice.ts` is the one Jev client. `JevChoiceClient.ask` sends `{ model, state, questions }` with the headers, the timeout (900 ms unless `SHANNON_JEV_TIMEOUT_MS`) and the order of reading of the voice router, which now asks through it (its bytes are unchanged: the Jev digests of the switched-off proof). `JevChooser.decide` adds what the voice gateway has around its call: the caller's fallback on a timeout, a failure or an answer off the menu (never an exception), and one decision trace per call, the call counted by `countedJevFetch` (stage 1). One Jev call is one trace, so the usage summary's call count from the traces stays right.

## Jev's confidence band, question sets, cache and replay (ADR-0008 §14)

After Canny and JevBystander (`docs/knowledge/external-agent-architectures.md` in the Syzygy hub):

- **The band.** A Jev probability is acted on only when it is confident: `yes` at p ≥ 0.9, `no` at p ≤ 0.1 (`jevBand`, `JEV_BAND` in `difficultyPolicy.ts`). In between (`unsure`) each site falls back to its own rule:

  | Site | `yes` (≥ 0.9) | `unsure` | `no` (≤ 0.1) |
  | --- | --- | --- | --- |
  | `needs_strong_model` | `sonnet` (served as the switches allow) | luna, escalated once on evidence (a tool failed, a round ran out of time), never before | on to the rules below |
  | `multi_step` | `luna_plus`, one rethink | luna's own tool rounds | same |
  | `needs_verification` | the luna checker (text), one rethink | the deterministic verifier alone | same |
  | small talk (`jev_only`) | — | — | only when all three are `no` and the kind is `chat` |
  | `retry_or_correction` (S) | S = 0 | settled as if no next turn had told her anything: competence and skill uses from G alone; the choice ledger at S = ½ with code `next_turn_unsure` (never a mood, `MOOD_INELIGIBLE_CODES`) | S = 1 |
  | tree recall usefulness | kept as a passage; counts toward the stop | the node may still be opened (reading more never blocks); not a passage, so the note keeps its deterministic sections | not opened |
  | `choice` (tool menu) | — | — | a menu answer is a choice, not a probability; `tool_open` keeps recovery |

  Jev never blocks: every confident answer adds care (a stronger tier, a check, a rethink) or narrows a search; the deterministic verifier runs on every turn that offered a write whatever Jev said, and a hard verdict on her reply comes only from evidence (the verifier, the tool results). Learned weakness (`luna_weak`) is evidence too, from the competence table.
- **Question sets** (`JEV_QUESTION_SETS`, `jevChoice.ts`): `voice_route.v1`, `tool_menu.v1`, `difficulty.v1`, `retry_or_correction.v1`, `recall_beam.v1`, all in English (`ql: en`). Any change of wording is a new version; a menu's entries are data and are covered by the questions' digest.
- **Traces** record the sets asked (`qv`), their language (`ql`), a digest of the exact questions (`qh`) and of the whole input (`h`: model, state, questions), whether the answer came from the cache (`cached`), and Jev's raw answer to every question (`a.<key>`: a probability or the chosen key, `invalid` when unusable). `replayedAnswers(trace.answers)` rebuilds the answers, so the selector's parse, the band and the policy recompute every decision from the traces alone (`jevBand.test.ts`). The voice router's trace gets `qv` and `ql` only while stage 2 is on (switched off it is stage 1's).
- **Cache.** `JevChooser` keeps the last usable answer per scope and input digest for 60 s (at most 128 inputs): the same input in that time makes no call (traced `cached: true`, cost 0). An unusable answer is never kept. Jev drifts about 0.05 between runs; a repeated turn gets the same decision.

## The tool menu (step 2, `SHANNON_TOOL_MENU`)

ADR-0008 §8 「道具は名前と短い説明だけを毎回渡し、使うときに定義を取り寄せる」.

- **What Jev is asked** (`mind/selectors/toolMenu.ts`): one `choice` question `tool` over the provider names of the tools the turn offers, each with its summary, plus `none`. At most 64 entries a menu; beyond 63 tools they are grouped by area (`tool__<area>__<part>`), all in the same call, and every group's answer that is not `none` is chosen. Jev's state is the turn's words (at most 2,000 characters; the voice router already reads them) and the surface: never a schema, a description, a tool result or anything the turn's audience would withhold. The candidates are exactly what `conversationTools` would offer (`toolMenuCandidates`, which opens nothing), so an audience with others present gets a menu of her Aether reading tools only.
- **When.** Text: in every turn that would offer tools (not a fixed command, an organizing turn, a forced web search or a place search), started before recall and awaited after the offer, so it runs in parallel with recall. Voice: only when the turn's words would offer tools, as a second Jev call started beside the router's (whose questions are unchanged); its answer is used only if the turn does offer tools in the end.
- **What the model gets** (`mind/tools/shannonToolMenu.ts`, `withToolMenu`): the schemas of the chosen tools (only those the turn offers) plus `tool_open(name)`, whose `name` is an enum of the tools the turn offers. Its instructions list every offered tool by provider name and summary (`[ボクの道具・献立]`); the capability lines (Aether, her Minecraft body) and the instruction lines follow every offered tool, not only the schemas sent. `tool_open` is answered by the session: it runs nothing, is not counted against the turn's six calls, takes no time and is not written to the activity record or the turn's trace; the opened tool's schema is in the request from the next round (`withToolRounds`). A call of an offered tool that was not opened is refused like a name the turn does not offer, and runs nothing. The offer, the audience, the gate and the runner are unchanged.
- **Fallback.** When Jev times out, fails or answers off the menu, the turn's session is not narrowed: every offered schema goes, as before.
- **Trace.** `tool_menu` with `tool` (the first chosen name, `none`, or `all` for the fallback), `chosen` (how many; −1 for the fallback), `offered`, `groups`.

## What the menu never hides (Hermes Agent finding)

- **Always loaded.** In every turn that offers them, the schemas of `ALWAYS_LOADED_TOOL_NAMES` (`shannonTools.ts`) go to the model whatever Jev chose (`withToolMenu`): the way to stop (`minecraft.cancel`) and the way to ask for the owner's approval (`aether.propose`, a proposal he adopts or rejects). The registry has no tool to ask the owner or to clarify (she asks in her reply) and none to speak or send (showing, publishing or sending to anyone is never a tool, `AGENTS.md`); none is invented. A tool the turn does not offer (others present, no Minecraft body in the game, no Aether inbox) is not sent either.
- **"Not found" is not "cannot".** With the tool menu's switch (`toolHints`, `skillRoutingParts`), a reading tool's answer that found nothing (`nothingFound`: `not_found`, or the whole text of an empty answer) carries one more line naming the places this turn can look in, each with one of its reading tools (`sourcesLine`). Only the text the model reads changes; the turn's trace and the activity record are as before.

## Read tools (step 3, `SHANNON_READ_TOOLS`)

The read capabilities that were projections only also become registry tools (one registry, one gate, one record), each with its own gate domain:

| Tool | Domain | Reads (the same read as) | Cost |
| --- | --- | --- | --- |
| `notion.read(query)` | `notion_read` | the Notion projection (`notionTurnProjection`) for one search word | none |
| `voyager.tasks(query?)` | `voyager_read` | the Voyager task read (`conversationCapabilityPrompt`, keyword search) | none |
| `schedule.upcoming(range)` | `schedule_read` | the owner's upcoming items as he alone hears them (`OwnerUpcoming.promptFor`, 48 hours or 8 days) | none |
| `places.search(query, area?)` | `places_search` | the place skill (`runPlaceDiscoverySkill`, a model with web search; no device location) | model |

- **Who.** The registry lists them for the owner alone, text and voice, never her own time; the gate (`authorizeToolCall`) refuses anyone else. They exist only while the wiring hands the runner their ports (`ShannonToolRunner.useReads`, `readToolPorts`); without them every offer, name and refusal is what it was (a call of `notion_read` is a name that does not exist). The self-diagnosis lists them only while the switch is on.
- **Audience rules unchanged.** A turn offers them only where its own projection rules would read the same thing (`conversationTools` option `reads`, fail closed): text, the owner alone in the app (`readToolPlan` of his selection: Notion, tasks and the schedule as he alone hears them; places); voice, the owner alone (`ownerAloneReads`). With the owner alone the turn's context is byte for byte what it was (`readTools.test.ts`); only the tools and their capability line are added. With anyone else present (text marked `others`, a companion, 「友人も一緒」, a platform conversation) no read tool is offered and every projection, guarded marks included, is exactly what it was (`readTools.test.ts`, the audience matrix). Jev's menu never lists a read tool in such a turn, because it lists only what the turn offers.
- **In addition, never instead (coordinator, 2026-10-07).** Every projection of every turn is exactly what it was: Notion with its source links, tasks, the schedule, and places with the device's location (`placeLocation` still runs the place skill and forces the web search, with no function tools). The read tools are offered beside them, for a deeper or another read than the projection made; their descriptions say not to call one when the same read is already in the turn's context, so what today's projection answers needs no extra model round. Voice likewise keeps its projections and offers the tools in a turn that offers tools.
- **Web** is a capability entry of the menu (`WEB_CAPABILITY_ENTRY`, text only, beside her read tools), not a function tool: choosing it sets the turn's `useWebSearch` (the provider's own search; no function tools that turn, as before).
- **Capability line.** `SHANNON_READ_TOOLS_CAPABILITY` (`packages/cognition`, conditional like Aether's and the Minecraft body's) is added after the Notion line only to a turn that offers a read tool (`withToolCapabilityLines`); with the switch off the description is what it was.
- **Record.** Each call is written to the activity record by name and outcome only (`会話の中でNotionの共有ページを読みました。`), never the query or what was read; a failure is `unavailable` and retryable.

## Difficulty and tiers (step 4, `SHANNON_DIFFICULTY`)

- **Jev's questions** (`mind/selectors/turnChoices.ts`), in the same call as the menu: `task_kind` (closed: `chat`, `feelings`, `recall`, `lookup`, `write`, `plan`, `analysis`, `code`, `action`), `needs_strong_model`, `needs_verification`, `multi_step` (`noul`), and, in a turn of the owner alone that follows a reply of hers in the same Talk within ten minutes, `retry_or_correction` (`noul`; Jev reads that reply as `previous_reply`, never in a turn with anyone else present). Text: in every model turn, in parallel with recall. Voice: in every turn the router routes (not an overheard guest turn), as the second Jev call beside the router's, whose questions are unchanged. One call, one trace (`difficulty`, with the menu's answers when there was a menu).
- **The policy** (`packages/learning/src/difficultyPolicy.ts`, pure, core **response path**: listed by name in the core map, so not emotion's). Luna first, inside Jev's band (§14 above). `sonnet` when p(strong) ≥ 0.9, or when luna's learned success for the kind is below 0.6 over at least five outcomes; luna with one escalation allowed when 0.1 < p(strong) < 0.9; `luna_plus` for multi-step (≥ 0.9); `jev_only` for small talk (served by luna; all three ≤ 0.1); luna otherwise and whenever Jev could not answer. `verify` (the luna checker) when p(verification) ≥ 0.9; `rethinks` (0–2) is one for each confident multi-step and verification. `sonnet` is served as `luna_plus` unless Sonnet is available (the key **and** `SHANNON_SONNET_ROUTING=on`; never in step 4: there is no Anthropic client yet). On voice (I-2) an available Sonnet serves only when the turn's time left covers its first-token latency plus 6 s (`sonnetFirstTokenMs`, step 5's measured-latency hook; an estimate of 2.5 s until then), else luna.
- **Serving** (`infra/models`): `luna_plus` is luna with reasoning one step up (text `none` → `low`; voice `none` → `low`, `low` → `medium`). A request without a tier is byte for byte what it was. **Escalation** (`ShannonTierRequest.escalation`, `withToolRounds` option `escalate`): once a turn, at a round boundary after a tool failed (not a refused name) or after a round with tools ran out of time, and only while no word of hers has gone out (a streamed text round that wrote is the answer; on voice not once anything was said, a waiting phrase included): every later round is `luna_plus`. The result says `escalated`.
- **The turn verifier** (`SHANNON_TURN_VERIFY`, `mind/selectors/turnVerifier.ts`): in a turn that offered her a write (and could write), a sentence that claims she wrote, saved, made or sent something of hers must be matched by a write that worked; else her text reply gets one fixed line in her voice (`WRITE_CLAIM_CORRECTION`). On text, when the policy asked for verification and at least 15 s are left, a luna checker in its own context (`infra/models/turnChecker.ts`; her reply and the closed results of her tools; usage lane `chat`) may flag what the pattern missed. On voice her words were already spoken: the verdict is learned, the reply is not amended.
- **The competence table** (`shannon_tier_outcomes`, `mind/selectors/tierCompetence.ts`): one row per routed turn (tier served, kind, surface, Talk, G), settled by the owner's next turn in the Talk (`tierOutcome`: G ≥ ⅔ and S ≥ ½) or after 30 minutes from G alone; competence is the Beta(1, 1) fold per (tier, kind). Read for routing only; never reward, mood or the value table. Created by the API process; kept 90 days.

## The Sonnet tier (step 5; owner answers I-1, I-2, I-6)

- **Inert by default.** `configuredSonnet` (`wiring/sonnetWiring.ts`) builds the adapter only with the key (`SHANNON_ANTHROPIC_API_KEY`, else `ANTHROPIC_API_KEY`) **and** `SHANNON_SONNET_ROUTING=on` (default off, read only as `on`/`true`/`1`/`yes`) **and** stage 2's difficulty on. Without it the kernel's chat model is luna itself, every request is what it was, and the policy serves `sonnet` as `luna_plus`. The coordinator turns the switch on in production after a live `tier.*` run.
- **The tiered model** (`infra/models/tieredChatModel.ts`): a request with `tier: 'sonnet'` goes to Sonnet; every other request goes to luna unchanged. A Sonnet failure or refusal before any word went out and before any tool ran is answered by plain luna (no tier, no escalation), with one content-free log line; the caller's cancellation is not retried. After a tool ran or a word went out, a failure ends the turn with her fixed out-of-time line, as on luna, so no write runs twice.
- **The adapter** (`infra/models/anthropic/`, `@anthropic-ai/sdk` 0.131.0, model `SHANNON_SONNET_MODEL`, default `claude-sonnet-5-5`):
  - *Prompt.* Built from luna's own parts (`chatTurnRequestBody`, the voice payload's parts): her identity, the fixed instructions, the tool instructions and what she knows of the owner are one `system` block with `cache_control` (tools render before it: tools and system are the cached prefix); the turn's context is a mid-conversation `system` message after the owner's words; consecutive turns of one role are joined and a conversation that begins with her turn gets a user marker first. Only these lines are Sonnet's own: `SONNET_TEXT_LINES` (the JSON reply only, no prose in a calling turn), `SONNET_VOICE_LINES` (spoken words only), `SONNET_WEB_LINE` (search before answering). The registry's text is unchanged.
  - *Tools.* Her registry tools as `strict` tools with the same names and descriptions; the limits strict schemas do not support (`minLength`, `maxLength`, `minimum`, `maximum`) are written into the property's description. `tool_choice` is `auto`, and `none` for the answer without tools (forced use is a 400 on this model). The rounds (`anthropicRounds.ts`) are at parity with `withToolRounds`: the turn's one deadline, the six calls, `runToolStep` (the same session, gate, runner, parallel rule, refusal of names not offered, `tool_open`), all results in one user turn, the assistant turn appended whole (thinking blocks unchanged), a cut-off response or a timed-out round runs nothing and the answer comes without tools. A web search the server paused (`pause_turn`) is resumed at most three times.
  - *Web.* The server tool `web_search_20260209` (`max_uses` 3, voice 2 or 3) with `SONNET_WEB_LINE`, never a forced search; no function tool beside it, as on luna. Its pages become the reply's sources.
  - *Structured reply.* Text: luna's structured-turn schema through `output_config.format`, rewritten to the supported subset (`structuredSchema`: nullable types as `anyOf`, size limits in words), read with luna's `parsedChatTurn` and `chatTurnResult`. Voice: spoken text.
  - *Thinking.* Text `adaptive`, voice `between_tools`, at effort `low` (`SHANNON_SONNET_EFFORT`, `SHANNON_SONNET_TEXT_THINKING`, `SHANNON_SONNET_VOICE_THINKING` for tuning; `between_tools` is valid only at `high` or below, which is all the setting allows).
  - *Streaming.* Text: the `reply` field goes out as it is written (`ChatReplyStreamDecoder`); voice: every word, with her fixed waiting phrase before the first call of a turn in which she said nothing.
  - *Usage and price.* One `chat` row per response: input = uncached + cache write + cache read, cached = cache read; priced at 2 / 10 USD per million (cache write 2.5, cache read 0.20) and 0.01 USD per web search (`estimatedAnthropicCostUsd`).
  - *First-token latency.* On a streamed turn, the time from its first request to its first word or tool call; a rolling 80th percentile of the last 20 (at least 3) is `sonnetFirstTokenMs`, which the voice policy reads (I-2: Sonnet on voice only when the time left covers it plus 6 s; else luna).
- **The skill proposer of her sleep** (step 6's `strongest` hook, `configuredSkillProposer` in `wiring/sonnetWiring.ts`, `infra/models/anthropic/anthropicSkillModel.ts`): Sonnet whenever the Anthropic key is present, independent of `SHANNON_SONNET_ROUTING` (a sleep job, not a turn); without the key, terra as before. One structured answer per call, adaptive thinking at `SHANNON_SKILL_PROPOSER_EFFORT` (`medium` default), its usage on the background lane (`memory_background`, inside the monthly background budget) priced with cache reads. The maintainer of the pattern wiki stays on OpenAI.
- **Dependency.** `@anthropic-ai/sdk` is added to `services/api/package.json` and `pnpm-lock.yaml` (owner answer I-6, deployment core). The production install must fetch it once (the VM's offline store does not have it yet).
- **The `tier.*` set and the tuning harness** (`packages/evaluation/src/reach/tierSet.ts`, driver `services/api/tests/reach/reachTier.ts`): 25 owner turns (17 text, 8 voice) covering every tier, her study tools, the read tools, a web search, writes and a voice turn too short for Sonnet. Each runs through the real adapter (streamed) with stub tools and is judged on `policy.tier`, `request.accepted`, `answer.shape`, `tool.expected`, `claims.verified` and, on voice, `latency.first_token` (≤ 4 s); metrics keep first-token latency, tool calls and rounds, and the cost record keeps tokens, cache reads and yen. Model-free (`scripts/reach-measures.sh run --only tier.`) a script answers and the build is checked; live (`run --live --yes --only tier.`, with the key) it is the tuning harness: each record's inputs hold the model and the three tuning knobs, so `reach-measures.sh compare` compares only like with like. The model-free response shapes follow the SDK's types; the live run is what holds them against the API.

## Conversation choices in reward (owner answer I-3, `SHANNON_CONVERSATION_REWARD`)

This reverses stage 1's rule that a conversation's tool call is data only (`docs/cognition-ledger-contract.md`, the choice ledger).

- **Recorded at the end of the turn** (`recordTurn`, `wiring/turnRoutingWiring.ts`) in the stage-1 choice ledger: each tool call that ran (`tool.<name>`, source `tool_call`) and the turn's tier (`tier.<served>`, source `turn`), surface `text` or `voice`, context `<band>.<alone|others>`, subject `talk` (the Talk), pending. Stage 1's immediate data-only record of a conversation tool call is not made then (`server.ts`).
- **Closed signals.** G (reported as the choice's success, in [0, 1]): the mean of the signals that apply: the tool worked, the turn ended inside its deadline, the verifier found nothing (when it checked); for the tier, inside the deadline, the verifier, and every tool worked. S: the owner's next turn in the same Talk, Jev's `retry_or_correction` inside the band: ≤ 0.1 → 1, ≥ 0.9 → 0 (settle code `next_turn`), else ½ with code `next_turn_unsure`, which never moves her mood. No next turn in 30 minutes: S = ½, code `turn_expired`, which never moves her mood (`MOOD_INELIGIBLE_CODES`). W: 0 (no linked prediction yet). r = (W + S + G)/3 as for every choice.
- **Effects.** Settled conversation choices are folded into the value table with her own time's (same cells: `tool.study.search` learns from both), are claimed by the reward mood under the same warm-up (a cell that learned from three) and hourly cap (the stationary band) (`turnRouting.test.ts`, a chat burst of twenty calls), and may appear in her value facts (facts only, never with anyone else present, as before). Stage 1's data-only rows (no Talk) are never folded or claimed.

## Skill memory (step 6, `SHANNON_SKILLS`)

ADR-0008 §8 「記憶は目次は毎回、中身は必要なとき」, with WikiSkill's three layers (arXiv 2608.27454, coordinator 2026-10-07) and review rules and provenance adapted from Hermes Agent (Nous Research, MIT; `THIRD_PARTY_NOTICES.md`).

- **Three layers.** The raw experience (her turns, her settled choices, the outcomes of her tools and steps) is only read; it is never edited here. The **pattern wiki** (`shannon_skill_patterns`, `shannon_skill_pattern_log`) holds pages of a failure mode (`failure`) or a strategy (`strategy`), each with what to do about it, and the log of how every page evolved (created, patched, appended, merged, deprecated). The **skills** (`shannon_skills`, `shannon_skill_revisions`) are what a turn may use. Nothing is deleted: a deprecated page and a retired skill are kept for reference. **Pages are never given to a turn** (WikiSkill: raw patterns given to the acting model made it worse, 63.7 → 60.9); they feed the proposer only.
- **SKILL.md** (`skillDocument.ts`): a frontmatter of exactly `name` (lower-case ASCII words joined by `-`, at most 40) and `description` (one line, at most 36 characters), then `## 手順` (never empty), `## 補助`, `## 参考`, in that order; at most 4,200 characters. The validator refuses anything else, a credential-shaped text (`looksSecret`) and a prompt injection (`injectionThreats`: an instruction to ignore earlier instructions, a new role, a system or developer message, a tool call, a request to send a credential, hidden direction characters). A skill keeps the pages that motivated it (`purpose_pattern_ids`, its PURPOSE).
- **The sleep** (`skillConsolidation.ts`), after knowledge consolidation in the worker, inside the shared background budget, never failing the batch:
  1. Model-free: uses that waited for the owner's next turn settle from G alone; a skill or a page built from something the owner had her forget is retired or deprecated (`source_forgotten`); trials are judged (below); active skills whose last eight resolved uses (at least five) succeeded less than 0.4 retire.
  2. **The maintainer** (one call, terra): root-cause analysis of the day's **failed episodes** (her choices in one Talk, or in her own time less than half an hour apart, with which step failed and how it was settled: closed symbols only) and the strategies of the successful ones, with her confirmed notes and the summaries of the day's turns with the owner alone as evidence; it edits the wiki incrementally (create, patch, append, merge duplicates, deprecate), at most six edits a night, each citing evidence ids.
  3. **The proposer** (ReAct, up to three runs a night): it is given the pattern index, the skills (whether each may be edited, its uses and successes), the capacity, and the changes the audit saw reverted; it opens the pages it needs (up to two rounds), then proposes **one** change or none: a targeted patch (replacements of passages that occur exactly once, applied to the current version read again in the same pass) by default, or a new class-level skill. Order of preference: patch the skill that was loaded, then a broader existing skill, then a support section, then a new skill. At most two new and three patched skills a night. Every proposal names its pages.
  - **What is never captured** (Hermes Agent's rules, `skillSleepRules.ts`): environment or setup failures, "tool X is broken", transient errors, one-off stories, unresolved failures presented as a method; a pitfall is a rule plus one clause of why; a skill is fixed in place, never with an appended "UPDATE" section.
  - **Models.** `SHANNON_SKILL_MODEL` (else `SHANNON_KNOWLEDGE_MODEL`, else terra) for the maintainer; `SHANNON_SKILL_PROPOSER_MODEL` (else the same) for the proposer. The proposer should be the strongest model there is (skills from a stronger model carry over to luna): `createConfiguredSkillSleepModels` takes a `strongest` hook, where Sonnet 5.5 is plugged in once step 5's Anthropic adapter and key are present. Usage is the `memory_background` lane.
- **Every body and page is checked before it is stored**: `conversationSecrets` (what the owner asked to keep secret, marked 機微 by hand, or had her forget) and the owner-private check judged for an unnamed guest (`othersSecrets(...).withheld`), since every skill has a copy in a folder guests can read (owner answer I-4: 内緒 never enters a skill, checked when the body is built, not at export); a copy check against the day's turns (24-character runs, the knowledge notes' rule); the injection scan. A check that cannot be read writes nothing. Lint warnings (`incident_log`, `update_section`, `oversized` over 3,000 characters) are recorded with the change in the audit.
- **Trials and the audit** (WikiSkill's acceptance gate, adapted: Shannon has no validation set). A new skill and a patched version are on **trial**. A new skill is accepted (active) after two successful uses and retired if its first three bring fewer; a patched version is judged after three uses against the success rate of the version before it (that version's resolved uses, or ⅔ with fewer than three): kept, or reverted to it. `shannon_skill_audit` keeps each proposal: its target, its diff, its pages, the rate it had to reach, the lint, what its trial measured, and `accepted`, `reverted` or `superseded` (the owner's edit or a rollback ended it). A change the audit saw reverted (the same body, or the same target for the same pages) is refused (`audit_reverted`) and shown to the proposer, so a failed edit is not retried. While a skill is on trial nothing else changes it.
- **Provenance and rollback** (Hermes Agent, adapted). Every revision records its actor (`sleep`, `conversation`, `owner`), its evidence ids, the sha256 of the body before and after, and whether the skill was pinned. A rollback (a failed trial's revert, or the owner's) is a new version restored from a revision, after a **safety snapshot** of the current state; if the snapshot cannot be written nothing changes (fail closed). The sleep refuses mechanically to write to the owner's version (`owner_edited`) or a pinned skill (`pinned`), a retirement included.
- **A use** is a skill whose content she loaded with `skill.read` in a turn, not one listed in the index. It is noted on the skill at the turn's end with G (the call worked, the turn ended in time, the verifier found nothing), and settled like a tier's outcome (`tierOutcome`: G ≥ ⅔ and the owner's next turn in the Talk not a retry or correction, Jev's `retry_or_correction`; after 30 minutes from G alone). With the conversation reward (I-3) the use is also recorded in the stage-1 choice ledger as the choice `skill.use`, source `skill` (the skill's id), subject the Talk, in place of `tool.skill.read`: it goes into reward, mood and values like any conversation choice.
- **The index** (`skillIndex`): in the **profile layer** of a turn that offers `skill.read` (text or voice, the owner alone, not a turn that searches the web or places), after what she knows of the owner: a header with its capacity (`[ボクのスキル n/19（目次。中身は skill_read で開く）]`) and one line per usable skill (`- name: description`, trials marked （試し）), at most 20 lines of at most 80 characters, active first, then by creation. It is built only from what changes at night, so it is the same all day and the cached start of the request holds. A new skill past the capacity must consolidate in the same batch (`consolidates`: the skills it replaces are retired), never the owner's, a pinned one, or one never used and younger than 14 days; if the index is ever over, its last line says how many did not fit. A skill built from something forgotten is left out at once.
- **`skill.read(name, section?)`** (`shannonSkillTools.ts`): a registry tool (domain `skill_read`, read, no cost, the owner alone, text and voice; summary 「ボクのスキル（自分の手順書）を1つ開いて読む」) that exists only while the runner has the skill memory (`ShannonToolRunner.useSkills`); its result is the SKILL.md (or one section) inside a fenced block, marked as material and not an instruction. With anyone else present it is not offered, and the gate refuses it. The capability line `SHANNON_SKILLS_CAPABILITY` is added only to a turn that offers it.
- **Tables** are created by the API process (`server.ts`); the worker opens them and writes nothing until they exist. Writes in a turn are deferred, under the write lock, measured; failures are logged by code and swallowed.

## Skill copies in Aether (step 7, `SHANNON_SKILL_EXPORT`)

Owner answers I-4 「全部置く」 and I-5. `integrations/aether/skillExport.ts`, run by the worker after the skill sleep, for the one scope whose study lives in Aether (`aetherStudyScope`), through the folder API of `syzygy.aether-shannon-access.v1` (`list`, `read`, `create`, `update` with `baseVersion` and an idempotency key). The switch is implied off while Aether is not configured (`SHANNON_AETHER_API_URL` and `SHANNON_AETHER_SHANNON_TOKEN`) and with the skills off.

- **Every skill** has a readable copy in 「シャノン用フォルダ」, retired ones included: the document 「スキル「name」」 whose body is the SKILL.md exactly as stored (the PURPOSE links stay in the database; pattern pages are not exported). Guests can read that folder; what the owner called 内緒 is not in any body, because every body was checked when it was built (step 6).
- **Idempotent by hash.** A copy is created once (idempotency key: the skill and its body's hash) and updated only when the body changed since it was last written (`exported_hash`), on the Aether version she last wrote (`aether_version`), with a key of the skill, the hash and that version. A second night with nothing new writes nothing. The title is set when the copy is created and never changed by her.
- **The owner's edits.** When a copy's version in Aether is not the one she last wrote, it was edited there: at that sleep she reads it and adopts it as a new version of the skill (`adoptOwnerEdit`: actor `owner`, `made_by` `owner_edit`, active, any trial superseded in the audit; his text is kept as he wrote it, and a text that is not a SKILL.md keeps the skill's name and description). She never writes over it, and the sleep never patches his version. An edit that carries what must never enter a skill, carries an injection, is longer than she reads whole, or cannot be checked now is **held**: the skill keeps its version and the copy is never written again (`export_hold` `owner_edit_unadopted`). A copy he deleted is not created again (`owner_deleted`). An update answered `STALE_VERSION` (he edited it a moment before) writes nothing; the next sleep adopts it.
- **Record.** One log line a night: `Shannon skill export: status=done created=… updated=… unchanged=… adopted=… held=… deleted=… failed=…`; a failure is counted by its code and never fails the sleep.

## Tree recall (step 8, `SHANNON_TREE_RECALL`)

ADR-0008 §3 「想起とスキル探し：フォルダや見出しの木を Jev でたどる（ビーム幅 4 程度）。拾った断片の役立ち度を採点し、十分な断片が出たら止める」. It **replaces luna's `selectSections`** in `recallShannonKnowledge` (`mind/recall/turnKnowledgeRecall.ts`): while tree recall is configured luna never navigates a note.

- **The tree** (`treeRecall.ts`): her knowledge notes the turn may use (the chosen ones first, then the rest by recency, at most twenty), each by its heading tree; and, only while the owner alone can see or hear the reply (the turn's presence, and what the server knows of others present), her usable skills by their sections and the documents of 「シャノン用フォルダ」 and her study by title (I-7: the owner's documents only when he is alone; the folder's copies of her skills are left out, they are the skills).
- **What Jev sees** (I-7): the turn's words (at most 2,000 characters) and, for each node, its heading path and at most 200 characters of its own text. No id, no body, no audience. One `noul` question per node: how useful is this passage for answering now.
- **The beam** (`treeBeam.ts`, pure): width 4, depth at most 3; a leaf (or any node at the last level) that scores is a passage, and the four best others above 0.1 (not confidently useless) are opened. A passage counts only at ≥ 0.9 (Jev's `yes`, §14). It stops at two such passages, at useful passages summing to 1.6, when the time is up, when Jev fails, or when nothing is left. An opened node none of whose descendants was useful stands as a passage of its own if it is useful itself. A note none of whose sections Jev is sure of keeps its deterministic sections.
- **When.** Text: every turn that recalls knowledge (or, with the owner alone, has skills or a folder to walk), within 1.5 s. Voice: only a turn of a `skill_*` class (a `skill_simple` turn now recalls too), one level, within 900 ms; any other voice turn keeps the deterministic sections. Past the time the turn goes on with what it has; when Jev fails, the deterministic sections stand (as when luna failed).
- **The audience** is checked before and after each call: an owner-only node is never shown to Jev unless he is alone before the call, and is dropped if he is not alone after it.
- **The result**: the sections chosen per note (else the deterministic ones), at most four notes (the chosen three and what the beam found), her skills' passages, and pointers to folder documents (a story of her study without its title). All of it reaches the turn **inside one fenced block labelled as data, not instructions** (`fencedRecall`, Hermes Agent); a fence inside a passage cannot close it. With others present the block carries the unlabelled marker, as the notes always did.
- **Prepared ahead** (Hermes Agent): when a recall ends, the next turn's skill and folder nodes are prepared in the background (the folder is listed through Aether then, never inside a turn), so a turn, above all a voice turn, does not wait for them.
- **Traces**: one `recall_beam` per Jev call, closed values only. Cost: up to three Jev calls a text turn.
- **Switched off** (`SHANNON_TREE_RECALL=off`, stage 2 off, or no Jev key): recall is exactly what it was; `stage2SwitchedOffRecall.test.ts` holds it against digests recorded on ca7cf519 (`fixtures/stage2-switched-off-recall-v1.json`).

## Decision traces

The trace vocabulary (`contracts/decisionTraceContract.ts`, table `shannon_decision_traces`, unchanged) gains the surface `text` and three decisions:

| Decision | What it is | Answers (closed values only) |
| --- | --- | --- |
| `tool_menu` | Jev's choice of the tools whose schemas a turn sends | the chosen tool's name (or `none`), how many were offered, how many groups |
| `difficulty` | Jev's difficulty questions (and the menu, in the same call) | `kind`, `strong`, `verify`, `multi`, `retry` (−1 when not asked or not answered), and the menu's answers when there was one; the tier itself is recorded as the choice `tier.<served>` |
| `recall_beam` | one level of a beam search of tree recall (step 8): one trace per Jev call | `level`, `width`, `scored`, `best`, `useful`, `stop` (`continue`, `enough`, `sum`, `exhausted`, `failed`) |

Every stage-2 trace also holds the §14 fields (`qv`, `ql`, `qh`, `h`, `cached`, `a.<key>`). A trace never holds the owner's words, a tool's input or a heading's text. Jev's cost per call follows stage 1 (`SHANNON_JEV_USD_PER_CALL`, unset: unknown).
